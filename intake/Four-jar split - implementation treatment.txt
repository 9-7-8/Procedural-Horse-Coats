Four-jar split (Base, Breeding, Equipment, All-in-One) - implementation treatment

This treatment is written across several files in intake/four-jar-split/, so each can be open beside the code
while a piece is built. THIS FILE IS ONLY THE ENTRY POINT; the folder is the treatment. process-intake: build from
the piece files, in order, and read 00, 01 and 07 first.

Scoped with the owner and probed (/probe-a-scope, three rounds). Every "Decided" line is her call; "Recommended" lines
are the scoping session's, not asked; "Open" lines are still to be settled, by whom is said on the line; "UNVERIFIED"
lines are facts this file set has not proved and the building session must check first. Source of truth for what exists
is wiki/architecture.html, wiki/horse-gear.html, wiki/carts.html, wiki/horse-care.html, wiki/horse-browser.html and
wiki/api-notes.html. These files are retired (deleted, per /process-intake step 8) as each piece ships and moves onto
those pages' Gameplay and Coding tabs; keep 01 and 02 until the last piece ships.
Release: each piece counts toward the next patch release (Recommended); the first four-jar release is piece 3. Saves keep
loading by keeping every saved key (rule 10); the one deliberate loss is that a world that used an add-on will not load
without it unless the server.toml override is on (Decided).

THE ASK, IN ONE SENTENCE
Ship four jars per release: a required Base (framework + every quality-of-life feature + hunger + sex rule + plain wild herds),
a Breeding add-on and an Equipment add-on (each needing only Base), and an All-in-One used instead of the three. Owner
(2026-10-03): "I want to make this mod a little more modular ... Every release, we should ship those three jars plus a 'all in
one' jar", later "QOL becomes the base ... and we remove core as a concept".
