Five-jar split (Core, Breeding, Equipment, Quality of Life, All-in-One) - implementation treatment

Scoped with the owner. Every "Decided" line below is her call; "Recommended" lines
are the scoping session's, not asked; "Open" lines are still to be settled, by
whom is said on the line; "UNVERIFIED" lines are facts this file has not proved
and the building session must check first. Source of truth for what exists is
wiki/architecture.html, wiki/horse-gear.html, wiki/carts.html, wiki/horse-care.html,
wiki/horse-browser.html and wiki/api-notes.html. This file is retired (deleted, per
/process-intake step 8) as each piece ships and moves onto those pages' Coding tabs.
Written from the cloud session (no game, no jar build): every claim about code comes from
reading it or from two read-only survey agents whose file lists the building session must
re-grep before relying on them.
Release: each piece counts toward the next patch release; the five-jar release itself only
turns on with the last piece. Saves keep loading (hard rule 10) - see Decisions H.

1. THE REQUEST, AS GIVEN
------------------------
"I want to make this mod a little more modular, because it breaks into three major parts:
the procedural horse coats, the equipment overhaul, and the horse QOL changes. Every
release, we should ship those three jars plus a 'all in one' jar. Each jar should be
modular, so they can use any subset of the jars (except it's redundant to combine with the
all in one)" (owner, 2026-10-03).
Her answer to how the shared code is handled: "There's a core base game code jar they have
to download, then they pick their add-ons, and they can pick 'all in one' instead. So we
ship five jars with each release. The goal is to keep the file size of the core base game
jar as small as possible."
Read as: Core (small, required by the three parts), Breeding, Equipment, Quality of Life
(each needs Core, none needs another part), and All-in-One (Core plus all three parts in
one file, used INSTEAD of them). Confirmed in the answers below.

2. IN SCOPE, AND WHAT IS NOT
----------------------------
In scope
- Five jars per release, one lockstep version number, built by one Gradle build.
- Splitting :common into four Gradle modules and :neoforge-26.1.2 into the matching jars.
- A genome-agnostic horse record in Core; extension points in Core for info-screen tabs,
  H-browser tabs, checklist tasks, and per-jar registries (items, blocks, attachments,
  payloads, menus, config specs, mixins).
- A public, documented API on those extension points (owner chose it; see Open 3).
- A size report and a budget gate on Core in the build.
- A world marker so a world that used a part refuses to load without it.
- Readable "incompatible" errors for all-in-one plus a part.
- Release procedure, README, wiki and tests updated for five jars.
Not in scope (re-askable unless stated)
- Any new feature. The split moves code and splits registries; no gameplay changes except
  the ones Decided below (hunger/healing absent without Breeding).
- The rename to Ixora's Horse Overhaul (own treatment; this waits on it, see Decision N).
- Bridle/saddle split, horse shoes, command whistle, troughs: each stays its own treatment
  and lands in the jar assigned below (Decision B).
- A fourth part jar for carts, or for realm/villagers (offered, not chosen).
- Per-jar version numbers (offered, not chosen).
- Other loaders and other Minecraft versions (the port treatments); each now multiplies
  by five jars, so they must be re-sized after this ships.

3. WHAT ALREADY EXISTS, SO THE BUILDING SESSION DOES NOT REDO IT
----------------------------------------------------------------
Today: three Gradle modules (settings.gradle.kts: :common, :neoforge-26.1.2, :web), ONE
jar. neoforge-26.1.2/build.gradle's 'jar' task copies :common's compiled classes into it
(excluding *Tool classes and example-genes). mod_id, mod_version and mod_group_id are one
set in gradle.properties; there is one neoforge.mods.toml and one horsegenetics.mixins.json
(14 common + 6 client mixins, per the survey: re-count).
common/ is 400 files (survey counts: genetics 247, coat 36, breed 23, horse 18, trait 16,
parts 15, repro 11, care 9, name 4, herd 4, stable 3, cart 2, log 2, realm 2, wild 2,
progress 1). neoforge has about 545.

The seams, each one a single hard-coded file today (all paths under
neoforge-26.1.2/src/main/java/com/example/horsegenetics/neoforge/ unless marked C =
common/src/main/java/com/example/horsegenetics/common/):
- HorseGenetics.java: the one constructor registering everything, order-sensitive. Gene
  and breed specs load first (ModGeneSpecs.load, api/GeneRegistration, ModBreedSpecs.load);
  then DeferredRegisters (ModAttachments, ModDataComponents, ModBlocks, ModBlockEntities,
  ModMenus, ModItems, ModEntities, ModAttributes, ModPoiTypes, ModVillagerProfessions,
  ModRecipes, loot, ModBiomeModifiers, ModStructureTypes, ModTriggers, ModCreativeTabs).
  ModdedMaterials.scan(), ModdedArmour.init(), DoubleGates.init() and Jumps.init() must
  run BEFORE ModBlocks/ModItems attach to the bus (they register as the classes load):
  the nastiest seam. HorseCarts.init() registers through RegisterEvent.
- network/ModNetworking.java (942 lines): all 44 payloads in one method. data/ModAttachments
  (17 types). menu/ModMenus. item/ModItems (590 lines), block/ModBlocks. ServerConfig (one
  SPEC, 1394 lines) and ClientConfig, written to phc/server.toml and phc/client.toml. The
  carts already keep their own two files (carts/CartsConfig).
- client/HorseInfoScreen.java (about 2300 lines): a private Tab enum of eight tabs
  (Overview, Gear, Genes, Health, Coat, Other genes, Offspring, Family tree), including the
  gear doll, picker, Dress button and drawDraught (uses CartDraft, CartKind, CART_METRES).
- client/HorseBrowserScreen.java (about 4500 lines): a private Tab enum of ten tabs
  (Getting started, Recipes, My horses, Horse realm, Query, Breeding preview, Log, Gene
  database, Alleles, Breeds). Mostly Breeding content; the Log tab is C/log/HorseEventLog.
- client/TutorialPage.java: the chapter-to-task mapping, hard-coded (about 69 ProgressTask
  references, about 8 cart pages). C/progress/ProgressTask.java: one enum, about 103
  constants, completed by HorseProgress.complete from about 44 files; one advancement
  trigger (ModTriggers.PROGRESS_TASK) is data-driven off it.
- server/HorseRecords.java and C/horse/HorseRecord.java (a record) hold the genome; read by
  QOL (HorseSocialAttachment, HerdSocialHandler, StallSignHandler, EnderWhistleCalls) and
  Equipment (server/HorseDraft: pullOf, speedOf; TackEquipHandler).
- server/HorseCareHandler.java (554 lines): ONE slow tick doing bond, hunger, healing, herd
  flag and breed-based progress awards. C/care/Hunger.java drains by the vanilla SCALE
  attribute, not the genome; gating of healing reads the diet locus (HorseDietHandler).
- api/: only RegisterHorseGenesEvent and GeneRegistration (genes only; javadoc says
  unverified in a running game).

Closest precedent: carts. They are already a self-contained subsystem with their own
config files, registry (HorseCarts.init), payloads and 7 mixins, and touch the horse only
through server/HorseDraft. Treat carts as the template for how a part plugs in.

LOOKS BUILT BUT IS NOT
- There is no extension API for tabs, rows, tasks, payloads or items. Gene registration is
  the only hook.
- Shoes, saddle pads, saddlebags, bridles and halters are slot enums and planned wiki pages
  only. The 17 gear item tags under data/horsegenetics/tags/item/gear/ are empty except
  mane.json and tail.json (rescuing_braid). Equipment's real content today is carts, the
  19-slot screen, the rescuing braid and dyed tack on the bench.
- common/ is NOT organised by the three parts. Hunger, bond, herd, braid and send-home logic
  sit together in C/care/ and C/herd/; 'wild herds' (HerdManager) is Breeding despite the name.
- Horse speed does not read shoes yet.

4. THE PIECES
-------------
ORDER: 1 Core extraction -> 2 Equipment jar -> 3 Quality of Life jar -> 4 Breeding jar plus the
five-jar pipeline (owner picked this order). Until piece 4, the shipped artifact stays the
one all-in-one jar, so each piece leaves a playable game and a release can still be cut.

PIECE 1 - Core extraction: the same single jar, built from Core plus parts (L)
-----------------------------------------------------------------------------
What the player sees: nothing. The same jar plays the same; the owner can see the module
boundaries and a Core size report in the build output.
Decided
- Core contents = only what two or more parts need. Everything else belongs to a part.
- HorseRecord in Core is genome-agnostic: id, name, sex, gelded, owner, and a hook for a
  stat provider and for part data (owner). Breeding attaches the genome and supplies stats;
  without Breeding a plain record and vanilla stats are used.
- Extension points in scope: info-screen tabs and H-browser tabs; checklist/tutorial tasks
  per jar; per-jar registries (items, blocks, attachments, payloads, menus, config specs,
  mixins); and a public third-party API on all of these.
- H-browser frame and its Log tab live in Core, so every jar can write log events; Breeding adds
  the other tabs.
- common/ splits into :common-core, :common-coats, :common-equipment, :common-qol. :web
  and the all-in-one depend on all four. Hard rules 1 and 2 hold for each of them.
- Core size is enforced by the build: it prints per-jar sizes and FAILS if Core exceeds a
  recorded budget; the budget is set from the first measured build and raised only by a
  deliberate edit with a reason.
Recommended
- The attachment keys and the horse_record codec keep their exact current serialised form
  so no migration is needed; Breeding' genome is stored under the same key it has today.
  (Rule 10: if this cannot be kept, stop and write the migration.)
- The ProgressTask enum becomes a registered task id list; each jar contributes its own
  tasks, with the existing ids and advancement JSONs unchanged.
- HorseCareHandler is split into a Core scheduler (the shared slow tick, with a list of
  subscribers) plus one subscriber per part, so the tick is still one pass.
- Do the class-load-order registrations (ModdedMaterials, ModdedArmour, DoubleGates,
  Jumps) as explicit init calls per part, in a fixed order called from each part's own
  constructor, rather than by class loading.
Open (building session)
- Which classes are "needed by two or more parts" for Core; the building session starts by
  producing that list from a dependency scan and posts it on wiki/architecture.html.
- Whether ServerConfig splits into one spec per jar, one file per jar (Recommended:
  phc/server.toml keeps its path; each jar adds its own section and a missing section is
  fine), or a shared file with optional sections.
Where the code lives: C: record, ProgressTask registry, HerdRules/Bond/Hunger interfaces
that need no genome, event log. NeoForge: the extension registries, ModNetworking helper
that takes a registrar, config plumbing, info and browser frames, DebugAnnounce, creative
tab helper, lang merge.
Data and saves: no saved key may change (see Recommended above).
Sync: the existing record sync payload carries the slim record; part data rides in parts'
own payloads.
Config: none new, apart from Core's own budget in the build (not a game config).
Tests: C-level tests for the slim record round trip and the task registry; a test that
Core's classpath imports nothing from the part modules (a Gradle dependency check or an
ArchUnit-style scan written as a JUnit test); the existing suites for the touched classes
(--tests only, hard rule on the full suite); runGameTest; a server boot to "Done (".
Play checks: load an old world and see the same horses, names, genomes, gear, hunger;
open the info screen and the H browser and see every tab as before.
Docs: wiki/architecture.html (module split, packages, data flow), wiki/api-reference.html
and api-notes.html (the new API), wiki/coding-notes.html (how to add a part).

Sync: the gear payloads and the five cart payloads move to the Equipment registrar.
Config: carts keep horsegenetics-carts.toml and the -client file (names change only with the

Docs: wiki/horse-gear.html, carts.html, cart-bench.html, item-rescuing-braid.html,

PIECE 4 - Breeding jar and the five-jar release (L)
------------------------------------------------
What the player sees: download Core plus any of the three parts, or the all-in-one on its own.
Decided
- Breeding owns everything not assigned elsewhere: genetics, coat painting and pipeline, breeds,
  breeding, pedigree, body stats, breed designer and horse designer, breeding/splice carrots,
  research papers and the gene database, stasis chambers, banks and the bank block, the vet kit,
  hunger/diet/healing, wild herds (HerdManager), the horse realm and hay portals, stables,

- The five jars: ixoras_horses_core (Core); ixoras_horses_breeding, ixoras_horses_equipment,
  ixoras_horses_qol (parts, each requires Core, none requires another);
  ixoras_horses (the all-in-one, which keeps the existing id and holds Core plus all three
  parts, with no separate Core needed). Display names: brand + role (owner: "Brand + role:
  ixoras_horses_breeding, and so on").
- Namespace: every jar registers under the one namespace of the all-in-one, so items, blocks,
  entities, attachments and gene keys keep identical ids and a world moves between the
  all-in-one and any combination (owner: shared namespace).
- Lockstep versioning: one number 0.<compat>.<patch> for all five; every release ships all
  five; each part requires Core at the same compat series.
- Each part, and the all-in-one, declares the other four as `incompatible` where they
  overlap (all-in-one vs each part and vs Core; two copies of a part) so loading stops with
  a message naming the jar to remove.
- A world that has used a part REFUSES TO LOAD without it (owner), with a message naming
  the part to install. Nothing is deleted. A part first used in an existing world later is
  fine (adding is allowed).
Recommended
- The world marker: Core writes a SavedData file listing the parts that have been active in
  the world, updated on each load. An older world with no marker but with the mod's old data
  files is treated as "all parts used" (it was played with the single jar). A world with
  neither is new and may start with any subset.
- No override flag (matches the rename treatment, which also has none). Open for the owner:
  does she want an escape hatch for a server owner who deliberately drops a part?
- Name the Core id ixoras_horses_core (derived from "ixoras_horses_breeding, and so on"; not asked).
Open
- 3 (owner): the public API's stability promise. She chose to include it; what does it promise?
  Recommended: documented but marked unstable until 1.0.0, with the extension points listed on
  wiki/api-reference.html.
- 4 (building session): the horse villager professions and trades for tack (leatherworker,

- 5 (owner): the downloads' file naming, page layout and whether the release note lists five
  files. Recommended: names like ixoras-horses-<part>-<version>.jar, one note, five assets.
Where the code lives: Gradle (new modules, a build-wide version, a jarJar-free all-in-one task
that merges the four module outputs and a merged mods.toml and mixins config), the release

Data and saves: no registry id changes; the world marker is new and additive.
Sync: unchanged.
Config: phc/ stays the folder (the rename treatment moves it). Each jar writes only its own

Tests: the combination matrix, minimum five boots to "Done (": Core alone; Core + each single

Docs: README.md (which jar to download), wiki/releases.html, wiki/architecture.html,

5. DECISIONS (Part 4 headings not already covered inside a piece)
-----------------------------------------------------------------
A. The ask: Decided. Five jars from one build; any subset of parts on top of Core, or the
   all-in-one alone. For server owners, modpack makers and players who want only part of the
   mod. Smallest worthwhile version: Core + Equipment (carts) on vanilla horses.
B. Fit: bends no settled decision in the text read (decisions.html is a pointer page only;
   philosophy read in wiki/text/philosophy.txt). UNVERIFIED that it bends none: the building
   session re-reads philosophy for "horses only" and "carrot not stick" before piece 1.
   Parts assignments (Decided, owner): Breeding = genetics, breeding, stats, breeds, breed designer,
   carrots, papers, stasis, vet kit, hunger and healing, realm, stables, villagers, wild herds.
   Equipment = gear, tack, shoes, pads, carts, braid. QOL = bond, herd socialising, whistles,
   signs, jumps, gates, posts, bench.
C. How the player meets it: Decided that the three parts are downloads on the mod pages
   alongside Core. The tutorial/checklist/H-menu only show a part's content when it is
   installed (Piece 1). Recommended: Core's H-menu "Getting started" lists which parts are
   installed and which jars add what.
D. Genetics: untouched in rules; Breeding keeps the gene registry. Gene keys and allele order are
   unchanged. Both editors (rule 5): unchanged by this piece except the module imports.
E. Breeds: no change.
F. Items and blocks: no new items. Ids unchanged. Per-wood variants (jumps, gates, carts) keep
   their author-time bake and run-time twin; bakes read their module's registry now.
G. Config: Decided that a disabled or absent part simply has no config. A bad value never crashes a
   world load (existing rule).
H. Saves and permanence: Decided that nothing saved changes key. Decided that a world that used a part
   refuses to load without it (owner). UNVERIFIED that the marker can be read before chunks load on
   both a singleplayer open and a dedicated-server start (same uncertainty as the rename treatment).
   Removing a part and then re-adding it restores everything.
I. Multiplayer: payloads split by registrar; a client missing a part the server has is refused by
   NeoForge's own mod-list check (UNVERIFIED how it words it for optional mods; if a part is declared
   required on both sides there is nothing to design). Recommended: all parts declare side=BOTH.
J. Compatibility: Jade, Waystones, FTB Teams and HorsePowered compat stay where their feature is
   (Jade: Core or Breeding; Waystones and FTB Teams: Breeding' ownership/teleport; HorsePowered: Equipment's carts).
   Recommended: a compat class loads only if its owning jar is present.
K. Performance: one shared slow tick (Piece 1) so no extra passes; cost per horse unchanged.
L. Testing: see each piece; plus a unit test that no Core class imports a part package.
M. Release: see section 8.
N. Sequencing: Decided (owner) that the split lands AFTER the rename to Ixora's Horse Overhaul. The
   five ids use the new brand. If the rename slips, this treatment waits; do not build both
   before the converter exists.

THREE MOST LIKELY WAYS IT GOES WRONG FOR A REAL PLAYER
1. A server owner swaps the all-in-one for Core + two parts and their world refuses to load, or loads
   and silently loses a part's data. Handling: the marker plus refusal (Decision H); play check: swap
   jars in both directions on a copy of the old world; Open: the escape hatch (4, owner).
