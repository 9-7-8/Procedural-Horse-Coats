Undead horse conversion - treatment, spec and implementation guide

Status: PLAN ONLY. Nothing here is built and no code was written for it.
The owner has settled the design calls D1-D8 and the bundle question (section 5). What
is left open is the two genes' own look and the API checks marked UNVERIFIED.
Nothing here has been checked in-game. Anything that touches a Minecraft or
NeoForge API is marked UNVERIFIED and must be read out of the 26.1.2 sources
(or proved in a gametest) before it is relied on - see CLAUDE.md hard rule 8.

Where this goes: intake/ is an inbox, not a plan (START HERE.txt). When this is
picked up it is routed onto wiki/undead-horses.html's Roadmap tab, and this file
is deleted. Section 12 says exactly what goes where. Appendix A is a script for the stage 0
check.


1. What is being asked
======================
Vanilla has two undead equines, minecraft:zombie_horse and
minecraft:skeleton_horse. They are not minecraft:horse, so this mod has never
touched them. The owner's design (wiki/undead-horses.html) is that undeath
becomes two loci - a skeleton gene and a zombie gene - carried by ANY breed on
an ordinary minecraft:horse.

This document adds the half that page does not have: what happens to the undead
horses that already exist. A world saved before this ships contains vanilla
zombie horses and skeleton horses - wild, tamed, saddled, armoured, named,
ridden, leashed, sitting in a skeleton-trap field, or still unloaded in a chunk
nobody has visited. Each of them must, when it next loads, quietly become a
horse of this mod: a real record, a real genome expressing the matching undead
gene, a coat, a name, a pedigree entry, resolved body stats, herd and care
attachments. The player should notice that the horse looks different and has a
name. They should not lose the saddle, the armour, the ownership, the lead, the
rider, or the horse itself.

"Backwards compatible" here means two things, and both are requirements:
  (a) An old save opens and its undead horses convert on their own, with no
      command, no migration screen and no data loss.
  (b) The mod can be removed or the feature switched off (config) and the
      vanilla undead horses go back to behaving as vanilla ones.


2. Back-compat is now a requirement, and rule 6 is gone
=======================================================
CLAUDE.md hard rule 6 ("no legacy or back-compat code, no saves worth keeping")
was removed by the owner once the mod went to a tester. From now on a change
that would break an existing world needs a migration path, and this feature is
the first one planned under that rule.
  - The converter is a PERMANENT adapter, not a one-shot migration: its input,
    a vanilla zombie_horse or skeleton_horse, never stops arriving (spawn eggs,
    /summon, skeleton traps, other mods, old saves). It is the same kind of
    thing as the path that gives an unrecorded vanilla horse a founder record.
  - The new loci need NO padding or migration code. Genotype.of() fills any gene
    a code does not mention with its default allele, and Genotype.parse() goes
    through it, so every existing horse reads as wild type (not undead) at the
    two new loci. The epigenome fill for a missing gene is the existing
    "record.hasGenome()" path in ensureExistingRecordResolved. Verify both with
    a test that parses a code saved before the genes existed.
  - Two things to check for other back-compat surfaces the new genes touch, as
    they are exactly what rule 6 used to excuse: the designer's genes.json and
    any saved designer/breed-designer files, and every checked-in genotype code
    in tests and fixtures (they should still parse unchanged).

3. What already exists (checked against the source, not assumed)
================================================================
The mod adds no horse entity. Everything hangs off vanilla minecraft:horse as
data attachments plus a renderer override (wiki/compatibility.html). That is
why the design is cheap, and it fixes the shape of the answer.

3.1 Nothing in common/ knows about undeath. There is no skeleton or zombie
    gene, allele, breed or painter yet. Both genes are still to be written, and
    the pipeline question (how a coat pipeline paints the absence of a coat) is
    still open on the page's Verification tab.

3.2 The founding path is the model to copy. HorseFoundingTickHandler runs on
    EntityTickEvent.Post, never on the join event or a server.execute task,
    because writing Attributes.SCALE can force-load a chunk and corrupt the
    chunk ticket iterator (a hard NullPointerException in
    DistanceManager.runAllUpdates). It handles each entity once per level load
    (HANDLED set, cleared on EntityLeaveLevelEvent) and rations work with a
    per-tick nanosecond budget (mayFound / charge). Any converter MUST live in
    the same place, under the same budget, for the same reason. Do not convert
    in EntityJoinLevelEvent.

3.3 HerdManager.assignFounder(horse, rng) founds a horse: it picks a breed,
    calls BreedFounder.roll(breed, rng, sex, magic), builds a HorseRecord via
    HorseRecord.founder(uuid, first, last, genome, lineageToken), applies it with
    HorseRecords.apply, resolves the body with
    HorseRecords.applyTraitsToEntity, and syncs the coat. BreedFounder.roll
    already has overloads that force allele pairs (List<AllelePair> forced, and
    MagicalVariant = gene + pair for magical herds). Pinning an undead gene pair
    onto a founder is therefore existing machinery, not new machinery.

3.4 There is a precedent for swapping one entity for another: LycanthropyHandler.
    It creates the new entity, copies position, baby flag, custom name and
    health fraction, calls setPersistenceRequired, ejectPassengers, discards the
    old one and addFreshEntity's the new one, all from an entity tick. It also
    has the reverse direction, restoring a Horse from a saved tag with
    horse.load(TagValueInput...), and a clearOfBlocks pass because a horse's
    box is bigger than the animal it replaced (a converted horse needs the same
    pass in reverse: a skeleton horse in a two-block gap).

3.5 Undead horses already reach part of the mod. ModAttributes.HORSE_TYPES names
    SKELETON_HORSE and ZOMBIE_HORSE (LAVA_MOVEMENT, DRAFT_POWER), the saddle
    equipment asset carries skeleton_horse_saddle and zombie_horse_saddle with
    the same dyeable layers, and every mixin targeting AbstractHorse (carts,
    flight while ridden, instant jump, rearing, two riders, regeneration)
    already applies to them. HorseRegenMixin's comment says it is for Horse
    only. These are what becomes dead code if the vanilla entities are
    suppressed - see section 9.

3.6 GeneticHorseRenderer is registered for EntityType.HORSE only (ClientSetup).
    Undead horses are drawn by vanilla's renderers today. Registering a second
    renderer for the undead types is NOT part of this plan (section 5.2).

3.7 BreedSpawnHandler (FinalizeSpawnEvent) only acts on Horse. It never sees the
    undead types, which is the "spawning overhaul is the actual work" point on
    the roadmap page.

3.8 MobGroups resolves "undead" through the vanilla entity-type tag, so a
    Horse carrying a skeleton or zombie gene is NOT in that group unless
    something makes it so (section 8.4).


4. Design summary
=================
- Undeath is two homozygous-recessive loci on a minecraft:horse. It is not an
  entity type. Carriers look like ordinary horses and are NOT undead for any
  effect (D6).
- A vanilla zombie_horse or skeleton_horse is treated as an unconverted horse:
  seen on its first tick, replaced by a minecraft:horse founded from a breed in
  that undead type's POOL. The pool starts with one breed each: the Great
  Valley Skeleton Horse and the Graveborn Warmblood. The breed pins the undead
  pair homozygous and also pins the diet, temper and stat loci beside it (D3,
  D-bundle).
- The loci also roll, rarely and expressing, in other breeds' founder tables,
  so "an undead Shire" stays possible later (D3b).
- The replacement is atomic per entity, idempotent, and can be switched off.
- Everything that identifies the animal to the player is carried across:
  UUID, name, position, age, health fraction, tame state, owner, saddle,
  armour, lead, passengers, persistence, team, custom tags.
- Everything that came from the entity TYPE (skin, stats, sounds, hitbox,
  tag-derived behaviours) is deliberately re-derived from the genome. That is
  the resolved-not-rolled rule; the old stats are not preserved.


5. Decisions settled by the owner
=================================
D1  Permanent adapter, not a one-shot migration.
D2  Conversion is ON by default from the first release of the feature. So the
    two genes, the two breeds and their look must all be finished in the same
    release; the converter must not ship ahead of them. A config switch still
    exists (section 7), defaulting on.
D3  A converted horse is founded from a POOL of breeds per undead type, not from
    Feral Mixed. Skeleton pool: the Great Valley Skeleton Horse. Zombie pool:
    the Graveborn Warmblood. One breed each for now; more can be added later
    without touching the converter. How a pool member is picked (uniform,
    weighted, seeded from the UUID) is a breed-file / BreedSpawnSettings detail
    for stage 1 (see 6.5).
D3b The undead loci are pinned by the two undead breeds ONLY in the first
    release. No other breed's founder table carries them yet (owner: "add per
    breed later"). The gene is still a locus any breed can be given later by a
    founder-table line, so 'an undead Shire' stays possible; nothing rolls it
    at random. So no other breed sheet changes, and the census diff is just
    the two new breeds.
D4  Old stats are dropped and re-derived from the genome. Health FRACTION is
    kept. State this in one sentence on the Gameplay tab and in the release
    notes.
D5  Skeleton-trap horses convert only after the trap has sprung.
D6  Only horses HOMOZYGOUS for an undead gene are "undead" for cleansing light,
    holy ward and the like. Carriers (heterozygous, look normal) are not
    affected. One clause in MobGroups.
D7  Other mods' undead horses are NOT converted. Leave a clean extension point
    so a patch for a specific modded horse can be written later (6.1, 7).
D8  A converted tamed horse starts with bond zero; the player's custom name is
    kept; a player-ridden horse waits until the rider dismounts; the realm and
    debug-pen dimensions convert too.
D-bundle  The breed sets the bundle. The undead gene is the visible undeath
    locus; the diet, temper and stat loci are separate loci pinned by the
    breed. No exception to "a concept is a breed, not a gene" is needed, and
    philosophy.html's live-test paragraph is rewritten to say so. This closes
    the first blocker on the Verification tab.
D9  Diet and temper REUSE existing loci; no new diet or temper genes. Zombie
    breed pins Diet=raw meat and an aggression allele. Skeleton breed pins a
    new DIET ALLELE (eats nothing, heals on its own - blood diet is the
    precedent for a horse fed by something other than food) and an aggression
    allele. The only new genes are the two undeath loci.
D10 Taming reuses PassificationGene (horsegenetics.passification). Both undead
    breeds ship aggressive and are passified with "their item", then tamed as
    normal. No new taming handler. (Details in section 5a.)
D11 Drops: bones and rotten flesh, then the vanilla undead sounds. Drops extend
    MagicItemDropGene with two alleles (its locus today has Dia, Egg, Swd and
    wild type only, and no bone or flesh); sounds go through the existing sound
    effect verb. Both UNVERIFIED as to fit - see 5a.
D12 A breed names its undead pool with a field on the breed sheet (e.g.
    "undeadOf": "skeleton" | "zombie"). BreedFilesTest validates it, the breed
    designer offers it, and joining a pool is editing that breed's file.

D13 Skeleton passification: Prm/Prm (permanent) with minecraft:bone.
D14 Zombie passification: FTm (temporary) with minecraft:rotten_flesh. The
    player must tame inside the calm window; that is the intended contrast.
    Both items are appended to PassificationGene.OFFERINGS (never reordered).
D15 Drops REPLACE leather: skeleton drops bones, zombie drops rotten flesh
    (two new MagicItemDropGene alleles, same shape as Dia/Egg/Swd).
D16 Both undead breeds pin aggression Anp (riders, after dark).
D17 Skeleton diet allele: eats BONES and heals from them, the way a metal-eater
    eats one metal. It reuses the DietGene feeding path exactly; no passive-
    regen timer and no hunger-system change. It shares the item with D13's
    passification offering, which is deliberate: the horse is hostile until you
    give it the thing it is made of, and bones then also keep it alive.
D18 Undead breeds do NOT spawn in the wild in the first release: "spawn" is
    ["spawn_egg"] only; vanilla trap, /summon and old saves feed the converter.
    No biome, herd or spawn_in_dark work for them.
D19 undead.suppressVanillaSpawns is a later stage; the converter catches new
    vanilla undead horses a tick after they spawn.
D20 Body: average height for both. Zombie sturdier: high health band, slow
    speed band (double hearts, speed penalty). Skeleton light, fast, low
    health. Plain numbers in the two breed sheets, no new stat code.

D21 Undead horses breed normally, no special rule. Undead x undead gives undead
    foals; undead x normal gives carriers that look ordinary. Nothing to code.
D22 Both breeds are kind "magical", like nightmare and netherhorse, whose
    passification precedent is being copied. Check what "magical" turns on
    (MagicalVariant, herd rolls, price and stable rules) before assuming it is
    free of side effects.
D23 Unsellable: no price (or zero) on either breed. Verify a breed with no
    price is accepted by BreedFilesTest and skipped by cowboy stock, barn and
    stable code rather than crashing.
D24 First release includes: debug-yard rows (one per undead breed plus a
    converted-vanilla case), breed-book lore entries for both, and gene wiki
    pages for both undeath genes with a Science tab (check-gene-tabs.mjs
    requires one for a natural gene page). Skipped for now: nothing else.

Still open, and not answered here: how the coat pipeline paints a skeleton (the
absence of a coat) - see stage 1.


5a. Reuse map: what already exists for each undead trait
========================================================
Read from the source. This is what turns "new system" into "two breed files
plus a few alleles". Each row names the thing to copy.
  Trait                     Existing machinery                      New work
  ------------------------  --------------------------------------  ---------
  Aggressive on sight       AggressionGene grid (when x who)        pick alleles
  Passified with an item,   PassificationGene: Prm = permanent, FTm   add the two
   then tamed as normal     = temporary; the offering is an INDEX     offerings
                            into a closed OFFERINGS list, appended
                            to freely (adding to the END is free,
                            reordering rewrites every horse)
  Breed pinned to a route   nightmare.json pins Prm/Prm and bands     copy it
                            the offering index; its note records
                            the veto fix the flee path needed
  Zombie eats raw meat      DietGene raw-meat allele                  none
  Skeleton eats bones,      DietGene narrow diets (one metal, one     one new
   heals from them           gem: full health per item)                allele
  Double hearts, slow       breed "stats" block and stat targets      numbers
  Bone / flesh drops        MagicItemDropGene (Dia, Egg, Swd, n)      two alleles
  Vanilla undead sounds     the sound effect (meowing gene)           sound ids
  Counts as undead          MobGroups "undead" group                  one clause
Passification, settled (D13, D14):
  - Skeleton: Prm/Prm (permanent), offering minecraft:bone.
  - Zombie: FTm (temporary), offering minecraft:rotten_flesh.
  - Offering amount, duration and cooldown are epigenetic and banded per breed,
    as nightmare.json does.
  - Any aggression allele must be checked against PassificationGene's veto: it
    vetoes TARGETING, not harmful auras, and it must also stop FLEEING (the
    nightmare note records that fix). A passified undead horse is still an
    undead horse to cleansing light.
Two things in this table are UNVERIFIED and one may not fit:
  - MagicItemDropGene's alleles are "instead of leather" (diamonds, an egg, a
    sword). Whether a drop that ADDS bones and flesh alongside leather, or that
    replaces it, is what is wanted is not decided; and its runtime-registry
    todo in To do.txt touches the same gene, so coordinate.
  - The sound effect's vocabulary was not read; confirm it can name a vanilla
    entity sound event (zombie_horse / skeleton_horse ambient, hurt, death) and
    that it fires per-horse rather than per-gene.

6. The conversion algorithm (neoforge module)
=============================================
New class, working name server/UndeadHorseConverter, subscribing to
EntityTickEvent.Post exactly as HorseFoundingTickHandler does. Steps, in order.
The order is the point: build and place the replacement BEFORE anything is
taken from the original.

6.1  Filter (cheap, first)
     - Only entities whose EntityType is EXACTLY minecraft:skeleton_horse or
       minecraft:zombie_horse (compare the type, not instanceof), server side
       only. This is looked up in a small registry keyed by EntityType (an
       "undead adapter": type -> which undead gene, which breed pool). The two
       vanilla types are its only entries today; a patch for another mod's
       undead horse is a third entry, which is the extension point D7 asks for.
       Do not convert subclasses.
     - Config gate on (section 7). Off means return immediately and leave the
       vanilla entity completely alone.
     - Skip if the entity carries the marker tag "horsegenetics:converting"
       (guards a re-entrant tick while the replacement exists).
     - Skip if HANDLED contains its network id (same discipline as founding).
     - Skip and retry later if any of the DEFER conditions in 6.2 hold.
     - Skip if it is dead or dying (health <= 0, deathTime > 0): a corpse must
       not be resurrected as a fresh horse.
     - Skip if the entity is in a dimension the mod says is off limits
       (horse dimension rules in HorseRealmRules; decide if realm/debug pens
       convert - decided yes, D8).

6.2  Defer conditions (retry next tick, never convert now)
     - Budget: reuse mayFound()/charge() so a chunk full of undead horses does
       not spend more than the founding budget in one tick. The founding budget
       is per tick across dimensions; share it, do not add a second one.
     - A PLAYER is a passenger. Converting under a rider dismounts or
       teleports the player and desyncs the client. Wait until the rider gets
       off. (A server with someone permanently riding a zombie horse converts
       it on their next login/chunk reload - acceptable, and stated in the
       docs.)
     - An unsprung skeleton trap (section 8.1).
     - The entity is not fully loaded (removed flag, no level, position in an
       unloaded chunk): do nothing, try again.

6.3  Snapshot what must be carried (read only, from the old entity)
     uuid, position/rotation/motion, isBaby and age, health and max health,
     custom name and visibility, isTamed, owner UUID, temper, saddle item,
     body armour item (both via the equipment slots), any other equipment,
     leash holder (UNVERIFIED how leash is stored and re-attached in 26.1.2),
     passengers, persistence flag / despawn state, team, entity tags
     (scoreboard tags), Fire ticks, glowing/invulnerable flags, and the
     persistent data compound (NeoForge getPersistentData - other mods'
     markers live there).
     UNVERIFIED: whether Mob.convertTo(EntityType, ConversionParams, ...)
     exists in 26.1.2 and what it already copies (equipment, leash, team,
     passengers). It is how vanilla turns a zombie into a drowned, and using it
     would be less code than hand-copying. Read the decompiled source first; if
     it discards the original itself, or skips tame/owner (likely, they are
     AbstractHorse state), hand-copy those on top of it.

6.4  Build the replacement
     - EntityType.HORSE.create(level, EntitySpawnReason.CONVERSION). (LOAD is
       what Lycanthropy and stasis use; CONVERSION is the honest reason here.
       UNVERIFIED whether any 26.1.2 code path treats the two differently.)
     - Give it the SAME UUID as the original. The ancestry database, stall
       signs, the browser roster, HorseWhereabouts and any pedigree all key on
       the horse UUID, and the original is about to be discarded so there is
       no duplicate. The alreadyLoose() check in HorseStasisHandler exists
       because two live entities on one UUID is a real failure - so this must be
       done as: add new, THEN discard old, in one tick, and abort (leave the
       old one alone) if addFreshEntity returns false. UNVERIFIED that
       ServerLevel accepts a new entity with a UUID still held by an entity
       that has not been removed yet; the alternative is discard-first with the
       snapshot in hand. Prove which works in a gametest before choosing.
     - Copy from the snapshot: position, baby/age, name, tame + owner (through
       HorseRecords.setOwner so the record's ownerId mirrors it), saddle and
       armour, leash, persistence, tags, team, persistent data (minus this
       mod's own keys), fire/invulnerable flags.
     - Set the seed for everything random from the UUID
       (SeededRng(uuid.mostSig ^ uuid.leastSig, "undead-conversion") - the
       pattern HerdManager already uses for magical herds). A conversion that is
       replayed after a crash, or run on two servers from one save, then gives
       the same horse.

6.5  Found it
     - Sex: coin flip from the seeded rng (matches assignFounder's non-natural
       branch). A tamed horse keeps whatever sex it rolls; there is no sex on
       the vanilla entity to preserve.
     - Breed: pick from the undead adapter's pool for this type (skeleton pool:
       the Great Valley Skeleton Horse; zombie pool: the Graveborn Warmblood),
       seeded from the UUID so the choice is stable. With one member the pool is
       trivial, but build it as a list from the start (a field on the breed
       sheet naming the undead type it belongs to, or a small pool file - decide
       against wiki/breed-format.html; a breed is JSON, not Java).
     - Genome: BreedFounder.roll(breed, rng, sex) - the breed itself pins the
       undead pair and the diet, temper and stat loci, so no forced list is
       needed. Check the pinned pair can never roll a lethal outcome for a
       CONVERSION founder (a horse must not convert straight into a dead foal).
       The sex-linkage rules (EditorRules.enforceSexLinkage) still apply.
     - Lineage token: BreedLineage.pure(breed.id()).toToken().
     - Name: if the vanilla entity has a custom name, KEEP it - use it as the
       record's first name and roll only a surname (or none); check how
       NameParts and displayName handle a one-part name. If it has no custom
       name, HorseRecords.newNameParts(rng). The record's displayName is what
       shows on the nameplate, so the entity name and the record name must
       agree (HorseNotices, ClientHorseRecordCache).
     - HorseRecord.founder(...), HorseRecords.apply(...),
       HorseRecords.applyTraitsToEntity(horse, record, true).
       Careful: applyTraitsToEntity writes Attributes.SCALE - see 3.2; it is
       safe here only because the whole conversion is running from the entity
       tick.
     - Health: preserve the FRACTION, not the points
       (healthLeft * newMaxHealth, floor at 1), exactly as Lycanthropy does.
       A near-dead zombie horse must not come out full health, and a doubled
       max health must not leave it at half.
     - Care: HORSE_CARE attachment starts at bond ZERO (D8), owner and tame state
       kept. Hunger: start FULL, as the stasis release does.

6.6  Place and swap
     - Clear the box: reuse the clearOfBlocks logic (extract it from
       LycanthropyHandler into a shared helper rather than copy it; it is
       currently private to that class).
     - Move passengers: for every passenger, dismount from the old entity and
       startRiding(new, true) (UNVERIFIED signature/force flag in 26.1.2).
       Player passengers were already deferred in 6.2, so this is only
       non-player riders - the four skeletons of a sprung trap, a baby zombie
       jockey, a villager on a lead.
     - addFreshEntity(new). If it returns false: abort, leave the original
       untouched, log once, and retry next tick up to a small cap so a blocked
       spot cannot loop forever.
     - Only after it succeeds: discard the original (discard(), not kill(), so
       no death event, no drops, no LivingDeathEvent, and HorseAfterlifeHandler
       and HorseDeathNoticeHandler never think a horse died - both listen for
       Horse only, which is right, but the vanilla ZombieHorse's own drops and
       any other mod's death listeners must not fire either).
     - Tell the ancestry database and roster the new founder
       (HorseAncestryData.record - the existing ensureExistingRecordResolved
       path already does this on the next tick, which is fine).
     - Sync coat and record to trackers (CoatSyncPayload, the record payload,
       HorseCareSyncPayload - onStartTracking in HorseGeneticsEventHandler
       already re-sends these when a player begins tracking the entity, so a
       player in range at conversion time needs the explicit send and a
       player who arrives later gets it for free).
     - Mark HANDLED.

6.7  Failure policy
     Any exception, any null from create(), any refusal from addFreshEntity:
     the original stays exactly as it was, one WARN line names the entity, its
     position and the reason, and the horse is retried a limited number of times
     and then left as a vanilla undead horse for the rest of the session.
     The failure mode of this feature must be "the horse is still there and
     still vanilla", never "the horse is gone".


7. Config
=========
ServerConfig gets a small group under an undead section. Server-authoritative;
clients never decide.
  - undead.convert : boolean, default TRUE (D2). Whether existing and newly
    arriving vanilla undead horses are converted. Off means the converter
    returns immediately and leaves vanilla entities completely alone.
  - undead.suppressVanillaSpawns : boolean - the spawning half, section 9.
There is deliberately NO "convert modded" switch: other mods' undead horses are
never converted (D7). The adapter registry in 6.1 is the extension point for a
future per-mod patch, which would carry its own gate.
Keep "convert what exists" and "stop new ones appearing" separate: they are
different promises and a server may want one without the other.
Removing the mod, or setting undead.convert=false, leaves any converted horse
as a plain minecraft:horse with orphaned attachment data. That is the same
outcome every other horse of this mod has when the mod is removed.


8. Edge cases (each one is a test case, section 11)
===================================================
8.1  Skeleton traps. A trap horse is a SkeletonHorse with its trap flag set; when
     a player comes near, vanilla springs the trap (lightning, four skeletons,
     one riding the horse) and the flag clears. UNVERIFIED in 26.1.2: the
     field/tag names (SkeletonTrap, SkeletonTrapTime) and which class spawns the
     trap horse. Converting an unsprung trap horse would silently disarm the
     trap, and converting a sprung one mid-lightning would eject its skeleton
     rider. Recommend: a trap horse is left alone until the trap has sprung and
     the skeletons have been dealt with (isTrap() false), then converts like any
     other. The trap remains a vanilla mechanic and only the horse it leaves
     behind becomes this mod's. Owner to confirm (open decision D5).
8.2  Ridden by a player: deferred (6.2). Tamed and saddled with nobody on it:
     converts normally and keeps saddle and owner.
8.3  Leashed to a fence or a player: the lead must survive (6.3). If it cannot
     be re-attached reliably, drop the lead item at the horse's feet rather than
     lose it, and log it. A destroyed lead is a small loss; a horse that stays
     tied to nothing is a bug.
8.4  "Undead" identity (D6). Undead is a homozygous-recessive trait. Only a horse
     expressing an undead gene counts as undead for cleansing light, holy ward
     and similar effects; a carrier looks like an ordinary horse and is
     unaffected. MobGroups (which resolves "undead" through the entity-type tag)
     gets one clause: a Horse whose genotype is homozygous for an undead allele
     matches. Keep it in that one place.
     Vanilla also gives the two types tag-driven behaviour that a Horse cannot
     inherit: healing and harming potions inverted, sunlight and drowning
     rules, aggro from other mobs (skeletons ignoring skeleton horses),
     breathing and swimming. Each is UNVERIFIED as to which tags the vanilla
     types actually carry in 26.1.2 - read data/minecraft/tags/entity_type/ in
     the vanilla jar. Each one becomes an effect on the breed's bundle (the
     effects block, wiki/horse-traits.html) or is explicitly declared not to
     carry over. Inverted potions need a mixin or event and are a separate,
     later call; do not promise them.
8.5  Foals. Baby skeleton and zombie horses exist. Copy isBaby and the age in
     ticks; do not re-roll age. A converted foal is founded with no parents.
8.6  Tamed horses that were bred by the player. Vanilla undead horses cannot
     breed with each other, so there are no player-bred lineages to protect.
     A modded horse that can is never converted (D7).
8.7  Unloaded chunks and other dimensions. Nothing runs against a chunk nobody
     has loaded. Conversion is lazy - a horse converts on its first tick after
     its chunk loads - which is the same "acquires a genome the first time it is
     ticked, whenever that is" guarantee the attachment approach already makes.
     There is deliberately NO world scan and NO migration command that walks
     region files.
8.8  Spawn eggs and other item-carried entities. A vanilla zombie or skeleton
     horse spawn egg, or an item with saved entity data, spawns an undead entity
     and reaches the tick converter like anything else. Whether to also cancel
     it at spawn (section 9) is separate; the tick converter is the one
     chokepoint that catches every route, and it is what makes an old save safe.
8.9  Duplicate UUID / replayed conversion. If the game crashes between addFresh
     and discard, the next load has two entities on one UUID. Vanilla resolves
     duplicate UUIDs on chunk load by dropping one; UNVERIFIED which. The replay
     rule (seeded rng, section 6.4) means both are identical apart from type, so
     whichever survives is fine; but a gametest must prove it.
8.10 Realm and debug pens (D8): undead horses convert there too. Check that the
     realm's release and ownership rules (HorseRealm.isInRealm,
     DebugPenManager) do not treat a converted horse as a fresh, unowned import,
     and that a debug pen holding a deliberately vanilla test entity has a way
     to keep it (a persistent-data marker the converter skips).
8.11 Multiplayer. Conversion runs server side, and the client sees a remove-entity
     and an add-entity packet, not a mutation. A player standing next to it will
     see the old horse vanish and the new one appear in the same tick. Sync the
     coat and record BEFORE the client can render the new entity a white horse;
     sendToPlayersTrackingEntity right after addFreshEntity, and verify there is
     no visible white flash (GeneticCoatTextureFactory may need the coat before
     first render; check ClientCoatCache).
8.12 Other mods that key on the entity. A mod that holds a reference to the old
     zombie horse (a waypoint, a mount-tracking list, a claim) loses it. Not
     fixable from here; the README/compat page states that enabling
     undead.convert replaces the entities, and undead.convert=false is the
     escape hatch.

#!/usr/bin/env python3
"""
Do vanilla's zombie horse and skeleton horse share the ordinary horse mesh?

Read-only. Standard library only (Python 3.8+). Optional: `javap` from the JDK
(the project already needs JDK 25) for the model-layer half.

    python check_undead_meshes.py                 # finds the Minecraft jar itself
    python check_undead_meshes.py path/to/minecraft-client.jar

Part 1 finds the jar. Part 2 lists the horse-family textures. Part 3 decodes the
white, zombie and skeleton PNGs and compares their alpha masks (same UV layout?
how many holes?). Part 4 runs javap over the model-layer registry and the horse
renderers so you can see which model definition feeds which entity.
Paste the whole output back.
"""
import os, re, struct, subprocess, sys, zipfile, zlib, shutil
from pathlib import Path

TEX = re.compile(r"assets/minecraft/textures/entity/.*(horse|equine)", re.I)
WHITE = re.compile(r"textures/entity/[^/]*/?(horse_white|white)\.png$", re.I)


# ---------------------------------------------------------------- part 1: jar
def has_horse_textures(path):
    try:
        with zipfile.ZipFile(path) as z:
            return any(TEX.search(n) for n in z.namelist())
    except (zipfile.BadZipFile, OSError):
        return False


def find_jar():
    roots = [Path.cwd() / "neoforge-26.1.2" / "build", Path.cwd() / ".gradle",
             Path.home() / ".gradle", Path.home() / ".m2"]
    seen = 0
    for root in roots:
        if not root.exists():
            continue
        for dirpath, _dirs, files in os.walk(root):
            for f in files:
                if not f.endswith(".jar") or "sources" in f:
                    continue
                p = Path(dirpath) / f
                try:
                    if p.stat().st_size < 1_000_000:
                        continue
                except OSError:
                    continue
                seen += 1
                if has_horse_textures(p):
                    return p
    print(f"  (looked at {seen} jars of 1 MB or more, none had horse textures)")
    return None


# ---------------------------------------------------------------- PNG decode
def decode_alpha(data):
    """Return (w, h, alpha list of w*h ints 0..255). Non-interlaced PNG only."""
    assert data[:8] == b"\x89PNG\r\n\x1a\n", "not a PNG"
    pos, idat, plte, trns = 8, b"", None, None
    while pos < len(data):
        n, typ = struct.unpack(">I4s", data[pos:pos + 8])
        body = data[pos + 8:pos + 8 + n]
        pos += 12 + n
        if typ == b"IHDR":
            w, h, depth, ctype, _c, _f, inter = struct.unpack(">IIBBBBB", body)
        elif typ == b"PLTE":
            plte = body
        elif typ == b"tRNS":
            trns = body
        elif typ == b"IDAT":
            idat += body
    if inter:
        raise ValueError("interlaced PNG not supported")
    chans = {0: 1, 2: 3, 3: 1, 4: 2, 6: 4}[ctype]
    bits = chans * depth
    stride = (w * bits + 7) // 8
    bpp = max(1, bits // 8)
    raw = zlib.decompress(idat)
    rows, prev = [], bytearray(stride)
    for y in range(h):
        ft = raw[y * (stride + 1)]
        line = bytearray(raw[y * (stride + 1) + 1:(y + 1) * (stride + 1)])
        for i in range(stride):
            a = line[i - bpp] if i >= bpp else 0
            b = prev[i]
            c = prev[i - bpp] if i >= bpp else 0
            if ft == 1:
                line[i] = (line[i] + a) & 255
            elif ft == 2:
                line[i] = (line[i] + b) & 255
            elif ft == 3:
                line[i] = (line[i] + (a + b) // 2) & 255
            elif ft == 4:
                p = a + b - c
                pa, pb, pc = abs(p - a), abs(p - b), abs(p - c)
                pr = a if (pa <= pb and pa <= pc) else (b if pb <= pc else c)
                line[i] = (line[i] + pr) & 255
        rows.append(line)
        prev = line
    alpha = []
    for line in rows:
        if ctype == 6 and depth == 8:
            alpha += line[3::4]
        elif ctype == 4 and depth == 8:
            alpha += line[1::2]
        elif ctype == 3:
            for x in range(w):
                if depth == 8:
                    idx = line[x]
                else:
                    per = 8 // depth
                    idx = (line[x // per] >> (8 - depth * (x % per + 1))) & ((1 << depth) - 1)
                alpha.append(trns[idx] if trns and idx < len(trns) else 255)
        elif ctype in (0, 2) and depth == 8:
            alpha += [255] * w
        else:
            raise ValueError(f"unsupported PNG (colour type {ctype}, depth {depth})")
    return w, h, alpha


def summary(alpha):
    n = len(alpha)
    t = sum(1 for a in alpha if a == 0)
    o = sum(1 for a in alpha if a == 255)
    return n, t, n - t - o, o


# ---------------------------------------------------------------- javap half
def javap(jar, cls):
    exe = shutil.which("javap")
    if not exe and os.environ.get("JAVA_HOME"):
        cand = Path(os.environ["JAVA_HOME"]) / "bin" / "javap"
        exe = str(cand) if cand.exists() or Path(str(cand) + ".exe").exists() else None
    if not exe:
        return None
    r = subprocess.run([exe, "-c", "-p", "-constants", "-classpath", str(jar), cls],
                       capture_output=True, text=True)
    return r.stdout if r.returncode == 0 else None


def main():
    jar = Path(sys.argv[1]) if len(sys.argv) > 1 else None
    print("== 1. Minecraft jar ==")
    if jar is None:
        jar = find_jar()
    if jar is None or not jar.exists():
        print("  Not found. Run once:  ./gradlew :neoforge-26.1.2:build  (or runClient)\n"
              "  then re-run, or pass the jar path yourself. Look for the jar that contains\n"
              "  assets/minecraft/textures/entity/horse/.")
        return 1
    print(" ", jar)
    z = zipfile.ZipFile(jar)
    names = z.namelist()

    print("\n== 2. horse-family textures in the jar ==")
    tex = sorted(n for n in names if n.endswith(".png") and TEX.search(n))
    for n in tex:
        print("  ", n[len("assets/minecraft/"):])

    print("\n== 3. alpha masks ==")
    def pick(pattern):
        m = [n for n in tex if re.search(pattern, n, re.I)]
        return m[0] if m else None
    picks = {"white": pick(r"horse_white\.png$|/white\.png$"),
             "zombie": pick(r"zombie[^/]*\.png$"),
             "skeleton": pick(r"skeleton[^/]*\.png$")}
    masks = {}
    for k, n in picks.items():
        if not n:
            print(f"  {k}: no texture matched")
            continue
        try:
            w, h, a = decode_alpha(z.read(n))
        except Exception as e:
            print(f"  {k}: could not decode {n}: {e}")
            continue
        masks[k] = (w, h, a)
        total, clear, part, solid = summary(a)
        print(f"  {k:8} {w}x{h}  transparent {clear} ({100*clear/total:.1f}%)  "
              f"partial {part}  opaque {solid} ({100*solid/total:.1f}%)   {n.split('/')[-1]}")
    if "white" in masks:
        w0, h0, aw = masks["white"]
        island = [x > 0 for x in aw]
        for k in ("zombie", "skeleton"):
            if k not in masks:
                continue
            w, h, a = masks[k]
            if (w, h) != (w0, h0):
                print(f"  {k}: size differs from the white horse ({w}x{h} vs {w0}x{h0}); "
                      "UV layouts are not directly comparable")
                continue
            drawn = [x > 0 for x in a]
            inside = sum(1 for d, i in zip(drawn, island) if d and i)
            outside = sum(1 for d, i in zip(drawn, island) if d and not i)
            holes = sum(1 for d, i in zip(drawn, island) if i and not d)
            isl = sum(island)
            print(f"  {k} vs white: drawn pixels inside the horse's UV islands {inside}, "
                  f"outside {outside}; holes cut inside the islands {holes} of {isl} "
                  f"({100*holes/max(1,isl):.1f}%)")
        print("  Reading it: 'outside' near 0 means the same UV layout as the horse (so the\n"
              "  same mesh, or at least the same skin map). A large 'holes' figure on the\n"
              "  skeleton is the 'more transparent pixels' hunch.")

    print("\n== 4. which model definition feeds which entity (javap) ==")
    if shutil.which("javap") is None and not os.environ.get("JAVA_HOME"):
        print("  javap not on PATH and JAVA_HOME unset; skipping. Put the JDK bin on PATH.")
        return 0
    classes = [n[:-6].replace("/", ".") for n in names if n.endswith(".class")]
    layer = [c for c in classes if c.endswith("LayerDefinitions")]
    for c in layer[:1]:
        out = javap(jar, c)
        if out is None:
            print("  javap failed on", c)
            continue
        lines = out.splitlines()
        print(" ", c)
        want = re.compile(r"ModelLayers\.(HORSE|ZOMBIE_HORSE|SKELETON_HORSE|DONKEY|MULE)\b")
        for i, ln in enumerate(lines):
            m = want.search(ln)
            if m:
                print(f"   --- {m.group(1)} ---")
                for j in range(max(0, i - 4), min(len(lines), i + 4)):
                    print("     ", lines[j].strip())

              "  and SKELETON_HORSE. Same source = same mesh.")
    rend = [c for c in classes if re.search(r"(?i)horse", c) and re.search(r"(?i)renderer", c)]
    print("\n  horse renderers:", ", ".join(c.split(".")[-1] for c in rend) or "none found")
    key = re.compile(r"ModelLayers|RenderType|entityCutout|entityTranslucent|textures/entity|"
                     r"createBodyLayer|HorseModel|Model;")
    for c in rend:
        out = javap(jar, c)
        if not out:
            continue
        print("  ---", c.split(".")[-1], "---")
        seen = set()
        for ln in out.splitlines():
            if key.search(ln) and "invoke" in ln or "textures/entity" in ln or "ModelLayers" in ln:
                s = ln.strip()
                if s not in seen:
                    seen.add(s)
                    print("     ", s[:170])
    print("\nDone. Paste everything above back into the chat.")
    return 0

    sys.exit(main())
