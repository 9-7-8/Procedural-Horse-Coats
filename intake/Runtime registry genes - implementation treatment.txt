Runtime registry genes - implementation treatment

Scoped with the owner. Every "Decided" line below is her call; "Open" lines are
still to be settled; "UNVERIFIED" lines are facts this file has not proved and
the building session must check first. Source of truth for what exists is the
five gene pages (wiki/gene-lycan.html, gene-pack-leader.html, gene-spawner.html,
gene-egg-layer.html, gene-magic-item-drop.html). This file is the handoff for
the two "To do.txt" lines it replaces (the LYCAN roster line and the
item-producing genes line). It is retired (deleted, per START HERE step 3) as
each piece ships and moves onto those pages' Gameplay and Coding tabs. Delete
the two To do.txt bullets when a Roadmap tab holds the plan (magical-genes.html
already has one - extend it), not before.

The idea, in one paragraph
===========================
Hand-writing a list of every mob and item every mod adds is impossible, and
generating one allele per registry entry is a trap (see "Why not one allele per
thing" below). So: keep every existing hand-written allele exactly as it is, and
add ONE new allele to each locus, called CHAOS, that stands in for "everything
we have no allele for". It copies the pattern the eye colour locus already
uses (EyeColourGene, EyeHue.CHAOS): the value lives on the allele COPY, in the
epigenome, not on the allele, so no two chaos horses match and a line of them
can be bred toward something. Here the value is a SEED that picks one entry
from a list built from the live registry when the server starts.

What already exists, so the building session does not redo it
==============================================================
- common/.../genes/MobRoster.java: the hand-written roster. Entry(token, mob,
  label, Habitat). ground() is LycanGene's allele set, peaceful() is
  PackLeaderGene's, all() (peaceful + hostile) is SpawnerGene's. Its own note:
  never reorder tokens, append only - a token is in every saved genotype code.
- Lycan is guarded twice: the constructor only takes GROUND entries, and
  server/LycanthropyHandler.isWearable re-checks the real animal (swims, flies,
  hostile) at shift time. That second check was written to still hold "when the
  roster is derived from the live registry" - so the runtime gate for mobs
  already exists and needs reusing, not rewriting.
- An id the build has never heard of already does nothing (Lycan logs once and
  does not shift). So a chaos seed that lands on nothing has a safe outcome.
- Genotype.readableStored drops a whole gene segment (BOTH copies) when it
  names an allele the build no longer has. That is the cost of a removed mod
  under a per-thing allele, and the reason chaos avoids it: chaos is one
  permanent allele, so nothing is ever "no longer there".
- EggLayerGene: nine alleles, one item each (AbstractMatchedPairGene.Variant0
  token, item id, label), abilitiesFor builds GeneAbility.Produce(item id, ...).
  The Produce verb already accepts any item id.
- MagicItemDropGene: three fixed alleles (Dia, Egg, Swd) plus n, with drop
  names ("diamonds", "spawn_egg", "enchanted_sword") switched on in
  server/GeneDeathHandler.itemFor. It is NOT one-allele-per-item, so unlike the
  egg layer it needs a new drop kind, not just a new list entry.
- The epigenome has value kinds SEED (a long; drift never nudges it, at most a
  rare whole re-roll) and CATEGORY (an index into a list the gene owns). SEED is
  the fit; the eye locus and Lycan's own "cloud" colour show the pattern.

Why not one allele per thing (recorded so it is not reopened)
==============================================================
Rejected after reading the code, not just preferred against:
- A token is text inside the genotype code, split on the two separator
  characters the Allele javadoc documents. Registry ids contain characters that
  collide with them, so per-thing tokens would need an escaping scheme.
- Allele order is the list index and must never change. A live-registry list
  changes with the modpack, so two servers would disagree on what a code means,
  and a horse moved between packs would change species.
- The gene set is fixed when the game starts, and the designer, the gene
  bundle, the census and the wiki are baked from common/ where no registry
  exists. A per-thing allele set would exist in-game and nowhere else.
Chaos answers all three: one fixed allele, a number on the copy.

Shared machinery (build first, used by all three pieces)
==========================================================
A NeoForge-side "chaos roster", in server/ (not common/ - hard rule 1):
- Built once, when the server has its registries, from EntityType and Item.
  Sorted by resource id so the same pack always gives the same list, and
  cached; resolved to an entry as seed modulo list size.
- A seed picks an entry by position, so ADDING or REMOVING a mod moves what an
  existing seed means. Decided: acceptable, it is chaos. Say so on the Gameplay
  tabs so nobody expects a chaos line to survive a modpack change unchanged.
- One config block, behaviour-style, server side: an exclude list of mod ids
  and an exclude list of individual ids, applied to both mobs and items.
  UNVERIFIED how ServerConfig lists are declared elsewhere (read
  ServerConfig.java for an existing string-list option first and copy it).

Piece A - the three mob loci (Lycan, Pack leader, Spawner)
==========================================================
Decided: all three loci read the live registry, through chaos.
Decided: chaos covers ONLY modded mobs. Vanilla mobs keep their hand-written
alleles exactly as today, so nothing about a vanilla horse changes. The roster's
chaos list is every mob whose namespace is not minecraft.
Decided: wild share is "same as vanilla" - the chaos allele is weighted like a
single vanilla allele in the founder table, not like one allele per modded mob.
(This reads the owner's "same as vanilla" answer together with her later "chaos
allele instead": modded mobs must not multiply the odds by how many there are.)
- Lycan: append Chaos AFTER the current last allele so every existing order
  index stays valid. Decided: two Chaos copies shift only if they carry the SAME
  seed (matched-pair rule kept); different seeds are the existing "mismatched"
  outcome, a horse. The shift resolves the seed against the modded, GROUND-safe
  list only; isWearable stays as the hard second gate and is the reason a hostile
  or flying modded mob can never be worn. If no modded mob passes, Chaos does
  nothing, like an unknown id.
- Pack leader: same allele, seed picks a modded mob that follows the horse. Its
  habitat rule is the looser one it has today (peaceful only). Which modded mobs
  count as peaceful is the one design piece here - see UNVERIFIED below.
- Spawner: same allele; it deliberately reaches hostile mobs today, so chaos
  here may name any modded mob. Decided by extension, not asked: keep it
  looser than the other two, as it is now. Confirm with the owner if a modded
  boss-class mob is a concern; a blocklist entry is the answer.
- Open: founder weight when NO modded mob is installed. Recommendation: still
  present in the table (so codes and the designer are identical everywhere) but
  its outcome text says "no modded animal available". Alternative is dropping
  it from the wild table when the list is empty, which needs the pack's state to
  reach FounderContext (UNVERIFIED that it can carry it).

Piece B - egg layer chaos
=========================
Decided: EggLayerGene gets a Chaos allele. The nine hand-picked alleles stay.
Decided: Chaos covers every item that is not one of the nine, vanilla and
modded alike, under the item policy below ("fills in everything we do not have
a set allele for").
- The Produce verb takes an item id string. Recommended: pass a sentinel such as
  "chaos:<seed>" in the existing item field and resolve it in the game module,
  rather than adding a field to GeneAbility.Produce. A new record field would
  touch SpecSchema and the spec fixtures (bakeSpecFixtures, then
  check-parity.mjs) for no player-visible gain. Open only in that the owner has
  not been asked; it is an internal choice.
- interval stays the one epigenetic value; the seed is a second, SEED kind.
- Accumulation: the nearby_cap guard already exists on the verb. Decided by
  extension, not asked: it counts item entities of any kind, so a chaos layer
  does not lay a second item on top of an uncollected pile.

Piece C - magic item drop chaos
===============================
Decided: MagicItemDropGene gets a Chaos allele, "functions similarly to the eye
allele", filling in everything without a set allele.
Decided: the seed is a SEED on the allele copy, inherited exactly, with only the
rare whole re-roll drift gives a seed (so a line breeds true).
Decided: Chaos is recessive like every other variant here: it takes two Chaos
copies. Decided by extension, not asked: two copies with DIFFERENT seeds follow
the locus's existing rule for two different variants (they settle on nothing and
drop the ordinary leather). Same-seed pair drops the item the seed picks.
- New drop name for GeneDeathHandler.itemFor: "chaos" with the seed carried in
  the string ("chaos:<seed>"), same reasoning as piece B, and one more case in a
  switch that already has four. The picked item drops as a normal stack of 1;
  count is the ability's min/max, so start with 1-1 and let the owner tune.
- Open: should a chaos drop REPLACE the leather (the way Dia does) or drop
  beside it? Recommendation: replace, so it stays a choice a breeder makes.
- Founder table: doubled forms only, as the rest of this locus (rewards, not
  hazards). Chaos joins with a small weight of its own; number is the owner's.

Item eligibility (pieces B and C)
=================================
Decided: a default blocklist plus config.
Default blocklist, every item that is:
- creative-only or operator items (command blocks, structure/jigsaw blocks,
  barrier, light, debug stick, knowledge book and the like),
- a spawn egg,
- a container that can hold things (shulker boxes, bundles) - a horse laying a
  full shulker is a duplication route,
- another mod's item that carries a creative-only tab and no survival source
  (UNVERIFIED that the game exposes this; if it does not, exclude by mod-config
  only and say so).
Decided: the config adds an exclude-by-mod-id list and an exclude-by-item-id list
on top. Default is "allowed unless blocked", not opt-in.
- UNVERIFIED and important: whether the registry can tell an "obtainable in
  survival" item from a creative-only one. If not, the default list is only the
  hand-written vanilla set above and modded operator items are the pack
  author's job - state that plainly on the Gameplay tab and in the config
  comment.
- Open: should a chaos-laid or chaos-dropped item be allowed to be an item that
  is itself a gene carrier (this mod's carrots, splices, papers, spawn eggs)?
  Recommendation: exclude everything in this mod's own namespace. The horse is
  not a source of the mod's own progression items.

UNVERIFIED - the owner is to be asked about each before building
=================================================================
1. Whether the game lets the roster tell a peaceful modded mob from a hostile
   one. Vanilla's habitat tag here is hand-written. At runtime the only real
   signals are MobCategory (spawn category) and the instantiated animal's
   navigation, which isWearable already uses. Pack leader needs "peaceful" and
   nothing gives it for free.
2. Whether a chaos seed has a legible display anywhere. The info screens show
   allele labels; a chaos copy would read "Chaos" with no idea what it is. The
   choices are showing the resolved thing ("would shift into: <mob>") on the
   server-known horse, or a generic label.
3. Whether the horse designer and the in-game custom spawn screen can offer
   Chaos. The allele is in common/ so both will list it, but only the game can
   resolve a seed. Hard rule 5 wants a deliberate divergence written in the
   comment on BOTH files: the designer offers the allele and a seed field and
   says "resolved in game".
4. Whether FounderContext can carry "are modded mobs installed" (see piece A).
5. Whether ServerConfig already has a list-of-strings option to copy for the
   exclude lists.
6. Whether an item's "creative-only" nature is readable at run time (see the
   eligibility section).

Tests and checks
================
- common/: every gene gained an allele, so the gene tests for these five run
  first (--tests, never the whole suite). The coat goldens should NOT move, none
  of these five paints anything; if a row moves, something else changed.
- Lycan matched-pair: same seed shifts, different seed does not, chaos with
  n does not (add to LycanGeneTest).
- Roster: a gametest that builds the roster, checks it is sorted, excludes the
  default blocklist and this mod's own items, and is identical when built twice.
- Play checks (Verification tab, not unit-testable): a modded mob as a werewolf,
  a modded mob that flies or drowns is refused, a chaos layer in a pack with no
  eligible item, and a saved chaos horse after a mod is removed.
