How to report a bug - routine for a Claude cloud session

Who this is for
===============
A Claude Code session running in the cloud (claude.ai/code, the mobile app, or a
GitHub-triggered session) that the owner or a tester has told about a bug. The job is
to turn the report into ONE good GitHub issue on 9-7-8/Procedural-Horse-Coats, or a
comment on an existing one. This routine REPORTS bugs. It does not fix them. Fixing is
the /fix-bug routine (.claude/skills/fix-bug/SKILL.md), run later on the owner's machine,
where the game can be built, launched and tested.

This file lives in intake/ so a cloud session finds it, but it is a routine, not a
feature request. Bugs never go into intake/ as files: every bug is a GitHub issue
(CLAUDE.md hard rule 9).

What the cloud session can and cannot do
========================================
CAN:
- read the whole repository, which is a fresh clone of main;
- search and read the git history;
- read wiki/text/;
- search, read, create and comment on GitHub issues through the GitHub MCP tools
  (named mcp__github__...). If they are not in the tool list, load them with
  ToolSearch. There is no gh CLI in the cloud.
CANNOT:
- see the owner's machine: no latest.log, no crash-reports folder, no running game;
- build or launch the game in any way that proves a bug.
So any log, crash report or screenshot has to come from whoever reported the bug.
Ask for it (step 2).

Do NOT, in this routine:
- change code, the wiki or intake/;
- commit, push or open a pull request. The issue is the whole deliverable;
- touch the live server (26.1.2-neoforge-server belongs to another Claude);
- apply the found-in-yard label. That label is only for the yard test runs.


The routine
===========

1. Take the report as given
   Quote the reporter's own words. Note who reported it (the owner, or a named tester)
   and where it came from (playing, a server, a screenshot, a log they pasted).

2. Ask until the issue could be acted on without asking again
   Use the question tool (AskUserQuestion) for every gap. Give 2-4 concrete options
   with the likeliest first, so the reporter can pick rather than write. Ask in rounds,
   with follow-ups, until you have:
   - WHAT HAPPENED, and what they expected instead;
   - WHICH VERSION: the jar's version number (the mod list, or the jar's file name),
     and whether it was single-player, the owner's own world, or a server;
   - HOW TO REPEAT IT: the steps, and whether it happens every time, sometimes, or once;
   - WHAT ELSE IS INSTALLED, if it might matter: another mod, a modpack, shaders;
   - EVIDENCE: the exact error text, the crash report, the relevant lines of
     latest.log (it is in the instance's logs/ folder), or a screenshot. A crash
     needs its crash report; ask for it every time;
   - DAMAGE: was anything lost - a horse, an item, a world that no longer loads?
     That decides how urgent it is (step 6).
   If the reporter does not know an answer, write "unknown" in the issue rather than
   guessing.

3. Make sure it is a bug
   A bug is something built that behaves wrongly. If the report is really:
   - a NEW FEATURE ("it should also...", "it would be nice if...") -> it belongs in
     intake/ as a treatment, written by following "How to make an intake document.txt".
     Tell them that, and stop here.
   - a design disagreement ("this is too hard", "I don't like how...") -> it is still
     worth an issue, but with the needs-owner label (step 6).
   - working as intended -> say so, and quote the wiki page that says so (in
     wiki/text/), so they can see it is deliberate.

4. Check it is not already reported, or already fixed
   - Search the open AND closed issues for its keywords: the symptom, the item or gene
     name, the class name if there is one.
     - Found an open match -> add a comment to that issue with the new evidence, the
       version and the reporter. Do not open a duplicate.
     - Found a closed match -> read how it was closed. If the reporter's version came
       out after the fix, the fix did not work: open a new issue that links the old
       one and says so.
   - Search the history for a fix: git log --date=short -S 'someIdentifier' -- <file>,
     and grep wiki/session-log/ for the symptom.
     - If a fix landed, check whether the reporter's version has it:
       git tag --contains <commit>.
     - The fix is in their version -> it did not work; say so in the issue.
     - The fix landed after their version -> tell them which release carries it (or
       that the next release will), and do not open an issue unless they still see it
       on that version.

5. Find where it probably lives (read only, and keep it short)
   The issue is more useful with a suspect than without one, but this is not the fix.
   - Start at the symptom map: wiki/text/roadmap-execution.txt, the "Symptom-to-anchor
     map" section. Then go to the owning page from CLAUDE.md's map, in wiki/text/.
   - Name the suspected class and line (file:line on current main) only if you have
     actually read it. Otherwise say "suspected area: ...".
   - Never grep wiki/search-index.js.

6. Decide the labels
   - bug - always.
   - needs-owner - add it when fixing the bug needs the owner's decision: there is more
     than one reasonable fix, or it raises a design, balance or philosophy question. If
     you add it, end the issue with 2-4 fix options, your recommendation first. Without
     this label, the next yard run or /fix-bug run will pick the issue up.
   - Do not invent labels. Urgency goes in the issue body's first line instead:
       DAMAGE   - a crash, a lost horse or item, or a save that will not load
                  (CLAUDE.md hard rule 10);
       PLAYERS  - wrong behaviour on a released jar;
       COSMETIC - looks wrong, but nothing is lost or blocked.

7. Write the issue
   The repository is public and outside testers read it, so write plainly: no in-jokes,
   and no internal session chatter. Issue #13 is a good model.

   Title: the symptom, in a player's words, plus the thing it happens to.
     e.g. "Sold horse still appears in the H menu after a server restart"

   Body, in this order:
     **Urgency:** DAMAGE / PLAYERS / COSMETIC
     **What happens:** one or two sentences.
     **Expected:** one sentence.
     **Version:** 0.5.0xx, and single-player / own world / server. Write "unknown"
       if they did not know.
     **Steps to repeat:** a numbered list, and how often it happens.
     **Evidence:** the error text, crash-report excerpt or log lines, in a code block,
       exactly as given, with their date. Attach or link a screenshot if there is one.
     **Reported by:** the owner / tester name, and where they hit it.
     **Already known?** the related issues, and any fix commit with the release that
       carries it (from step 4). "None found" if there are none.
     **Suspected area:** class / file:line, and how sure you are.
     **Owning page:** the wiki page.
     **Fix options:** only when the issue has needs-owner. 2-4 options, recommendation
       first.
   End the body with the attribution footer, as the last lines:

     ---
     _Generated by [Claude Code](https://claude.ai/code)_

8. Report back
   Give the reporter:
   - the issue link (or the comment link, for a duplicate);
   - its urgency;
   - whether it will be picked up automatically (no needs-owner), or is waiting on the
     owner, and the question it is waiting on.
   If they reported several bugs at once, file them as separate issues, one bug each,
   and list all the links. Then stop. Do not start fixing.
