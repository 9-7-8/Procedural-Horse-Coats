1. THE REQUEST, AS GIVEN
------------------------
"bedrock on the latest version of bedrock" (owner, 2026-10-03). Read as: a Bedrock add-on
that does what the Java mod does, as far as Bedrock allows. Latest stable is 26.50
(2026-09-15); latest preview 26.60.29; 26.60 is due 2026-10-27 (minecraft.wiki snippets,
UNVERIFIED). It is a separate product, not a build target of this repo's loaders.

2. IN SCOPE, AND WHAT IS NOT
----------------------------
In: a spike that answers five questions; the genetics core running in Bedrock's script
engine; a coat system that Bedrock can render; horse data, naming, breeding hook; a short
list of items; forms for the screens.
Not in (re-askable): the hay-bale portal and generated stables (custom dimensions are
void-only: Open 4); carts; Jade-style compat; the web tools; Marketplace distribution (the
licence is CC BY-NC 4.0; Marketplace pays creators, Open 6).

3. WHAT ALREADY EXISTS
----------------------
- common/ is pure Java (hard rule 1) and the web/ module already compiles it with TeaVM to
  wasm-gc: web/DesignerApi has 65 @JSExport methods on a JSON-string and int[] boundary with
  no Minecraft types (hard rule 3: the browser runs the real genetics). So the logic can
  leave the JVM. TeaVM can also emit plain JavaScript (UNVERIFIED which options web/ uses;
  read web/build.gradle.kts).
- Hard rule 3 forbids HAND-WRITTEN JS ports of genes. A TeaVM-generated JS bundle is a
  compile of common/, not a port, and does not break it; a Bedrock bundle must be compiled,
  never hand-edited. Recorded as Decided by reading, not asked: Open 1 confirms it.
- The coat pipeline: common/coat/pattern/CoatTextureComposer (+ GradientLut, LutSet,
  TexelBudgetCache, HorseSkinGeometry) returns an int[] per horse; the client uploads it as a
  DynamicTexture (neoforge client/GeneticCoatTextureFactory). Bedrock has no equivalent.
- The editor-rule seam: common/EditorRules, web/HorseEditor (rule 5).
- Nothing in the repo targets Bedrock (the only "bedrock" hit in api-notes.txt is world-bottom).
- LOOKS built but is not: web/ proves the code runs under TeaVM, not under QuickJS. Bedrock's
  Script API is a customised QuickJS interpreter with no JIT; there is no confirmation of a
  WebAssembly global (believed absent). So wasm-gc is out; plain-JS output is untested there.

4. THE PIECES
-------------
Piece 1 - One-day spike (answers five questions; no shipped code)
  Player sees: nothing. Output: a note on architecture.html's Verification tab.
  Questions, riskiest first:
   1. Does TeaVM-compiled JS run in the Script API, and how fast? A long synchronous script
      is killed (hang 3000 ms, spike 100 ms, slow 2 ms, ~250 MB memory: UNVERIFIED, wiki
      snippets), so does Genotype.breedWith + naming fit under 2 ms?
   2. How many texture layers does entity_multitexture allow on a vanilla material
      (believed 2-4) and can a custom material add more?
   3. Is overlay_color per layer or per render controller (believed per controller)?
   4. Which platforms accept custom entity materials (believed restricted off Windows and out
      of Marketplace)?
   5. Is there a breed event, or must foals be found by entitySpawn plus nearby parents?
  Code: a throwaway add-on in a scratch dir, not in the repo.
  Tests/Play checks: the answers themselves; it must be run in a real Bedrock client and
    server (Bedrock Dedicated Server), neither of which this cloud environment has: this
    piece is local-only (hard rule 11: the owner is asked before downloading the client).
  Docs: architecture.html Verification tab.
Piece 2 - Genetics core as a generated JS bundle (common/ -> JS)
  Player sees: nothing yet.
  Recommended: a new Gradle module (:bedrock-js, beside :web) that exposes a thin
    JSON-string API of the same shape as DesignerApi, compiled by TeaVM to JS; the add-on's
    TypeScript calls it. Build :bedrock-js after adding any @JSExport (rule 3).
  Code: common/ unchanged; the new module; one test that runs the bundle's output through
    Node for a fixed genotype and compares it with the JVM (a parity golden).
  Data and saves: genotype and epigenome codes already travel as strings; Bedrock stores
    them as entity dynamic properties (per-entity size limits UNVERIFIED), and a world is a
    new world; no migration. A later change to allele order is still permanent (hard rule).
  Config: none. Sync: server-only.
  Tests: the JVM-vs-JS parity test (name: BedrockBundleParityTest, new); CommonPortabilityTest
    keeps guarding the JDK subset.
  Play checks: a horse spawned in Bedrock gets a genotype and a name.
Piece 3 - The coat, as a bounded layered coat (the premise question)
  Player sees: coloured, patterned horses that breed true.
  Open 2 (owner): does a bounded space (layers x variants x tints chosen by entity
    properties, at most 32 properties and enums of at most 16) count as the "functionally
    infinite coat space" philosophy requires? Philosophy and hard rule 4 say to never ship a
    pre-generated subset; a layered approximation is not a subset, but it quantises. Options:
    (a) layered tint approximation (Recommended); (b) a pre-baked atlas indexed by
    Molang (breaks rule 4 plainly); (c) do not ship coats on Bedrock. This touches
    wiki/philosophy.html: a decisions.html entry either way.
  Code: a rasteriser tool in common/ (or :bedrock-js) that renders the SAME composer to a
    fixed set of layer PNGs at build time; the add-on's render controller composes them.
    Gene effects that depend on the pixel (roan, dun shading, gradients) become overlays
    with a fixed look.
  Data and saves: layer ids and variant order are permanent once a world uses them.
  Tests: a golden that the quantiser maps every genotype to a valid layer set; visual
    checks by photograph (needs a Bedrock client).
  Play checks: horses show; foals match parents' layers.
Piece 4 - Horses, breeding, naming, a few items
  Player sees: a named horse with pedigree and stats; breeding passes genes.
  Open 3 (building session after the spike): breeding via entitySpawn on the foal plus
    nearest love-mode parents is a heuristic; if a breed event exists (spike question 5)
    use it.
  Code: TypeScript in a new add-on module; items via custom components (stable); gene
    carrots and the research items as simple custom items.
  Docs: a new wiki page for the Bedrock add-on (CLAUDE.md rule 9 and add-a-wiki-page).
Piece 5 - Screens and the rest (re-askable)
  Player sees: forms, not free-layout GUIs: server-ui forms replace the H menu, the family
    tree and the spawn screen. Villagers become entities with JSON trade tables. No
    advancements (script and dynamic properties instead).
  Open 4 (owner): the portal and generated stables: custom dimensions exist (stable since
    26.30) but are VOID-only; stables would be placed .mcstructure files. Recommended: leave
    out until everything else works.

5. DECISIONS
------------
A The ask: the small version worth having is piece 2 + 3 + 4 (a named, bred, coloured horse).
B Fit with the mod: philosophy bend (piece 3). Open 5 (owner): is Bedrock allowed to be a
  smaller game than Java ("a carrot, not a stick" still holds)? Recommended: yes.
  Open 6 (owner): Marketplace, or free .mcaddon only? CC BY-NC 4.0 conflicts with sales; the
  Marketplace needs a registered business (UNVERIFIED, secondary source). Recommended: free
  .mcaddon first.
C Items: custom components. D Genetics: unchanged, in common/. E Breeds: breed JSON loads
  in the bundle; spawning needs spawn rules (UNVERIFIED how well they express regions).
G Config: there is no config file on Bedrock; script constants or world dynamic properties.
H Saves: new worlds; dynamic property limits UNVERIFIED. I Multiplayer: Bedrock Dedicated
  Server and Realms add script and permission limits (UNVERIFIED). J Compat: none.
K Performance: QuickJS is an interpreter; TeaVM output size and speed are unknown (spike);
  chunk work across ticks. L Testing: no gametest in Bedrock for this; manual and the parity test.
M Release: Decided, held to 1.0.0.
1 (owner): confirm the TeaVM-JS-is-not-a-hand-port reading of hard rule 3.
