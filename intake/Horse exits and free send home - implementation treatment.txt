Horse exits and free send home - implementation treatment

Scoped with the owner. Every "Decided" line below is her call; "UNVERIFIED" lines
are facts this file has not proved and the building session must check first.
Two pieces, shippable separately: (1) a new Exits tab on the H menu, (2) Send
home becomes free by default and configurable. Source of truth for what exists is
wiki/horse-browser.html (the H menu) and wiki/horse-care.html / wiki/item-tickets.html
(Send home and tickets). This file is retired (deleted, per /process-intake step 8) as
each piece ships and moves onto those pages' Gameplay and Coding tabs.

What already exists, so the building session does not redo it
==============================================================
- client/HorseBrowserScreen: a private enum Tab (My horses, Breeding preview,
  Log, Realm, Recipes, Query, Getting started ...). A new tab is a new enum entry,
  a payload for its data, and a draw/click branch like the Log's.
- The Log tab and its data: common/log/HorseEvent (Kind: COVER, BIRTH, DEATH,
  TAMED, PURCHASE, SALE, TRANSFER, RESCUE, HOMED) and HorseEventLog, keyed per
  owner, BOUNDED at HorseEventLog.MAX_PER_OWNER. Sent whole as HorseLogPayload and
  filtered client-side (ClientHorseLog.of(filter)). Written from server/HorseLog.
- Where exits are written today, in server/HorseLog: death (with a cause), sale to
  a player and transfer (the same call writes a PURCHASE row for the taker and a
  SALE row for the giver), and soldToDealer (the wandering trader and the cowboy
  call it). HOMED is a horse walking to its stall, NOT an exit.
- NOT logged anywhere today: a horse leaving through the realm. Both ways in go
  through server/HorsePortalManager (hay-bale portal) and server/FreedomStickHandler.
  So "sent to the realm" is a new event, not a new view.
- The pedigree is the permanent record and survives death and sale. There is a
  family-tree request/response (FamilyTreeRequestPayload / FamilyTreeDataPayload)
  keyed by horse UUID.
- Send home: network/HorseRecallPayload (client to server, carries the horse's
  RECORD UUID, "not trusted") -> server/StallRecall.request. It re-checks
  ownership, death, stall, pen and TICKETS. chooseTicket picks the cheapest ticket
  that reaches (tier limits which worlds a ticket crosses) and ticket.shrink(1)
  spends it. The same path serves a horse inside a stasis chamber/bank
  (StallRecall.fromChamber), which is what "out of the gene bank" means: the
  Stasis Bank (wiki/horse-stasis.html).

Piece 1 - the Exits tab
=======================
What the player sees: one tab, called "Exits", listing every horse of theirs that
is gone, newest first, with filter chips.
- Decided: a SEPARATE PERMANENT LEDGER. Exits has its own per-owner store that is
  never trimmed. It is one row per horse that left, not one per cover, so it does
  not grow like the Log. The Log tab stays capped at its 200 rows and unchanged.
  Do not make Exits a filtered view of the Log: a busy breeder's covers would push
  old sales and deaths off the end, and the ask is "every horse".
- Decided: the filter chips are exactly four:
    Died - killed, drowned or otherwise died, with the cause where known.
    Sold/given to a player - transfer papers and /horsegive (one chip; the Log
      already writes both as SALE for the giver).
    Sold to a dealer - the wandering trader and the cowboy.
    Sent to the horse realm - the hay portal and the freedom stick.
  Plus an "all" state, as the Log's chips have. No other chips.
- Decided: a row shows the horse's name as it read at the time (a dead or sold
  horse cannot be asked later), when, and the other party where there is one (the
  buyer, the dealer, the cause). Same wording discipline as HorseEvent.line(): the
  wording lives in common/ so a test can pin it down.
- Decided: clicking a row OPENS THE HORSE'S RECORD (its pedigree and genetics),
  which the mod already keeps permanently. UNVERIFIED which existing screen can
  show a horse that is not in the world and has no entity: HorseInfoScreen is built
  from (record, horse, ...) and the horse part may be null or not; the family-tree
  payload is keyed by UUID and works for a gone horse. Read both first. If the
  info screen cannot show a horseless record, open the family tree instead and
  report which was used.
- Where the ledger lives: a new type in common/log/ (an ExitRecord / ExitLedger
  beside HorseEvent, game-free, hard rule 1), persisted by the game module the
  same way HorseEventLog is (copy that persistence rather than inventing one).
  Writes come from the SAME call sites as the Log: add the ledger write next to the
  existing HorseLog calls for death, sale/transfer and soldToDealer, plus two new
  call sites for the realm (HorsePortalManager and FreedomStickHandler). Do not
  derive exits by scanning the Log.
- Death passes through several handlers (HorseEventLog dedupes a repeat inside a
  window). The ledger needs the same: ONE row per horse per exit, keyed by the horse
  UUID, so a death reported twice is one row. A horse that exits, is claimed back
  from the realm and exits again is two rows: that is two exits.
- Decided: past exits are SEEDED from the existing Log. The first time a player's
  ledger is read after the update, copy any DEATH, SALE and TRANSFER rows still in
  their 200-row Log into it. Older ones are gone and the tab says so on one line.
  Realm exits cannot be seeded, because they were never logged. Seeding must be
  idempotent (running twice adds nothing) - key it on the horse UUID.
- Sync: same shape as HorseLogPayload (whole list on open, pushed when a row is
  written for an online player). UNVERIFIED that a whole-list payload is still fine
  for an unbounded ledger. A breeder who has lost a thousand horses is a payload of
  a thousand rows; if that is too big, page it, and say why. Do not decide silently.
- Config: none for the tab. Nothing about it is tunable.
- Tests: common/ unit tests for the ledger (one row per horse per exit, dedupe,
  seeding is idempotent, the four chips filter correctly, the line wording). A
  gametest for each of the new realm call sites writing a row, and for the death
  and sale ones still writing one.
- Play checks (Verification tab): sell a horse to a player, to a trader, kill one,
  portal one and freedom-stick one, and see all five on Exits; open each row.

Piece 2 - Send home is free, and can be made to cost
====================================================
What changes for the player: the Send home button in the H menu's My horses tab
works with no ticket, including for a horse sitting in a stasis chamber / bank.
- Decided: FREE BY DEFAULT. Today it spends a ticket; the default becomes no cost.
  This includes the stasis-chamber path (StallRecall.fromChamber).
- Decided: free means ANYWHERE. It no longer depends on a ticket's tier or on which
  dimension the horse is in, because the destination is the horse's own stall (or
  the holding pen, as it falls back today). The stall is still re-measured live at
  send time (the horse must not be teleported into a wall) and a refusal still
  leaves nothing spent. Reuse TicketHandler's landing rules; do not write a second
  copy (StallRecall's own class comment says why).
- Decided: PAYMENT IS CONFIGURABLE, as ONE ITEM + A COUNT. A server option names a
  registry item id (vanilla or modded, any item) and a count per trip. No item or a
  count of 0 means free, which is the default.
- Decided: the payment item is CONSUMED per successful trip. If the player does not
  have it, nothing happens and nothing is spent, the same rule tickets follow now.
  The refusal line names the item and the count.
- Decided: when payment is configured, it REPLACES ticket spending for the button.
  Tickets and whistles are not also charged. They remain the way to send or call a
  horse from the world with no menu.
- Decided: the button's tooltip and the refusal line SUGGEST the alternatives, in
  text, so a server owner who sets a price still points players at them: "Tickets
  and whistles can also bring a horse home." Keep it to one short sentence, and read
  the item names from the live roster rather than hard-coding them.
- Decided: a COOLDOWN of 5 seconds between sends, per player, default 5, and
  configurable (0 turns it off). It is per player, not per horse, and the refusal
  line says how long is left. Start the cooldown only on a successful send.
- Config home: ServerConfig, behaviour.*, with the usual safe accessor beside it
  (copy the pattern of leadsReturn()). Three new options: the payment item id, the
  payment count, the cooldown in seconds. UNVERIFIED how ServerConfig declares a
  string option holding a registry item id and how the existing items there
  are validated; read it first. An id that is not a registered item must be
  refused or logged and treated as free, never crash on a world load.
- Sync: the button needs to know whether it is free, to draw "Send home" vs "Send
  home (costs 1 x <item>)". The config is server-side. UNVERIFIED whether the
  client can read server config values; if it cannot, send the two values in the
  existing roster payload rather than adding a payload.
- Docs that must change with it: wiki/item-tickets.html and wiki/horse-browser.html
  currently describe the button as spending a ticket. Say what is true after.
- Tests: a gametest for free (no ticket, horse lands in its stall), for a refusal
  with payment configured and none held (nothing spent), for payment taken on
  success, and for the cooldown. The unloaded-horse path (chunk ticket, wait, then
  act) is unchanged and must keep working; check it once by hand.
