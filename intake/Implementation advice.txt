Implementation advice for intake/To do.txt

Fast path for an implementation session
========================================
Read wiki/roadmap-execution.html first. Its "Implementation handoff packet"
names the owning classes, first focused check, stop condition, and the order of
the hardening stages. Then read only the owning page and the listed classes.
Do not treat this file as a second roadmap: it is context for routing intake,
while the wiki page is the execution source of truth.

Before editing, write one sentence for the current hypothesis and one check
that could disprove it. After the first edit, run that check immediately. If a
check requires NeoForge runtime state, record the exact manual reproduction on
the owning Verification tab instead of widening the repository search.

Purpose
=======
This should be treated as an implementation plan, not as evidence that every
item is currently broken. Several entries look like stale reports or checks that
may already be present. The first pass should verify existing behavior in-game,
then only change code where the observed behavior is missing or wrong.

Recommended order
=================
1. Reproduce and fix the breeding and reproduction rules first.
2. Fix bond decay, AI pathing, and hunger/eating behavior next.
3. Verify the interaction, overview, and barn UI items after the gameplay logic.
4. Treat wings as a separate client rendering project, not as part of the core
   horse AI work.
5. Finish with search/filtering, naming, loot, and ownership transitions.

Core principles
===============
- Keep gameplay rules in the common module when possible; server-only code
  should handle config, chat, persistence, navigation, and rendering.
- Return typed results from the common breeding logic instead of leaking chat or
  player concerns into the model layer.
- Use server-authoritative config and checks for owner messages, breed caps,
  and naming policy; clients may suggest preferences, but they are not the
  authority.
- For AI and pathing problems, check reachability and path-failure states before
  changing movement rules, collision rules, or fence logic.
- Separate “state/history” from “current ownership”: sold or transferred horses
  should still remain in pedigree and family-history data.

1. Breeding and reproduction
===========================
Likely code:
- common/src/main/java/.../repro/NaturalCover.java
- common/src/main/java/.../repro/ReproRules.java
- common/src/main/java/.../genetics/genes/FertilityGene.java
- neoforge-26.1.2/src/main/java/.../server/NaturalBreedingHandler.java
- neoforge-26.1.2/src/main/java/.../server/ReproHandler.java

Implementation:
- Let a stallion evaluate all nearby eligible mares in heat, rather than stopping
  after the first target or a stale single-match check.
- Keep fertility and eligibility checks in the common rules, not in a second
  NeoForge-only validation path.
- Separate attempts from outcomes: a stallion may attempt each eligible mare,
  while conception may still fail for timing, fertility, capacity, or cooldown
  reasons.
- Add a server config value for the nearby-horse cap, with a default of 50 and a
  bounded maximum. Do not read this from client config.
- Treat crowding failures as typed breeding results, not as raw ActionTrace logs.
- Report every useful failed breeding attempt to the relevant owner or owners,
  with throttling so an autonomous AI loop does not spam chat.
- Do not add a lineage/ancestry rejection rule unless the design is explicitly
  changed; the current request is satisfied by no ancestry gate in the common
  conception logic.

Validation:
- Run NaturalCoverTest and ReproRulesTest against multiple mares, daily retry,
  negative fertility, and how the cap behaves under server config.
- Verify owner-facing messages for a full pen, a blocked target, and a failed
  conception follow the same typed reason path.
- Confirm a known related pair can still conceive when ordinary fertility and
  timing rules pass.

2. Bond decay and horse AI goals
=================================
Likely code:
- HorseCareAttachment and HorseCareHandler
- BondFollowGoal
- HungerFoodGoal
- DietFoods and HorseDiet

Implementation:
- Bond decay should reduce once per in-game day, not every tick, and should stop
  at a positive minimum floor. Persist the last-decay marker or timestamp so it
  survives unloads and restarts.
- Require a navigable path for bond follow/watch behavior. The goal should not
  treat “line of sight” or “owner visible” as enough when a wall or fence blocks
  movement.
- Keep feeding logic diet-driven rather than maintaining a second hard-coded
  edible-item list. The goal should search for valid dropped food, verify the
  item is in the horse's diet, and confirm the path to it is reachable.
- Reuse the same reachability/boundary predicate for pasture crowding, crop
  eating, and food selection so a horse does not grind against an unreachable
  fence or through a blocked barrier.
- Low-health panic should be server-authoritative, trigger at a configurable
  threshold, and include a single buck-off plus an escape goal that cannot
  phase through walls or into unverified landing spaces.

Validation:
- Test daily decay, minimum floor, persistence, and no multiple decays in one day.
- Test open pen, wall-separated pen, reachable gate, unreachable owner, and valid
  versus invalid dropped food.
- Confirm food goals do not bypass hunger state and that panic goals stop before
  they become an indefinite stuck state.

3. Interaction, overview, and horse UI
======================================
Likely code:
- HorseInfoInteraction
- HorseInteractionHandler
- HorseInfoScreen
- SetBarnNamePayload and its networking handler
- HorseRecord and its barn-name fields

Implementation:
- Fix the sneak-right-click flash by checking event cancellation and duplicate
  server handling before changing the UI itself.
- Keep the saddle state single-sourced. The overview should summarise saddle
  state without creating a second editing source or overlapping click targets.
- Verify the barn name round trip end-to-end: submit, validate, persist, reload,
  reconnect, and ownership checks.
- Do not add a second naming state in the UI without a server-side validation
  path; names are gameplay data, not personal client-only settings.

Validation:
- Inspect unsaddled and saddled horses across mouse and keyboard focus states.
- Confirm the barn name survives a save/reload cycle and rejects bad lengths or
  invalid characters.
- Reproduce the menu flash and confirm it is event ordering, not rendering.

4. Family history, ownership, and cowboy transitions
====================================================
Likely code:
- family-tree and horse-record ownership data
- cowboy stable/ownership transition logic
- horse damage and death hooks

Implementation:
- Treat sold status as historical relationship data, not as a deletion or a
  family-tree filter. Sold horses should remain in pedigree graphs with a sold
  presentation.
- Choose a deliberate ownership transition for cowboy horses instead of letting
  “cowboy died” silently revert to vanilla wild behavior. Preserve the record and
  pedigree while moving into a rescue, claim, or stable-transfer path.
- Hook damage and death messages on the server. Damage alerts should go only to
  the owner; death messages should only fire once and only for owned horses when
  that toggle is enabled.

Validation:
- Sell a horse, reload data, and confirm the family tree keeps the sold node and
  its pedigree link.
- Test cowboy defeat and recovery paths, death notifications, and owner-only
  routing in a two-player dedicated server setup.

5. Search, filters, naming, and loot
=====================================
Likely code:
- H-menu search and horse-search parsing
- breeding overview filter model
- name-generation helpers and horse creation path
- loot-table injection and horse-equipment loot pools

Implementation:
- Extend the existing search abstraction rather than adding a second screen-only
  filter path. Support allele combinations, exact pair modes, and known aliases
  through the common genotype registry.
- Keep the breeding overview filter separate from breeding eligibility: the
  display filter should be client-side and reversible, without mutating the actual
  mating rules.
- Replace duplicate-prone naming with a deterministic inheritance policy:
  default daughter -> dam last name, son -> sire last name, with random first
  names from the existing name tables.
- Treat loot as a centralized generation/injection pass, not as one-off edits.
  Increase golden carrot seed and gene-book frequency substantially while
  preserving rare/common tuning, and include dyed leather horse armor and saddle
  variants as valid generated item data.

Validation:
- Search for allele combinations in both H-menu and breeding overview, reverse
  order, and confirm invalid queries fail clearly.
- Create daughters and sons from parents with different surnames, reload, and
  confirm the name policy remains stable.
- Enumerate loot tables and verify the horse equipment pool is present, valid,
  and tuned for the intended rarity.

6. Specific implementation checks before closeout
==================================================
- First run the focused tests already in the project: NaturalCoverTest,
  ReproRulesTest, and FertilityGeneTest.
- Use the existing DebugYardFertility, DebugYardHunger, and
  DebugYardUnattended scenarios as the initial verification loop.
- Confirm that a feature is genuinely absent before adding a new test. Several
  TODO items are likely stale or already covered by the current code.
- Keep gameplay rules in the common module and keep NeoForge responsible for
  config, networking, chat, rendering, and navigation.
- Update the relevant wiki and verification page after implementation, rather
  than relying on this intake note as the long-term source of truth.

7. Wings
=========
This should be a separate client render task, not mixed into the core breeding,
AI, or UI queue.

Implementation:
- Start from the existing flight capability, but do not assume the vanilla elytra
  renderer can be attached directly to a horse.
- Add a dedicated horse-wing state and a horse-specific render layer or model.
- Keep flight physics separate from rendering; the server-side flight capability
  remains the authority for whether a horse can fly.
- Reuse the elytra texture path only if the UV layout is valid for a horse body;
  if not, use a documented horse-specific wing texture contract.

Validation:
- Check standing, walking, jumping, gliding, saddled, and different horse sizes.
- Verify at least one texture retexture works without assuming every elytra
  resource pack is compatible.
