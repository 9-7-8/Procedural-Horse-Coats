Implementation advice for intake/To do.txt

Fast path for an implementation session
========================================
Read wiki/roadmap-execution.html first. Its "Implementation handoff packet"
names the owning classes, first focused check, stop condition, and the order of
the hardening stages. Then read only the owning page and the listed classes.
Do not treat this file as a second roadmap: it is context for routing intake,
while the wiki page is the execution source of truth.

Run node wiki/tools/check-roadmap-execution.mjs before editing. It checks that
every roadmap page has a coverage row and every open Known gap is routed, so a
session does not need to audit those lists manually.

Before editing, write one sentence for the current hypothesis and one check
that could disprove it. After the first edit, run that check immediately. If a
check requires NeoForge runtime state, record the exact manual reproduction on
the owning Verification tab instead of widening the repository search.

Purpose
=======
This should be treated as an implementation plan, not as evidence that every
item is currently broken. Several entries look like stale reports or checks that
may already be present. The first pass should verify existing behavior in-game,
then only change code where the observed behavior is missing or wrong.

Recommended order
=================
1. Reproduce and fix the breeding and reproduction rules first.
2. Fix bond decay, AI pathing, and hunger/eating behavior next.
3. Finish with search/filtering, naming, loot, and ownership transitions.

Core principles
===============
- Keep gameplay rules in the common module when possible; server-only code
  should handle config, chat, persistence, navigation, and rendering.
- Return typed results from the common breeding logic instead of leaking chat or
  player concerns into the model layer.
- Use server-authoritative config and checks for owner messages, breed caps,
  and naming policy; clients may suggest preferences, but they are not the
  authority.
- For AI and pathing problems, check reachability and path-failure states before
  changing movement rules, collision rules, or fence logic.
- Separate “state/history” from “current ownership”: sold or transferred horses
  should still remain in pedigree and family-history data.

1. Breeding and reproduction
===========================
Likely code:
- common/src/main/java/.../repro/NaturalCover.java
- common/src/main/java/.../repro/ReproRules.java
- common/src/main/java/.../genetics/genes/FertilityGene.java
- neoforge-26.1.2/src/main/java/.../server/NaturalBreedingHandler.java
- neoforge-26.1.2/src/main/java/.../server/ReproHandler.java

Implementation:
- Let a stallion evaluate all nearby eligible mares in heat, rather than stopping
  after the first target or a stale single-match check.
- Keep fertility and eligibility checks in the common rules, not in a second
  NeoForge-only validation path.
- Separate attempts from outcomes: a stallion may attempt each eligible mare,
  while conception may still fail for timing, fertility, capacity, or cooldown
  reasons.
- Add a server config value for the nearby-horse cap, with a default of 50 and a
  bounded maximum. Do not read this from client config.
- Treat crowding failures as typed breeding results, not as raw ActionTrace logs.
- Report every useful failed breeding attempt to the relevant owner or owners,
  with throttling so an autonomous AI loop does not spam chat.
- Do not add a lineage/ancestry rejection rule unless the design is explicitly
  changed; the current request is satisfied by no ancestry gate in the common
  conception logic.

Validation:
- Run NaturalCoverTest and ReproRulesTest against multiple mares, daily retry,
  negative fertility, and how the cap behaves under server config.
- Verify owner-facing messages for a full pen, a blocked target, and a failed
  conception follow the same typed reason path.
- Confirm a known related pair can still conceive when ordinary fertility and
  timing rules pass.

2. Bond decay and horse AI goals
=================================
Likely code:
- HorseCareAttachment and HorseCareHandler
- BondFollowGoal
- HungerFoodGoal
- DietFoods and HorseDiet

Implementation:
- Bond decay should reduce once per in-game day, not every tick, and should stop
  at a positive minimum floor. Persist the last-decay marker or timestamp so it
  survives unloads and restarts.
- Keep feeding logic diet-driven rather than maintaining a second hard-coded
  edible-item list. The goal should search for valid dropped food, verify the
  item is in the horse's diet, and confirm the path to it is reachable.

Validation:
- Test daily decay, minimum floor, persistence, and no multiple decays in one day.
- Test open pen, wall-separated pen, reachable gate, unreachable owner, and valid
  versus invalid dropped food.
- Confirm food goals do not bypass hunger state.

4. Search, filters, naming, and loot
=====================================
Likely code:
- H-menu search and horse-search parsing
- breeding overview filter model
- name-generation helpers and horse creation path
- loot-table injection and horse-equipment loot pools

Implementation:
- Extend the existing search abstraction rather than adding a second screen-only
  filter path. Support allele combinations, exact pair modes, and known aliases
  through the common genotype registry.
- Keep the breeding overview filter separate from breeding eligibility: the
  display filter should be client-side and reversible, without mutating the actual
  mating rules.
- Replace duplicate-prone naming with a deterministic inheritance policy:
  default daughter -> dam last name, son -> sire last name, with random first
  names from the existing name tables.
- Treat loot as a centralized generation/injection pass, not as one-off edits.
  Increase golden carrot seed and gene-book frequency substantially while
  preserving rare/common tuning, and include dyed leather horse armor and saddle
  variants as valid generated item data.

Validation:
- Search for allele combinations in both H-menu and breeding overview, reverse
  order, and confirm invalid queries fail clearly.
- Create daughters and sons from parents with different surnames, reload, and
  confirm the name policy remains stable.
- Enumerate loot tables and verify the horse equipment pool is present, valid,
  and tuned for the intended rarity.

6. Magical loci: go runtime-registry for lycan/egg-layer/item-drop
=================================================================================================
Likely code:
- common/src/main/java/.../genetics/genes/LycanGene.java
- common/src/main/java/.../genetics/genes/EggLayerGene.java
- common/src/main/java/.../genetics/genes/MagicItemDropGene.java
- neoforge-26.1.2/src/main/java/.../server/LycanthropyHandler.java

Implementation:
- Lycan mob list: LycanGene currently hand-lists vanilla mob ids at compile
  time (form("Aly", "minecraft:allay", ...) etc.), grouped only by "non-hostile
  spawn category". Split that into a category blacklist (aquatic: water
  creature, water ambient, axolotl, underground water creature; flying: any
  mob whose movement type is flying, e.g. bat, bee, parrot, phantom, happy
  ghast; hostile: MONSTER and anything already excluded) and remove every mob
  in a blacklisted category from the allele set, including ones currently in
  the hand-written list.
- Lycan mob list, runtime: replace the hand-written form(...) calls with a
  derivation over the live entity-type registry at startup/data-gen time -
  every registered mob (vanilla or modded) whose spawn category and movement
  type pass the blacklist becomes a form/allele automatically. Common/ cannot
  import Minecraft classes, so this has to be resolved on the NeoForge side
  (following the existing "ids are plain strings, resolved against the live
  registry" pattern lycan and egg-layer already use for unrecognised ids) and
  handed to LycanGene as data, not hard-coded per mob.
- Egg layer / magic item drop, runtime: EggLayerGene and MagicItemDropGene each
  ship a fixed short list of vanilla item ids as alleles. Give both the same
  registry-driven treatment as the lycan mob list - a run built from every
  item any loaded mod registers - rather than adding modded items by hand one
  at a time. Keep the founder-table balancing (rarity per allele) as config the
  runtime derivation reads, not something that has to be re-authored per mod.
- All three derivations need to be stable across a world's lifetime (an allele
  index that shifts when a mod is added/removed corrupts saved genotypes), so
  settle the id-to-allele-index scheme (likely sorted-by-id, keyed by string id
  rather than by ordinal) before wiring it in.

Validation:
- LycanGeneTest (or equivalent) asserting no aquatic/flying/hostile mob id is
  ever produced, including under a modded entity-type registry fixture.
- A round trip test that a genotype recorded against one registry snapshot
  still resolves correctly after mobs/items are added by a fake "other mod" in
  the test fixture.


Netherhorse and Nightmare implementation review
================================================

Scope and rationale
-------------------
- `common/src/main/resources/horsegenetics/breeds/netherhorse.json`: defines
  the requested Nether tank. `E/E`, `A/A`, and `Sh/ShD` target liver bay;
  size `[1.85, 1.95]`, health 9, speed 3, and jump 2 express the giant,
  durable, slow, low-jumping profile. `Frp/Frp` gives fireproofing and lava
  swimming; `Lava/Lava` at milk produces lava; `Aaa/Aaa` attacks everything;
  `APr/APr` makes it permanently calmable only as an adult. Red `MltC/MltC`
  hoofprints, `Lava/Lava` particles, Emberveins, glowing red irises and
  red-banded glowing sclera, and red-banded mane and tail provide its visuals.
- `common/src/main/resources/horsegenetics/breeds/nightmare.json`: defines the
  paired Nether breed. Tiny size `[0.32, 0.42]`, baseline speed 5, jump 10,
  and pull 1 match the requested profile. `Tf/Tf` is true flight;
  `Frp/Frp` is fireproof; `Faa/Faa` flees everything while `n/n` aggression
  prevents it fighting. `Prm/Prm` makes cake a permanent passification route
  at any age. Its gold-banded `MltC/MltC` hoofprints, gold mane and eyes,
  `Rflm/Rflm` flame trail, and red-banded Emberveins distinguish it from the
  Netherhorse. `Wkn/Drk` potion milk combines Weakness with Darkness.
- `common/src/main/resources/horsegenetics/breeds/index.json`: registers both
  breed files so the loader includes them.
- `PassificationGene.OFFERINGS`: appends Nether Wart and Cake without moving
  the existing offering indices. The breed bands select the appended entries:
  Nether Wart for the adult Netherhorse, Cake for the Nightmare.
- `PotionMilkGene`: adds Weakness and Darkness as available potion-milk
  outcomes so the Nightmare can request both from the existing locus.
- `FoodTemptGoal`: recognizes an available passification offering as a
  high-priority lure, allowing an untamed Nightmare to approach a player
  holding Cake even though Cake is not ordinary horse food. The gene routes
  are resolved once per horse; per-player permanent/temporary calm, cooldown,
  and age-window rules are respected before approaching.
- `Passification`: exposes the already-resolved routes within the server
  package and centralizes whether a route is currently available, so the lure
  and interaction use the same route constraints.
- `GeneAbilityHandler.flee` and `Passification`: apply the existing per-player
  passification veto to flee-source selection. A newly calmed player no longer
  remains a flee target; other players and non-player threats remain eligible.
- `wiki/horse-designer/assets/breeds.json` and `wiki/gene-census.html`: baked
  outputs of the two breed definitions; regenerate with `:common:bakeBreedFiles`
  and `:common:bakeGeneCensus` rather than editing by hand.

Review and validation
---------------------
- Confirm the two breed pools use valid gene and allele ids, especially the
  Chaos sclera colour bands, both molten-hoof RGB bands, flight, and potion
  milk. Check whether the intended Nether biome spawn path is useful in play;
  ordinary horse spawning still requires grass and light, so eggs may be the
  practical acquisition route.
- In-game checks remain: the Nightmare approaches Cake, accepts the permanent
  route, and stops fleeing that player while still fleeing others; the
  Netherhorse accepts Nether Wart only as an adult; both hoofprint colours,
  flame/ember trails, eye and mane glow, lava swimming/milking, Nightmare
  flight, and potion effects render and behave as described.
- Passed: `./gradlew :neoforge-26.1.2:compileJava`,
  `./gradlew :common:bakeBreedFiles`, `./gradlew :common:bakeGeneCensus`, and
  `./gradlew :common:test --tests '*BreedFilesTest'` after rebaking. The first
  focused breed test found a stale browser bundle; rebaking resolved it.
- This integration is on `main`. The separately staged intake/wiki cleanup
  about dyed armour is unrelated and must remain outside this change.
