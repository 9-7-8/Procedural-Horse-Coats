FOUR-JAR SPLIT - 00 OVERVIEW AND READING ORDER

This folder is ONE implementation treatment, written across several files so each can be
open beside the code while a piece is built. The entry file in intake/ is
"Four-jar split - implementation treatment.txt"; it points here. Nothing in this folder is
built. Each file is retired (deleted) as the piece it describes ships and moves onto the wiki
pages named in it (per /process-intake step 8). Delete 02 and 01 last.

Scoped with the owner on 2026-10-03 in one long session (a first draft, then three probe
rounds of questions). Every "Decided" line is the owner's call. "Recommended" is the
scoping session's own pick, not asked. "Open" is unsettled and says who settles it.
"UNVERIFIED" is a fact nobody has proved; the building session checks it first.
Written from a cloud session with no game and no jar build.

1. THE REQUEST, AS GIVEN
------------------------
"I want to make this mod a little more modular, because it breaks into three major parts:
the procedural horse coats, the equipment overhaul, and the horse QOL changes. Every release,
we should ship those three jars plus a 'all in one' jar. Each jar should be modular, so they
can use any subset of the jars (except it's redundant to combine with the all in one)"
(owner). Later she changed the shape twice: first a required small Core jar plus three
add-ons ("There's a core base game code jar they have to download, then they pick their
add-ons, and they can pick 'all in one' instead"), then Core and QOL merged ("QOL becomes the
base ... we remove core as a concept") and Coats became Breeding ("rename this to the
breeding addon").

2. THE RESULT: FOUR JARS PER RELEASE
------------------------------------
BASE       id ixoras_horses_base       REQUIRED. The framework plus every quality-of-life change.
BREEDING   id ixoras_horses_breeding   add-on. Needs Base. Genetics, coats, breeds, breeding.
EQUIPMENT  id ixoras_horses_equipment  add-on. Needs Base. Gear slots, tack, carts, braid.
ALL-IN-ONE id ixoras_horses            Base + Breeding + Equipment in one file. Used INSTEAD.
- Breeding and Equipment do not need each other. Any subset on top of Base works.
- The all-in-one next to any other jar is "redundant" and is declared incompatible, so loading
  stops with a plain message.
- One namespace for everything (the all-in-one's), one lockstep version number
  0.<compat>.<patch>, every release ships all four.
- Each jar is its own download (GitHub releases first, other sites later) and states inside
  itself, and on launch, what it requires and what it is incompatible with.
- Files: ixoras-horses-<base|breeding|equipment>-<version>.jar and ixoras-horses-<version>.jar
  (the all-in-one name is Recommended, not asked).

3. WHAT EACH JAR HOLDS, IN ONE SCREEN (details: file 03)
--------------------------------------------------------
BASE: a slim horse record (id, names, barn name, owner, tamedBy, sex), the plug-in framework
(info-screen tabs, H-browser tabs, checklist tasks, per-jar registries, a documented but
unstable API), the H-browser frame and its Log tab, the creative tab, the shared slow tick,
the name tables, config plumbing, the world marker and its override. Features: bond, herd
behaviour, plain wild herds on vanilla horses, whistles and the ender whistle, stall signs,
jumps, double gates, equestrian posts, the Equestrian Bench (dyes vanilla saddles and armour),
bareback steering, bolting, horse leads, mining from the saddle, ALT+E, rider fade, the leash
fixes, HUNGER and water-gated healing (one config toggle), and the SEX rule (only opposite-sex
pairs breed; config toggle turns sex off).
BREEDING: genetics, coat painting, breeds, pedigree, body stats, breeding (autonomous covers,
heat, pregnancy), gelding and the vet kit, breeding/splice carrots, research papers, the gene
database, the breed and horse designers, stasis, DIET, breed herds and founders, the horse realm
and hay portals, stables, the cowboy / horseman / barn / scientist / supplier villagers, the F6
debug corridor, the gene-ability mixins.
EQUIPMENT: the 19-slot gear screen, tack slots and right-click-equips, tack looks, shoes and
saddle pads (planned), the rescuing braid (overlay needs Breeding), all carts, the armour and
material generators, the leatherworker and metalsmith villagers with their trades.

4. ORDER OF WORK (owner)
------------------------
1 Base (framework + QOL, still shipped as the one all-in-one jar)  -> file 04
2 Equipment                                                         -> file 05
3 Breeding + the four-jar release pipeline                          -> file 06
Until piece 3 the shipped artifact is the one all-in-one jar. Each piece leaves a playable
game and can be released as a patch. Reason for the order: Base is the groundwork both
add-ons need; Equipment is the most self-contained add-on (carts already plug in through one
bridge); Breeding is the largest and goes last, when the plug-in contract has been proven twice.

DEPENDENCY ON OTHER WORK (owner): this split lands AFTER the rename to Ixora's Horse Overhaul
(intake/Rename to Ixora's Horse Overhaul - implementation treatment.txt). The four ids above use
the new brand. Do not build both at once; do not start piece 1 until the converter exists.

5. IN SCOPE, AND WHAT IS NOT
----------------------------
In: four jars; :common split into three Gradle modules (:common-base, :common-breeding,
:common-equipment); the genome-agnostic record; the extension points and their documented
API; a Base size report and budget gate; the world marker and server.toml override; readable
incompatibility and dependency messages; hunger toggle; sex toggle; release procedure, README,
wiki and tests for four jars.
Out (re-askable): any other new feature; the rename itself; the bridle/saddle split, horse
shoes, command whistle and troughs (each its own treatment, landing in the jar named in 03); a
separate jar for carts or for the realm; per-jar version numbers; other loaders and other
Minecraft versions (the port treatments each multiply by four jars and must be re-sized after
this ships).

6. RELEASE (Part 4 M of the scoping procedure)
----------------------------------------------
Recommended (not asked): each piece counts toward the next patch release; the first four-jar
release is piece 3. Recommended: saves keep loading by keeping every saved key unchanged
(file 07). If a key cannot be kept, that is a compat (second-number) bump and needs the owner.
Confirm both at release time (procedures/release.txt).
