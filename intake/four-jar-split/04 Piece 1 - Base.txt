FOUR-JAR SPLIT - 04 PIECE 1: THE BASE (size L+, the largest piece)

Goal: build the Base as its own Gradle module and jar-shaped unit, move every quality-of-life
feature into it, add the plug-in framework, and make the horse record genome-agnostic. The shipped
artifact is STILL the one all-in-one jar (Base + everything else compiled together), so the game
plays the same and a patch release can be cut after this piece. Read 00, 01 and 03 first.
Do not start until the rename has shipped (file 01, D9).

WHAT THE PLAYER SEES
Nothing changes in the all-in-one except two new config toggles (hunger, sex), both default ON
(matching today), and a few corrected edge cases. The build output gains a per-jar size report.
The owner can see the module boundaries in the repo.

NEW BEHAVIOUR THIS PIECE ADDS (everything else is a move)
- Config toggle for hunger+healing (D15). Off = vanilla healing, nothing hidden or gated.
- Config toggle for sex (D25). Off = sex hidden and unused for pairing; flippable on a live save.
- The sex rule: only an opposite-sex pair breeds (hand-feeding path, via the canParent hook).
- A horse with no genome gets a stored random sex and a stored plain record.
These are the only intended gameplay changes. Everything else must be byte-for-byte the same.

STEP 3 - THE SLIM RECORD (the hardest step; the saved form must not change)
Facts to design against (read, 2026-10-03):
- HorseRecord (C/horse) has 15 fields. Sex is NOT a field: it is the "horsegenetics.sex" locus inside
  geneticCode, read through sex(). HorseRecordCodecs says why: serialising sex separately "would let a
  saved record disagree with the genome it carries".
- HorseRecordCodecs.MAP_CODEC (N/data) is the one codec, used by the HORSE_RECORD attachment and by
  HorseAncestryData (SavedData, Breeding).
- Without Breeding there IS no genome, so a Base-only horse cannot get its sex from one.
Design (Recommended; settle details at build time):
a) Split the type. Base owns HorseIdentity: id, firstName, lastName, barnName, tamedBy, ownerId, plus
   `sex` (see (c)). Breeding owns HorseRecord = a HorseIdentity plus the genome and breeding fields
   (geneticCode, epigenomeCode, breed, motherId, fatherId, bredBy, generation, parentStats, gelded).
   Whether `gelded` and `tamedBy` stay where they are is a build-time call: gelded is Breeding by D12/D27 but
   its saved field must round-trip in Base (D28); tamedBy is Base-friendly (no breeding use).
b) The codec keeps the SAME key names ("id", "first_name", "last_name", "barn_name", "genetic_code",
   "epigenome_code", "breed", "mother_id", "father_id", "tamed_by", "bred_by", "generation",
   "parent_stats", "gelded", "owner_id"). Base's codec reads the identity keys and keeps every other key as
   opaque data and writes it back unchanged; Breeding's codec reads/writes the rest. UNVERIFIED: how to hold
   unknown keys with DataFixerUpper in 26.1.2 (Dynamic/passthrough); the domain type stays DFU-free, so this
   sits in N/data. Spike it with one saved horse's NBT: Base-only load/save must reproduce identical NBT.
c) SEX. Add ONE new OPTIONAL key (e.g. "base_sex") that is written only for a horse that has NO genome.
   Rules: (1) a horse with a genome ignores the key and the genome's sex wins, so the two can never
   disagree; (2) a horse without a genome gets a random sex ONCE at first sight and it is stored then (it must
   not re-roll on reload); (3) when Breeding gives a horse a genome (D24) the genome is rolled with THAT sex
   fixed to the stored one, so a mare stays a mare; (4) old saves have no such key, and old records all have
   a genome, so nothing changes for them (rule 10: additive, optional). Check the all-in-one never writes it
   for a horse that has a genome.
d) HorseRecords (N/server) is used in 79 files. Split its API: identityOf(horse) for Base callers; recordOf
   (horse) for Breeding callers. Move call sites one package at a time; each must compile before the next.
e) The sync payload HorseRecordSyncPayload carries the identity; Breeding adds its own payload for the genome
   fields (it already has CoatSyncPayload etc.). Client cache ClientHorseRecordCache holds identity only.
CHECKPOINT: tests for (b) a round trip of a legacy record (full 15 keys) through Base alone (identical output),
and through Breeding; (c) sex rules 1-4; gametest: a vanilla horse in a Base-only configuration gets a record, a
name and a sex that survive save/reload; the all-in-one's existing horses are byte-identical before and after.

STEP 4 - THE HOOKS (interfaces Base defines; later jars implement)
Create these in :common-base (pure interfaces) and wire in N. Each has a default that means "no Breeding" and
no Equipment, so Base works alone:
- StatProvider: speed, jump, health, size for a horse (default: the vanilla attributes). Breeding registers the
  genetic implementation. Equipment's carts read it (HorseDraft). Replaces HorseDraft's direct genome reads.
- FoodChoice and RegenGate: which foods a horse seeks and eats (default: standard foods) and whether it may
  heal (default: yes, subject to hunger). Breeding's diet overrides (HorseDietHandler.canRegenerate,
  DietFoods, FoodPreferenceHandler).
- PairingRule: may these two horses breed. Base: opposite sex, unless the sex toggle is off. Breeding adds its
  own conditions (heat, gelding, fertility, health) on top. Hooked from HorseAlwaysParentMixin (R11).
- CareSubscriber: one slow tick, many subscribers (R2). Base: bond, hunger, healing, herd flag. Breeding: the
  gelded bond bonus and the breed-based progress awards (MEET_DHAMPIR, MEET_MAGICAL_HERD).
- OverlaySource: "extra things drawn on the horse" (the braid; also lets Breeding draw its layers). Base default:
  nothing.
- A trade/profession registration hook is NOT needed (Equipment owns its professions outright, D17).
CHECKPOINT: every hook has a unit test with its default; with no implementation registered the Base module's
tests pass; the all-in-one's behaviour is unchanged (gametest suite same result as the baseline).
