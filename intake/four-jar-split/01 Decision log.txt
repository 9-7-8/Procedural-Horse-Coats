FOUR-JAR SPLIT - 01 DECISION LOG

Every decision, grouped by subject. D = Decided by the owner (her words in quotes where she
gave them). R = Recommended by the scoping session, not asked. O = Open (who settles). Where a
decision replaced an earlier one, file 02 says what was replaced.

A. SHAPE OF THE SPLIT
D1  Ship several jars every release plus an "all in one". Each is usable alone or in any subset
    of add-ons (except combining with the all-in-one, which is redundant).
D2  One required Base jar; two optional add-ons (Breeding, Equipment); an all-in-one. Four jars.
    ("QOL becomes the base ... and we remove core as a concept.")
D3  Why QOL is the base (owner): "I can't imagine someone wanting the breeding changes but not
    the 'leads don't disappear' change."
D4  Ids: ixoras_horses_base, ixoras_horses_breeding, ixoras_horses_equipment; the all-in-one keeps
    the existing id ixoras_horses (owner: "keep the existing id for all in one, new ids for
    everything else, Brand + role").
D5  One shared namespace for all jars (the all-in-one's), so items, blocks, entities, attachments
    and gene keys keep identical ids and a world moves between the all-in-one and any combination.
D6  Lockstep versions: one number for all four jars, every release ships all four.
D7  Break common/ into three Gradle modules: :common-base, :common-breeding, :common-equipment.
    :web and the all-in-one depend on all three.
D8  Keep Base small by rule: Base holds only what every install needs. The build prints per-jar
    sizes and FAILS if Base exceeds a recorded budget, set from the first measured Base build and
    raised only by a deliberate edit with a reason.
D9  Sequencing: split AFTER the rename.
D10 Order of pieces: 1 Base, 2 Equipment, 3 Breeding + four-jar pipeline.
D11 Extension points in scope: info-screen tabs, H-browser tabs, checklist/tutorial tasks per
    jar, per-jar registries (items, blocks, attachments, payloads, menus, config specs, mixins),
    and a public API for third-party mods. The API is documented and UNSTABLE until 1.0.0.

B. WHAT EACH JAR OWNS
D12 BREEDING owns: genetics, breeding, pedigree, body stats (speed/health/jump), breeds, the breed
    designer, breeding/splice carrots, research papers, stasis chambers and banks, the vet kit,
    gelding, autonomous breeding, the horse realm, stables, villagers (cowboy, horseman, barn),
    diet, breed herds. ("Coats jar owns all of it.")
D13 BASE owns: bond, herd behaviour, whistles, stall signs, jumps, gates, posts, the Equestrian
    Bench and its dyeing of vanilla saddles and armour, horse leads and rider comfort, leash mixins,
    rider fade, bareback steering, bolting (HorseEscapeGoal), the framework (see D14-D17).
D14 EQUIPMENT owns: the gear slots and screen, tack, shoes, saddle pads, carts, the rescuing braid,
    right-click-equips-tack, the armour/material generators, and the villager tack trades.
D15 Hunger moves to Base, with the water-gated healing it pays for, under ONE config toggle (off =
    vanilla healing). Diet stays in Breeding. ("Move hunger, but not diet, into the base, but make
    it toggle-able from the config.")
D16 Wild herds at their plain level are Base: herd behaviour and wild upkeep (turnover, top-up) on
    ordinary vanilla horses. Breeding owns breed-specific herds and founders. ("Don't we get wild
    herds technically in the base, they're just not per breed?")
D17 Villager tack trades go to Equipment ("Villager tack trades go into equipment").
D18 The H-browser frame and its Log tab are Base so every jar can write log events; Breeding adds
    its tabs. The creative menu has one main tab owned by Base; each add-on appends its items and
    keeps its own extra tabs (Horse Carts, Breeds).
D19 Rider comfort grab bag: horse leads, mining from the saddle, ALT+E, rider fade, leash mixins ->
    Base. Right-click-equips and the armour/material generators -> Equipment.
D20 The rescuing braid is Equipment; it only draws an overlay if Breeding is installed.
D21 Bareback steering and bolting go to Base (QOL) with bond.
D22 The Equestrian Bench and its dyeing of vanilla saddles and armour are Base. (The DYE_TACK task
    goes with it.) Equipment's own tack dyes at the Base bench.

C. THE HORSE WITHOUT BREEDING
D23 The horse record in Base is genome-agnostic. A horse with no Breeding still gets a plain record,
    a generated name (Base keeps the name tables) and reduced screens: the info screen shows
    Overview plus tabs from installed jars; the H menu shows Log and My horses.
D24 Sex stays in Base. With no Breeding it is assigned at random; adding Breeding turns it into
    genetic sex automatically, and the horse KEEPS its current sex.
D25 Base enforces the sex rule: only an opposite-sex pair can breed. A config toggle turns sex OFF
    and can be flipped any time on the same save. Off: sex is hidden and unused when pairing; any two
    adult horses may breed. Stored sex is kept so switching back shows the same sexes.
D26 With Breeding installed and sex off: genetic sex still exists (sex-linked genes keep working) but
    is hidden and ignored for pairing; autonomous covers pick any adult pair; a gelding still never
    breeds.
D27 Without Breeding, gelding, heat, pregnancy, covers and autonomous breeding do not exist. Vanilla
    hand-feeding (golden food) still breeds two horses and gives a vanilla foal.
D28 The saved `gelded` field is kept untouched without Breeding (the record codec round-trips it),
    so a gelding is still a gelding when Breeding returns.

D. SAVES, MARKER, OVERRIDE
D29 A world that has used an add-on (Breeding or Equipment) REFUSES TO LOAD without it, with a message
    naming the add-on. Nothing is deleted.
D30 An add-on counts as "used" once it has written its own saved data into the world; merely
    launching with the jar does not lock the world.
D31 A server.toml switch, default OFF, lets a world load without an add-on it used. That add-on's
    data is kept untouched and ignored.
D32 Parts and the all-in-one are declared incompatible where they overlap, so combining them stops
    loading with a readable message.
D33 Distribution: GitHub releases first, then whatever sites host the mod; each jar its own
    download; each jar states, inside itself and on launch, which jars it requires and which it is
    incompatible with, "so it's foolproof as much as possible".

E. RECOMMENDED (not asked)
R1  Core jar id would have been ixoras_horses_core: dropped with Core.
R2  HorseCareHandler becomes a Base scheduler (one slow tick, a subscriber list) plus one subscriber
    per jar, so the tick stays one pass.
R3  ProgressTask becomes a registered task list; each jar contributes its own tasks; existing ids and
    advancement JSONs unchanged.
R4  The horse_record attachment keeps its exact current serialised form (genome fields in the same
    record, read and written by Breeding; Base round-trips fields it does not understand).
R5  ModdedMaterials, ModdedArmour, DoubleGates and Jumps registrations become explicit init calls in a
    fixed order from each jar's constructor, not class-load side effects.
R6  The dye-tint data component, SaddleTint and the client tint source stay in Base; Equipment's tack
    loot uses the same component.
R7  The marker is a SavedData file in Base listing the add-ons that have written data. A world with no
    marker but with the mod's old data files counts as "all add-ons used"; a world with neither is new.
R8  The override key lives in Base's config section, e.g. world.load_without_used_addons = false (name
    is the building session's), with a WARN naming each missing add-on on every start.
R9  HorseRegenMixin (the vanilla free-heal switch-off) is a plain Horse mixin, not a gene mixin; it
    moves to Base and honours the hunger toggle.
R10 The food-choice and canRegenerate hooks: Base horses eat the standard foods; Breeding's diet
    overrides through a hook in Base.
R11 HorseAlwaysParentMixin (relaxes AbstractHorse.canParent to the golden carrot) is the likely hook for
    the sex rule: Base owns the pairing rule and the mixin; Breeding adds conditions through a hook.
R12 Bond effects that read gelded() are Breeding-only; a Base-only horse never counts as gelded.
R13 Each jar's mods.toml lists required/incompatible jars and names them in the description; Base also
    runs a launch check that gives one plain sentence on a bad combination.
R14 Hunger toggle and sex toggle both default ON (matches today); both server-side; bad values read as
    the default and never crash a world load.
R15 A compat class (Jade, Waystones, FTB Teams, HorsePowered) loads only if its owning jar is present.
