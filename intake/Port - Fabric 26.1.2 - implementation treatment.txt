Port - Fabric 26.1.2 - implementation treatment

Scoped with the owner. Every "Decided" line below is her call; "Recommended" lines are the
scoping session's, not asked; "Open" lines are still to be settled, by whom is said on the
line; "UNVERIFIED" lines are facts this file has not proved and the building session must
check first. Source of truth for what exists is wiki/architecture.html and
wiki/api-notes.html; the shared evidence is intake/Port feasibility survey.txt. This file is
retired (deleted, per /process-intake step 8) as each piece ships and moves onto those

Release: held until 1.0.0, then released (Decided, owner, 2026-10-03).

1. THE REQUEST, AS GIVEN
------------------------
"fabric on 26.1.2" (owner, 2026-10-03). Read as: a Fabric jar of the same mod on the same
Minecraft version the NeoForge build targets today. Fabric supports 26.1.x through 26.3
(fabricmc.net posts 2026-03-14 and 2026-09-15; UNVERIFIED, search snippet only).

2. IN SCOPE, AND WHAT IS NOT
----------------------------
In: a Fabric platform module; moving the loader-free vanilla code into a shared place; a
Fabric implementation of every NeoForge facility the mod uses; Fabric config; the same
data (recipes, advancements, trades, dimension) shipped to both loaders; a Fabric server boot.
Not in: the newest Minecraft (port 1); Quilt (port 3 treatment); optional compat hooks
(Jade, Waystones, FTB Teams, HorsePowered) beyond what exists for Fabric (Open 3); the
gene creator, horse designer, breed designer (browser tools, loader-free).

3. WHAT ALREADY EXISTS
----------------------
- Modules: common/ (pure), neoforge-26.1.2/, web/. settings.gradle.kts. A Fabric module
  would be a fourth: fabric-26.1.2/.
- Coupling, measured 2026-10-03 (see the survey): 204 of 538 neoforge files import
  net.neoforged.*; 334 are vanilla-only. NeoForge facilities in use, with a Fabric target
  (all UNVERIFIED on 26.1.2; the Fabric docs were not readable):
    @SubscribeEvent, 273 handlers, ~45 event types -> Fabric API callbacks (some events have
      no callback and need a mixin: see Open 1). Heaviest: PlayerInteractEvent.EntityInteract
      (31), EntityTickEvent.Post (26), ServerTickEvent.Post (19), EntityJoinLevelEvent (18),
      LivingDeathEvent (12), LivingIncomingDamageEvent (11), FinalizeSpawnEvent,
      BabyEntitySpawnEvent, AnimalTameEvent, TradeWithVillagerEvent, BlockGrowFeatureEvent,
      EntityMountEvent, ScreenEvent.Init.Post.
    DeferredRegister, 37 files -> direct vanilla Registry.register. 17 create() calls plus
      item/block/entity helpers; registered types include VillagerProfession, PoiType,
      StructureType, RecipeSerializer, ParticleType, MenuType, loot function/condition types,
      DataComponentType, CriterionTrigger, CreativeModeTab, Attribute, BlockEntityType.
    Data attachments (data/ModAttachments: HORSE_RECORD, HORSE_CARE, HUNGER, HORSE_SOCIAL,
      HORSE_REPRO, CART_METRES; ~246 get/setData lines) -> Fabric Attachment API (a codec
      persists; sync is manual).
    ModConfigSpec in ServerConfig, ClientConfig, BreedSpawningConfig, carts/CartsConfig ->
      Fabric has no built-in config; a library (Forge Config API Port) or own file.
    Payload registrar, ModNetworking and 45 network files -> PayloadTypeRegistry plus
      ServerPlayNetworking/ClientPlayNetworking; the payload record classes and StreamCodecs
      are vanilla and can be shared.
    4 global loot modifiers (data/loot/*Modifier) and 2 biome modifiers
      (world/BreedHerdsBiomeModifier, data/horsegenetics/neoforge/biome_modifier/) are
      NeoForge-only -> Fabric loot table events and BiomeModifications.
    StasisBankCapability (block/) -> Fabric Transfer API / own storage.
    ClientExtensions (client/TackClientExtensions), TintSources, keymappings, 28 client
      event imports -> Fabric client callbacks.
    13-line accesstransformer.cfg -> accesswidener / classtweaker.
    gametest/ModGameTests (2.5k lines) -> fabric-gametest-api, a different harness.
- Mixins: 19 in neoforge/mixin, horsegenetics.mixins.json (JAVA_21, minVersion 0.8.5). Mixin
  is loader-neutral, so most move unchanged. Mappings are Mojang on both, so no refmap work.
- common/ and web/ need no change.
- LOOKS built but is not: nothing in the repo mentions Fabric (grep decisions.txt,
  architecture.txt: no hits). The 'common/ plus thin platform' split exists, but only the
  common/ half is loader-neutral; neoforge/ is not thin (102k lines).

4. THE PIECES
-------------
Piece 1 - The shared seam (groundwork, ships alone)
  Player sees: nothing; the NeoForge jar is byte-for-byte the same behaviour.
  Recommended: extract the 334 vanilla-only files, plus all data and assets, out of
    neoforge-26.1.2/ into a new shared module (name Open 2) that both platform modules
    depend on, and leave behind only the 204 loader-coupled files. Go for a Gradle source set
    or a module, not Architectury (see Open 2 and survey: the project already has its own
    loader-neutral core).
  Open 1 (building session): split the mixed files. Many files pair vanilla logic with an
    @SubscribeEvent; the seam is "handler method body in shared, one-line subscriber in
    platform". Decide the interface style per file, riskiest file first (see 6).
  Code: all in the NeoForge-neutral shared module; common/ unchanged.
  Data and saves: none; ids unchanged. Sync/Config: none. Tests: NeoForge gametests pass
    unchanged; :common:test --tests on a spot sample.
  Play checks: the NeoForge game still boots, a horse renders, a portal opens.
  Docs: architecture.html (module map, data flow), api-notes.html.
Piece 2 - Fabric boots and registers
  Player sees: the Fabric jar loads; items, blocks, entities, the dimension, the villager
    profession exist; a horse spawns with a coat.
  Code: fabric-26.1.2/ entrypoints, registry code, the attachment, the payloads, config.
  Data and saves: a Fabric world stores the same genotype codes (version-neutral strings in
    common/). Attachment ids must match NeoForge's so a world could in principle move
    between loaders (Open 4, owner: is that a goal? Recommended: no, do not promise it).
  Config: same options and defaults as ServerConfig/ClientConfig; Open 3 the library.
  Tests: a Fabric server boot with generated files deleted; whatever gametests port.
  Play checks: the full yard run (run-tests) on Fabric.
Piece 3 - Events: the long tail
  Player sees: care, hunger, stasis, the cowboy, realm rules and abilities all behave.
  Code: the 273 handlers, in the order of the heaviest event types; add mixins where Fabric
    has no event (UNVERIFIED which: BlockGrowFeatureEvent, FinalizeSpawnEvent,
    LivingIncomingDamageEvent are the likeliest).
  Tests: gametests on the Fabric harness for the abilities that have them.
Piece 4 - Client
  Player sees: the H menu, family tree, gear screens, the designer screen, renderers,
    HD models and layers all draw.
  Code: Fabric renderer/model registration, keybinds, screen hooks, tint sources.
  Play checks: photograph-horses on Fabric against the NeoForge set.
Piece 5 - Compat and distribution
  Open 3 (owner): Jade, Waystones, FTB Teams, HorsePowered on Fabric: which exist and are
    wanted. Recommended: ship without them first and list them as Roadmap.
  Docs: a Fabric section on compatibility.html; the install note in README.md (user-facing).

5. DECISIONS
------------
B Fit: no philosophy change. Open 5 (owner): one multiloader jar or two jars?
  Recommended: two separate jars (what the NeoForge-vs-Fabric gap suggests; a combined jar
  needs a jar-in-jar layout and complicates the release).
C-F, G (config: see piece 2), H (saves: see piece 2), I (multiplayer: payload parity is the
  risk; the same checks as today), J (compat: Open 3), K (performance: Fabric has no
  slow-tick difference; re-run /stress-test once), L (testing: above). D and E (genetics,
  breeds) do not apply, because common/ is shared unchanged. M: Release: Decided, held to 1.0.0.
Open 6 (owner): the Fabric jar's name and mod id: recommended the same id, "horsegenetics",
  with a different artifact name.

6. UNVERIFIED (riskiest first)
------------------------------
1. That Fabric API on 26.1.2 has a callback for each of the ~45 event types; the ones with
   none become mixins. Check: Fabric API on 26.1.2 source, and fabric-events lists.
2. That Fabric's Attachment API and the payload registry take the same codecs unchanged.
3. That the villager-trade side works: trade_set / villager_trade datapack JSON (71+20
   files) is vanilla in 26.x, but the mod's trade event (TradeWithVillagerEvent) is not.
4. That 'Fabric Loom (net.fabricmc.fabric-loom) + Gradle 9.4' builds this repo's three-module
   Gradle layout on JDK 25.
5. That Forge Config API Port (or whatever) supports 26.1.2.
6. The ten most loader-coupled files are the best seam test; read server/DebugWorldWatch,
   carts/HorseCarts, carts/client/CartsClient, client/ClientSetup first.
