Rename to Ixora's Horse Overhaul - implementation treatment

Scoped with the owner and probed (/probe-a-scope). Every "Decided" line is her call;
"Recommended" is the scoping session's pick, not yet her call; "Open" is unsettled;
"UNVERIFIED" is a fact this file has not proved - the building session checks it first.
Nothing here is built. This file is deleted, per /process-intake step 8, when it ships.
Written from the cloud session, which has no access to the owner's machine, the live
server or any old world; every claim about a world's contents is therefore UNVERIFIED.

What this is
============
A full rename: the shown name becomes "Ixora's Horse Overhaul", the mod id becomes
`ixoras_horses`, the Java packages and every resource/data namespace follow, and a
standalone converter moves old worlds across.
- Decided: full rename PLUS an offline world converter (not a shim, not display-only).
- Decided: new mod id `ixoras_horses`.
- Decided: it ships as a COMPAT release, 0.6.0 (hard rule 10). Its notes carry the
  "no longer back compatible with saves created under 0.5" stamp and link the converter.
  Compat release = the owner confirms the version number again at release time.
- Recommended: settle the naming at the same time - today "Horse Genetics", "Procedural
  Horse Genetics", `phc`, `PCH` and the repo name "Procedural-Horse-Coats" all appear.
  Open: the display name on each surface (jar file name, repo name, wiki title, README
  title, creative tab). The apostrophe cannot be in an id or a file name.

What the old id touches (counted by grep on 2026-10-03)
=======================================================
- com.example.horsegenetics Java packages: 1123 files, about 8400 mentions. Mechanical,
  no save impact. `com.example` is a placeholder group, so move it in the same sweep.
- assets/horsegenetics (about 1000 files in neoforge-26.1.2, 11 in common) and
  data/horsegenetics (428 files). Folder moves; no save impact; third-party packs break.
- About 500 string uses of "horsegenetics:" / "horsegenetics." in Java (registry ids,
  gene keys, translation keys). HorseGenetics.MOD_ID is the one constant.
- Gene keys inside every stored genotype code ("horsegenetics.extension=E/e"), in
  HorseRecord, carrots, splices, papers, deeds, stasis banks and realm backups.
- Runtime-generated ids: compat/GeneratedArmour, GeneratedCarts and GeneratedGates write
  datapack files and register ids under the namespace for other mods' materials. The
  same prefix rule covers them; the converter must not special-case them.
- The config and breed folder `phc/` (16 Java files).
- Wiki: 390 baked files in wiki/text plus the hand-written ports under wiki/gene-creator,
  wiki/horse-designer, wiki/breed-designer, web/src and wiki/tools. wiki/session-log is a
  dated record: Decided - leave it alone.
- 4 mixins and mixins config `horsegenetics.mixins.json`, neoforge.mods.toml (modId, the
  dependency tables are named `[[dependencies.horsegenetics]]`), gradle.properties
  (mod_id, mod_name, mod_group_id), Jade plugin id.

Why a world breaks without it
=============================
- The horse is vanilla minecraft:horse; genome, record, care and hunger ride as
  attachments keyed `horsegenetics:horse_record` etc. UNVERIFIED: that NeoForge 26.1.2
  silently drops an attachment key it no longer has, and that the next save then deletes
  it. Check in the SDK sources before trusting the refusal message's wording.
- Blocks, block entities, items (and their data components), carts, structures and
  the horse-realm dimension are stored by id or by namespace folder.
- Stored genotype codes keep the horse but reset every unreadable locus to its default
  (Genotype.readableStored), so a prefix mismatch would silently recolour every horse.

Piece 1 - the converter
=======================
Form
- Decided: a STANDALONE JAVA JAR, a new Gradle module (e.g. :converter), run by double
  click or one command. No third-party library: the JDK reads zlib and gzip; the NBT and
  region reader is written for this tool. Not Node, not inside the mod.
- Recommended: it lives outside common/ and neoforge-26.1.2/, so hard rules 1 and 2 are
  untouched. Add it to settings.gradle.kts and to procedures/rebake.txt only if it has
  derived files.
- Recommended: the old->new table has ONE entry (the prefix pair). Do not hand-list ids.

Rewrite rule
- Decided: rewrite EVERY id-shaped token, everywhere: any NBT string value or key, and
  any JSON file in the world, that contains "horsegenetics:" or "horsegenetics." ->
  the new prefix. This includes text players typed (book pages, signs, command blocks,
  custom names). Chosen for completeness: no field the mod stores can be missed.
- Recommended: write the old and new counts of rewritten tokens, per file kind, to a
  report. Open: whether the report also lists player-text hits (book / sign / command
  block, with coordinates). The owner did not take that option; default is a count only.
- Open: a token that appears in a longer unrelated word (e.g. "xhorsegenetics:"). The
  rewrite must anchor on a non-identifier character or string start. Recommended: anchor.

What it converts (all UNVERIFIED against 26.1.2 saves - none has been opened)
- region/*.mca, entities/*.mca and poi/*.mca: chunk palettes, block entities, entity
  NBT with attachments. UNVERIFIED: the compression types 26.1.2 writes (zlib, gzip,
  LZ4, uncompressed), whether oversized chunks spill to .mcc files, and whether the
  region format changed in this SDK. The converter must fail loudly on any it does not
  know, never skip a chunk.
- level.dat, playerdata/*.dat, data/*.dat (SavedData: HorseAncestryData,
  HorseEventData, StablePopulationData, RealmBackups, CartWorld), advancements/*.json,
  stats/*.json. UNVERIFIED: where 26.1.2 puts SavedData files, and whether they are
  still under data/<namespace>/.
- Folder renames: data/horsegenetics -> data/ixoras_horses, dimensions/horsegenetics ->
  dimensions/ixoras_horses. UNVERIFIED: the exact 26.1.2 layout of both.
- Nested NBT: horses stashed in stasis banks, realm backups and transfer deeds hold
  whole entity tags inside other tags; a generic walker covers them (the rewrite rule
  is not path-based, so no list of nested paths is needed).

Input and output
- Decided: it accepts every world that loads in 0.5.041 today. Older (pre-0.5.037)
  worlds are not promised; the converter does not add code for them. UNVERIFIED: that
  every such world loads in 0.5.041 - the converter's refusal for a world it cannot
  recognise must say so plainly rather than guess.
- Decided: output is a NEW FOLDER, original untouched: "MyWorld" -> "MyWorld (converted)".
  Needs free disk about equal to the world; the tool checks free space first and
  refuses rather than half-writing. No in-place mode.
- Recommended: it refuses to run if the output folder already exists, and never deletes
  anything. Open: a dry-run flag that only prints the report. Recommended: yes, cheap.

Packs
- Decided: the release notes tell datapack and resource-pack authors to change the
  namespace. The converter ALSO looks for packs and asks before converting them:
  datapacks inside the world folder (datapacks/), and any pack folder or zip the player
  points it at. It lists each pack that uses the old namespace and asks yes/no per pack.
  A converted pack is written next to the original, never over it.
- Open: resource packs live in the game folder, not the world. The converter can only
  see them if told a path. Recommended: an optional --packs argument, and the notes
  say so. Open: does it also rename pack asset/data folders (assets/horsegenetics ->
  assets/ixoras_horses)? Recommended: yes - that is the whole point of converting a pack.

Piece 2 - the mod side
======================
- Decided: on meeting an unconverted world (old-namespace folders present) the new mod
  REFUSES TO LOAD, with a message that names the converter. Nothing is lost.
  UNVERIFIED: that the folders can be detected before chunks load, on both a
  singleplayer open and a dedicated-server start, and that a refusal at that point is
  possible in NeoForge 26.1.2. Open: the one-time override flag was offered and not
  chosen - there is NO override.
- Open: a world that has no horsegenetics folders yet (vanilla world with the mod
  newly added) must still load. Recommended: detect by the presence of the old folders
  OR old keys in level.dat, never by absence of the new ones.
- Decided: the old gene prefix "horsegenetics." is still READ for the 0.6 series, and the
  new prefix is always written. After 0.6 starts a new compat series it goes. So pasted
  codes, saved designer links and custom phc/ files from before keep working through
  0.6.x. Lives in common/ (Genotype / Genes.byKeyOrNull); needs a test and the designer
  twin (hard rule 5).
- Decided: the `phc/` config and breed folder is RENAMED to match the new mod and its
  contents are auto-moved on first launch (breeds, genes, names, server.toml,
  breed-spawning.toml). Open: the new folder name. Recommended: `ixoras_horses/`.
  Open: what happens if both folders exist. Recommended: keep the new one, leave the
  old untouched, log a warning.
- Hard rule 5: the horse designer and CustomHorseSpawnScreen are one screen in two
  places; the gene-key prefix and the localStorage keys in wiki/horse-designer,
  wiki/gene-creator and wiki/breed-designer change in both.

Piece 3 - the proof and the cutover
===================================
- Decided: the converter is proven on a COPY of the live server world, made by the
  local session (which knows where that server is). This cloud session cannot reach
  it and does not try. Hard rule 12 applies to the local session too: never stop the
  live server by pattern or PID; copying a world that is running needs the owner's
  go-ahead for a quiet moment. Open: how the live world is copied while the server is
  running (stop it with tools/stop-dev-java.ps1, or copy a running world).
- Recommended: also generate a fixture world with the dev client holding one of every
  block, item and horse kind (stasis bank, hay portal, a realm horse, a cart, a splice,
  a transfer deed, a research paper). The owner was offered "both" and chose the live
  copy only; this is not decided - it is the cheapest way to cover kinds the live
  world may not hold. Open.
- Decided: THE LIVE CUTOVER IS A SEPARATE LATER STEP, run by the owner. The treatment
  produces a runbook (stop, back up, convert, start the new jar) and never touches
  the live server. It is not part of shipping 0.6.0.
- Done when: a converted copy of the live world loads in the new jar; every horse's
  genotype code, epigenome code, name and pedigree are identical after the prefix
  rewrite; the realm and stasis banks open; no "[genes] a saved horse carried" warning
  appears in the log; and the original world folder is byte-identical to before.

Risks nobody has met yet
========================
- The converter is the first code in this project that edits a player's world files.
  A bug in region handling can corrupt a world; the new-folder rule contains it.
- Chunk data a mod stores beyond ids (e.g. an UUID, a position) does not change; only
  the prefix does. UNVERIFIED that no stored value derives from the old id (a hash, a
  seed, a map key, a sort order). Grep for hashCode / ordering on the id before building.
- Registry ids sort and iterate differently under a new name (creative tab order, any
  id-ordered iteration in code). Check for id-ordered behaviour that a stored value
  depends on.
- Outside testers sit on the current tags: tell them before 0.6.0. A tagged number is
  never reused.
- Third-party mods that reference our ids (Jade plugin id at least) break.
- GitHub repo rename keeps redirects; CI, release links and the wiki's own links to
  the repo need a pass. Open: whether the repo is renamed at all.
- Performance: a large server world is gigabytes of region data. The converter streams
  region by region and never holds a world in memory. Open: a progress line and a
  resume after interruption. Recommended: progress line yes, resume no (re-run into a
  fresh folder).

Order
=====
1. Converter on a copy of the live world (the proof gates everything else).
2. Mod side: refuse-to-load, old-prefix read alias, config folder move.
3. The mechanical rename (packages, namespaces, wiki, tools), with every rebake in
   procedures/rebake.txt.
4. Release notes, upgrade guide, runbook; then the owner's cutover.
Re-running the converter on an already converted world must be a no-op, not an error.
