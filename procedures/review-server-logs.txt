PROCEDURE  : Review the server's log exports
COMMAND    : /review-server-logs
SAY        : "check the server logs", "review the PCH logs", "read the server logs",
             "what happened on the server"
RUNS       : local only (the exports are on the owner's machine)
TAKES      : the dated export folders written by the server's log exporter
LEAVES     : every new folder reviewed once; bugs and tuning requests filed as GitHub
             issues; new-feature wants filed as idea issues; a report; the
             reviewed-folders record updated; a zip of the reviewed folders in the archive
==============================================================================

WHEN TO USE
-----------
When the owner asks for the server's logs to be checked. Players on her server meet the
mod in ways no dev run does. These exports are the only record of what broke for them,
what they asked for in passing, and how their horses actually die.
This procedure says where to look and what counts as new. Recording what you find
follows the existing procedures: bugs through report-bug, and features as `idea` issues.

BEFORE YOU START
----------------
1. The paths are machine-specific, so they live in local memory, not here. The memory
   "pch-server-logs" names the export folder, the raw server logs folder, and THE RECORD
   of export folders already reviewed. The export path contains a space: quote it in
   every shell command.
2. The server belongs to someone else's session. Only ever READ these folders.
3. Know the export layout. Inside the export folder there is one dated folder per
   export (2026-10-01, 2026-10-02, ...). A second export on the same day gets -run2,
   -run3, and so on. For one date, the plain folder is earliest and each -runN is
   progressively later. Each folder holds:
     00-SUMMARY.txt                time window, counts, scope, limits. READ FIRST.
     01-errors-and-warnings.txt    horse-related ERROR/WARN, with stack traces
     02-player-chat.txt            every player chat line in the window, unfiltered
     03-player-activity.txt        joins, leaves, advancements
     04-equine-deaths.txt          named horse / donkey / mule death events
     05-compat-notes.txt           compatibility and back-compat findings, with evidence
     06-mod-versions.txt           which horsegenetics builds appeared in the window
     07-raw-horse-lines.txt        unfiltered horse-tagged lines, for grepping
   A file reading "(none in this window)" means nothing matched. It does not mean the
   export failed.

STEPS
-----
1. Work out what is new. The folders are normally incremental: each holds only what
   was new when it was written. But the exporter's watermark can be reset, and then a
   folder repeats everything since the first log. Its 00-SUMMARY.txt says so on the
   Watermark line ("first ever run - everything retained"), and its Window starts weeks
   back. 2026-10-03 was one. Read that line before anything else. In an overlapping
   folder, most findings are already filed: check each against the open AND closed
   issues before filing, and say in the report that the folder overlapped.
   a. List the dated folders.
   b. Skip every folder name already in the record.
   c. Take the rest in chronological order: by date, then plain, then -run2, -run3.
   If nothing is new, say so and stop.

2. For each new folder, in order:
   a. Read 00-SUMMARY.txt first: the window, the counts, and what was left out.
   b. Version context: 06-mod-versions.txt says which builds the window covers, so a
      regression can be tied to a release.
   c. Bugs: 01-errors-and-warnings.txt and 05-compat-notes.txt.
      - Trust the quoted evidence in 05. Do NOT trust its "SUGGESTION" text: that is
        generic advice attached to a pattern-matching rule, never checked against the
        mod's source. Verify every finding in the code before acting on it.
      - Separate the server operator's own scripts from the mod. An error from a
        server-side KubeJS script (names like horse_chunk_refresh.js or
        horse_wild_spawn_stamp.js) is the operator's code. Note it in the report, but
        never file it as a mod bug.
      - File each real mod bug following report-bug, steps 3 to 6: search for
        duplicates and earlier fixes, find the likely code, choose the labels and
        urgency, and write the issue. There is no reporter to ask questions, so skip
        its step 1. Write "Reported by: the server log export, folder <name>", and use
        06's builds as the version. Locally, use the gh CLI.
   d. Player wants and friction: 02-player-chat.txt. Players describe wants and
      annoyances in passing, and these are filed nowhere else. Sort each real one
      (owner's rule):
      - A NEW FEATURE -> a GitHub issue labelled feature (or enhancement, if it improves something already there), idea and from-server (#42,
        #69 are the model): the ask in a sentence, the Release/Open/Depends on/Owning
        page/Sized/Source lines, then your paraphrase of what the player
        wanted (never their words or name). Search open
        issues first and comment on a match instead of opening a second. It becomes a
        scoped feature only through write-intake-document, with the owner.
      - A BUG ("X is broken", "Y doesn't work") -> a GitHub issue labelled bug, as in
        step 2c.
      - A TUNING REQUEST ("too rare", "too slow", "dies too easily") -> a GitHub issue
        labelled tuning, plus needs-owner when it is a balance call. Say what the player
        found, the current value and where it lives, and 2-4 options.
      Either way, paraphrase: no player name and no quote.
      Players also talk to the server's own Claude in chat, and only their side is
      logged. When such a run of lines might be about the mod (eggs, horses, genes),
      read the raw log around it: the operator's command output ("Gave 1 [...]",
      "Malformed 'horsegenetics:...' component") is the other half of the conversation.
   e. How horses die: 04-equine-deaths.txt. Look for patterns, not single deaths: a
      cause that repeats, a place, a mob, a time. A pattern that is a defect becomes a
      bug issue. A pattern that is balance or AI becomes a tuning issue (with
      needs-owner and 2-4 options).
   f. 03-player-activity.txt and 07-raw-horse-lines.txt are context: grep them when a
      finding above needs more.
   g. Add the folder name to the record ONLY after the folder is finished, so an
      interrupted run retries it rather than silently skipping it.

3. If something is genuinely missing from the exports, the raw server logs folder
   (named in the memory) has more. debug-*.log.gz is not scanned by the exporter.
   Chunk-load traces are one thing only the raw logs hold. The server runs Cupboard,
   which logs "Trying to load chunk" with a stack trace each time something forces a
   synchronous chunk load. Tally the top frame of ours in each trace, over the plain
   logs AND the .log.gz ones (`zcat -f` reads both), and compare with any open issue
   waiting on that tally. Issue #13 was one; it is closed now, and its last comments
   name the sites that load chunks on purpose (TicketHandler.landingSpot, the stall fill
   under StallRecall, HorseRealm.safeReturn, arrival decoration, a glow light's old spot).
   A frame of ours at one of those is expected: report it, do not file it. Any other
   frame of ours is a new issue.
   Count only the logs from builds that carry the fix (each log names its jar near line
   178), and give the counts with their time range on the waiting issue.
   A trace is the Cupboard line, then a `java.lang.Exception: Chunk load debug` line, then
   the `at` frames. A counter that ends a trace at the first line that is not an `at`
   frame stops at that Exception line and counts zero everywhere. So run every counter
   on a CONTROL first, a log known to hold our frames (2026-10-02-1.log.gz holds 115:
   60 DebugPenManager.fastSet, 54 sweepPlot, 1 DebugWorldWatch.start). Never post a zero
   from a counter that has not reproduced the control.
   Raw logs rotate within a day: prev-nightly.log only reaches back to the last restart,
   and the dated .log.gz files do not cover every hour. Look for an export's events in
   debug-*.log.gz too: they carry every INFO/WARN line as well, and they sometimes hold
   a day that prev-nightly.log has already lost. Name the hours no log covers in
   every count you post, so a zero is not read as covering them.
   The operator's scripts can HIDE a mod defect. suffocation_rescue.js pulls a nearly
   dead horse out of a wall and logs "[suffrescue] moved horse <uuid>". Each line is a
   death that did not happen, so it never reaches 04-equine-deaths.txt, and the exporter
   does not tag it. Grep the raw logs for it (`zcat -f *.log.gz latest.log | grep
   suffrescue`) and add the count to issue #35, or to whatever replaced it.
   From 0.5.044 the mod logs its own "[clearance] <uuid> grew into blocks at x, y, z":
   a horse it moved out of a wall after growing. Count those beside the rescues, and pair
   them by UUID. A rescue with no clearance line before it for the same horse means
   something other than growth is putting horses in walls (#35's open question).
   THE MOD'S OWN LIVE-SERVER LINES all start "[phc-live] <topic> |" (server/FieldLog,
   always on, in builds after 0.5.046). Grep them first; they are written for this review:
     zcat -f debug-*.log.gz latest.log | grep -a 'phc-live'
   Topics, each tied to an open issue:
     in-blocks  #35. "SUFFOCATING <uuid> ... at x, y, z" is where a horse is being hurt by a
                wall: the burial spot the rescue line never gave, with its scale, the blocks
                its box touches and how long it has been loaded. "LOADED INSIDE BLOCKS" is a
                horse whose box collided ten ticks after it joined, so it was saved there.
                The "[clearance]" line now sits under this topic too. Pair all three with
                the [suffrescue] lines by UUID.
     lycan      #243, #244. SHIFT, REVERT and FORM DIED for every shifted horse. "WATER HURTS
                THIS FORM" marks a body like the strider; "horse SURVIVED" on a FORM DIED
                line is #244 happening.
     dealer     "SHORT STRING": a cowboy or dealer who founded with fewer horses than he
                wanted (seen with none, 2026-10-07).
     tables     #210. Row counts of the three whole-file tables at start, hourly and at stop.
   A topic goes when its issue closes; delete its row here in the same change.
   The exporter does not know these lines. Any mod line also carries the logger name
   "[horsegenetics/]", which is the way to separate ours from the other mods' in general.
   The exporter keeps only Horse, Donkey and Mule deaths. A shifted horse dies as another
   animal carrying its name, so grep the raw logs for `Named entity` and read every
   non-equine line whose name matches a horse death beside it (#243 was found this way).
   The raw logs usually run past the last export's window. Anything found there is
   still in scope: file it as usual, and say in "Reported by" that it came from the raw
   log, not from an export. A frame of ours that the fix never named is a new issue
   (#31 came this way), not a reason to keep the old one open.

4. Nothing to commit: issues are the output. (Update the reviewed-folders record in local
   memory as before.)
   Archive the folders you just reviewed: zip copies of them into the archive folder the
   memory names, outside the server, one zip per review. Leave the originals where
   they are (owner, 2026-10-05).

5. Report to the owner:
   - which folders were reviewed, and the window and builds they cover;
   - the bug and tuning issues filed or commented on, as links;
   - the new-feature wants filed as idea issues, as links;
   - the death patterns, and where each one went;
   - the operator-script errors (for whoever runs the server);
   - anything you could not tell from these logs.

DONE WHEN
---------
Every new folder has been reviewed and added to the record, each finding sits in its
place (an issue or the report), and the report is given.

NEVER
-----
- Never read, trust or modify the exporter's .state.json in the export folder. It is
  the exporter's own watermark, not a record of what was reviewed, and changing it
  corrupts future exports.
- Never write anything into the server's folders. Read only.
- Never put a player's name, a chat quote or anything a player said into the public
  repository or a GitHub issue. Paraphrase it.
- Never file a KubeJS script error as a mod bug.
- Never act on a 05 SUGGESTION without checking the code.
- Never conclude a command was not run because it is missing. The server does not log
  issued commands at all.
- Never treat these files as the server's whole health. Errors are filtered to ones that
  name a horse identifier, chat is only in-game chat (not Discord, not in person), and
  only this mod's footprint is captured.
