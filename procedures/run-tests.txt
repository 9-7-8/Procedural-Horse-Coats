PROCEDURE  : Run tests (the self-piloted yard loop)
COMMAND    : /run-tests
SAY        : "run tests", "run the yard", "test run", "check the yard"
RUNS       : local (it launches the game)
TAKES      : the test yard in the horse dimension, open Verification checks, open issues
LEAVES     : passed checks closed, new pens built, bugs filed as issues, small bugs fixed,
             the game running if pens are still timing, a report
==============================================================================

WHEN TO USE
-----------
When the owner says "run tests": run the whole verification loop, start to finish, with
no more input from her. She is the only person who can play the game, so the yard
exists to test without her. Its pens start themselves, run on a clock, and log their
own verdicts.
For one bug taken on deliberately, use fix-bug instead. To ask HER to test something by
hand, use hand-over-a-test.

BEFORE YOU START
----------------
1. `git pull`.
2. Read the last run before anything else: neoforge-26.1.2/run/logs/latest.log, plus
   the rolled <date>-1.log.gz if it ran past midnight (check `head -1 latest.log`: if it
   starts at 00:00, read both). Grep for "[trace] test yard", "CLOCKWORK", "[watch]",
   WARN and ERROR.
   Every FAIL and INCONCLUSIVE line in that run must be accounted for before anything
   else: it is either an open issue already, or it becomes one in step 6. Three checks
   failed on every launch from 2026-10-05 to 2026-10-08 with no issue, because each
   session set them aside as known. Check the rolled logs for how long a line has been
   failing, and whether it ever passed.

STEPS
-----
1. Survey.
   a. Read wiki/verification.html (generated) and the Verification tabs it points to.
   b. Read every open bug and tuning issue from anyone, testers included, except those
      waiting on the owner:
      `gh issue list --state open --search "label:bug,tuning -label:needs-owner" --limit 200`.
      Also scan unlabelled issues, and label any bug or tuning request you find.
   c. For each issue and check, decide whether a pen, a test or a small fix can settle
      it in this run, and fold those into steps 3, 4 and 7.
   d. Rank what can be wrong without anyone seeing it first, and visual checks last.

2. Close what passed.
   A yard PASS or a clockwork PASS closes the check it answers (owner's rule).
   a. Move the check off the page's Verification tab onto its Coding tab, with the date
      and the log line.
   b. Delete the pen.
   c. If the PASS proves a fix, close that issue too, with a comment quoting the PASS
      line and naming the fix commit.
   Judge each pen by its OWN question, written in its method's comment block, and not
   by the gene's Verified flag: a gene can be verified while a question about it is
   still open. INCONCLUSIVE and silent pens stay open. A night with no PASS line is
   evidence to record, not a closure.
   d. Audit every pen still standing, not only the ones that passed this run: list its
      checks (the pen's comment block) and find each on its page. A pen whose every
      question is already recorded as verified is deleted now, even if an earlier
      session closed the checks and left the pen. A pen that shares a class with one
      still open loses only its own half.
   e. Before a FAIL becomes a bug against the mod, rule out the pen. Read what the
      check actually compares. The yard is in the debug dimension, which cancels every
      block a survival player places, so a FakePlayer that places anything must be
      creative; and a pen's horses are rolled apart from the locus it fixes, so one can
      roll a disorder or a size that breaks the setup. A pen fault is still an issue
      (bug + found-in-yard), fixed in the pen.
   f. Read a PASS line's own numbers before closing on it. A verdict is only the pen's
      criterion, and a new pen's criterion can be too loose: AURA SILENT passed with its
      husks at 9.0 blocks against a control's 5.9, where the page asks for "exactly the
      control". When the numbers do not answer the page's question, leave the check
      open, write the reading under it, and tighten the pen.

3. Build new pens for open checks and issues a pen can answer unattended.
   A pen must start itself, run on a clock, and log its own PASS or FAIL (see the
   DebugTestYard javadoc, DebugWorldWatch, and DebugYardClockwork for anything that needs
   hands). A check that needs the owner's eyes or hands cannot be a pen: leave it where
   it is and list it in the report.

4. Re-aim the debug kit if what she would test by hand has changed (hand-over-a-test,
   "the kit").

5. Build and launch.
   Run the targeted --tests and `:neoforge-26.1.2:build`. Then launch into the yard
   detached, as launch-game describes, and confirm "all-day pens built" in a log
   newer than the launch. "Run tests" counts as permission to launch. If she is in a
   world, ask before closing it; the title screen may be closed without asking.
   - Add -PyardSprint=600000 to runClientTestWorld. The yard then runs its eight game
     hours in about three wall hours, and the short checks answer inside two minutes.
     A sprint has two artefacts that are not mod faults: block entities do not tick for
     roughly the first 180 sprinted ticks, and a "first poll" can land after the thing
     it meant to watch has already happened. Confirm either against an unsprinted run.
   - A ratio pen holds the client, and its memory, for thirty to sixty minutes even
     sprinted. Say so before launching, with the time it should answer. If the owner
     says stop: read the log, stop the client, and write each unanswered pen's tally
     under its open check as "not answered". A tally short of its verdict closes
     nothing.
   - The yard's world is new at every launch, so every pen runs on care days 0 and 1
     and at game tick 0. A reading that looks like the pen's artefact may be the mod
     treating day 0 or tick 0 as "never set" (#216 hid that way for six days).
   - When a pen needs a particular number on a horse's allele copy (a radius, a yield),
     write it after spawning instead of waiting for a founder to roll it, and read it
     back before judging (DebugYardGenes.horseWith, in git at 0bb188ca).
   - Wait for a verdict with a background `until grep -q ...; do sleep 2; done` (one
     notification when it exits). A foreground sleep is refused.
   - While the client runs, do not build (launch-game step 3). To check a change made
     meanwhile, type-check with javac off the live process's classpath; the four
     compile-only compat files (Jade, Waystones, FTB Teams, FadingGearMixin) error
     there and nothing else should. Build for real once the client is closed.
   - A fix whose proof is a pen needs the pen to hit the case. Sizes and other rolled
     traits differ between launches, so give the pen several horses of the extreme it
     needs, and say in the issue when a PASS could have been luck. Several launches
     running are proof where one is not.

6. Every bug found becomes a GitHub issue:
   `gh issue create --label bug --label found-in-yard`.
   The repository is public, so write plainly:
   - what failed;
   - the log evidence (exact lines, with the date);
   - the suspected code (file:line);
   - the owning wiki page.
   Search the existing issues first, and comment on a match rather than opening a
   duplicate. Then sort the bug:
   - SMALL (cause clear, fix obvious and local, no design / philosophy / save-format /
     balance call): open the issue anyway, for the audit trail, then fix it.
     a. Reference #N in the commit.
     b. Add a pen or test that proves the fix, then rebuild and relaunch under step 5.
     c. Leave the issue open until a PASS proves the fix. Close it at once only when a
        unit test proves it and no runtime question remains.
        Write "#N" in the commit message, never "fix #N" or "fixes #N": GitHub closes
        the issue on push at those words, before any pen has read the fix.
     d. A fix only her eyes can confirm stays open for her.
   - LARGE (needs her in any way): list the fix options in the issue, recommendation
     first, and add needs-owner. That label takes the issue out of every later run's
     survey, so never leave it off. When she has answered, remove the label and the
     next run picks the issue up.
   Testers' issues (no found-in-yard) follow the same split. Close a fixed one on
   proof, with the evidence and the commit.

7. Regenerate and push.
   Run the bakes from CLAUDE.md's table, at minimum:
   - bake-verification-index.mjs
   - bake-roadmap-index.mjs
   - build-search-index.mjs
   - check-links.mjs
   - bake-agent-text.mjs
   Commit and push. This is not end-session: leave the game running if pens are still
   timing.

8. Report in chat:
   - what closed, with its evidence;
   - the pens added and removed;
   - the issues opened and closed, as links;
   - what is still running, and when it should answer;
   - a short numbered list of what only she can check, with visual checks last.
   - pictures of anything a pen or a fix changed that can be seen, by
     photograph-horses.txt, "PICTURES FROM OTHER PROCEDURES", taken before the run's own launch or after it closes.

DONE WHEN
---------
Every PASS has closed its check and pen, every bug found has an issue, the small fixes
are pushed with their proof pending or in hand, and the report is given.

NEVER
-----
- Never poll a long pen with sleep. Say when it should answer.
- Never close a check on an INCONCLUSIVE or silent pen.
- Never leave needs-owner off a bug that needs her. If it was taken off so this run
  would read the issue, put it back once the run has tested what it could.
- Never put a bug on a Verification tab or in a feature issue (hard rule 9).
- Never launch a hidden, unfocused client without pauseOnLostFocus:false (launch-game).
