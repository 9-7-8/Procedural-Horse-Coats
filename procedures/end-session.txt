PROCEDURE  : End a session
COMMAND    : /end-session
SAY        : "end the session", "wrap up", "we're done for today", "end session"
RUNS       : local (it builds); a cloud session skips the build and process steps
TAKES      : a session's worth of work, finished or stopped at a clean point
LEAVES     : code and docs pushed as two commits, docs true, nothing left running
==============================================================================

WHEN TO USE
-----------
At the end of every working session, and as the last part of /process-intake, /fix-bug
and /release. The order is fixed. The docs pass comes AFTER the code is pushed, so it
describes where the session landed rather than narrating a change half-made.

BEFORE YOU START
----------------
Know which files the session touched: `git status --short` and `git diff --stat`.

STEPS
-----
1. Regenerate what the session invalidated, by the rebake procedure. It holds the table
   of what to re-run for what, and walks it row by row against the files that changed. If CustomHorseSpawnScreen or the horse designer changed, fix the
   other one too (hard rule 5).

2. Build green.
   Run `./gradlew :neoforge-26.1.2:build` and `node wiki/gene-creator/tools/check-parity.mjs`.
   If common/ or web/ moved, also run `node wiki/tools/check-designer-boots.mjs`. Do not
   pipe Gradle output to tail: that masks the exit code. Log to a file instead.
   A session that touched no Java, resource or Gradle file (wiki prose, intake/,
   procedures/ only) skips the Gradle build, since it cannot move it, and says so in the
   log. It still runs check-parity.
   Do not push red. If you truly must, say so in the commit message and file a GitHub
   issue for the failure.

3. Commit and push the code.
   a. Read `git status --short` first. If build or run output shows up, a .gitignore
      pattern is wrong: fix the pattern, never `git add` around it.
   b. Untracked files in intake/ are the owner queuing material. Commit around them.
   c. Work on main; do not branch. Cloud routines also push to main, so commit, THEN
      `git pull --rebase --autostash origin main`, then push. The tree is still dirty
      here whenever docs were written before this step (process-intake and fix-bug write
      them first), and a plain `--rebase` then refuses to run at all. A pull can still
      abort when upstream touched a file you edited (intake/To do.txt is the usual
      one), print that on a line a `| Select -Last 1` hides, and leave HEAD behind:
      the push is then rejected. Read the whole pull output.
   d. Write one descriptive commit that says what changed and why, not a file list.
      In PowerShell, write the message to a scratchpad file and `git commit -F <file>`:
      piping a here-string into `git commit -F -` is read as a pathspec, commits nothing,
      and the push after it reports "up to date".

4. Update the docs to what is true now, not to "what I changed today".
   Walk CLAUDE.md's page map and honour the source-of-truth rule. At minimum:
   a. Review the procedures against this session. Ask three questions:
      - Did a procedure followed this session say something wrong, stale or missing?
        Did a step fail, or get skipped because it did not fit, or did the owner correct
        how a routine was done? -> fix that procedure file now.
      - Was something done this session that is likely to be done again the same way,
        and has no procedure? -> write one by procedures/FORMAT.txt ("ADDING ONE": the
        file, its INDEX.txt row, the .claude/skills wrapper, the keyword memory). If it
        is too big to write now, add a bullet under "Routines to write up as
        procedures" in intake/To do.txt.
      - Does a change made this session (a new file, a renamed tool, a new rule) make
        another procedure's steps untrue? -> fix it. Grep procedures/ for the name.
      List what changed, for the session log. "None needed" is a valid answer, but only
      after asking all three questions.
   b. this session's own log, by procedures/write-session-log.txt: a NEW file with the
      time in its name, never appended to another session's file, plus its entry at the
      top of wiki/session-log.html;
   c. the Verification tab of each page the session built on: what is newly unplayed,
      and where to look. Delete only what the owner confirmed in game, or what an
      automated PASS answered. Then run bake-verification-index.mjs;
   d. any bug discovered goes in a GitHub issue (see report-bug), never on a page;
   e. any gene or system page the session moved;
   f. wiki/pages.js, if a page was added (hard rule 7);
   g. build-search-index.mjs, check-links.mjs and bake-agent-text.mjs, for any prose.

5. Audit CLAUDE.md with audit-claude-md: wc -l (at most 300), every line the session
   added run through the "every task?" test, dates and derived numbers moved out,
   routines moved to procedures, and every pointer checked.

6. Commit and push the docs as their own commit. Step 4 always leaves the tree dirty.

7. Verify clean: `git status --short` empty, and `git log origin/main..HEAD` empty.

8. Stop every process this session started - through tools/stop-dev-java.ps1 only.
   This covers Gradle daemons and workers, any runClient or runServer, and every
   background shell. Stop the game and server processes first, with
   `pwsh -File tools/stop-dev-java.ps1` (-WhatIf first; never Stop-Process, taskkill or kill, which
   a hook refuses - a pattern kill took the live server down on 2026-10-01), then
   `./gradlew --stop`: a daemon still running a build ignores the stop.
   Leave the owner's own terminals alone. If a client is up that you did not launch,
   ask before closing it (see launch-game).

9. Stop, with a short summary. Say what shipped, what is newly waiting in
   wiki/verification.html, which procedures step 4a changed or added, and the one thing
   the next session should pick up first.
   If main now holds enough to OFFER a release by release step 1 (a substantial batch,
   never a handful of fixes), ask the owner with the question tool and cut it only on a
   yes. Below the bar, say nothing about a release.
   Then stop: no new work, no "while I'm here" refactors.
   The LAST sentence of the summary is always exactly "Safe to clear." - whether the
   owner ran /end-session or another procedure (process-intake, fix-bug, release...)
   reached this step - once steps 7 and 8 hold. If something is left unpushed or running,
   say what instead and do not write it. (Owner, 2026-10-02.)

DONE WHEN
---------
- Both commits are on origin/main and the tree is clean.
- CLAUDE.md is 300 lines or fewer.
- No process this session started is still alive.
- The summary is given, ending "Safe to clear."

NEVER
-----
- Never run the full :common:test suite as part of this. It takes ten minutes or more,
  and the owner will not wait. Name in the summary what a full run would still check.
- Never commit a post-bake `git status` that only changed timestamps. `git diff` is
  the authority.
- Never leave doc changes unpushed. The owner reads the live wiki.
- Never close a Minecraft client the owner is playing in.
