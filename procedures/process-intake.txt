PROCEDURE  : Process intake
COMMAND    : /process-intake
SAY        : "process intake", "pick something from intake", "do the next intake item",
             "implement something from intake"
RUNS       : local (it builds and runs tests)
TAKES      : feature issues labelled scoped (an implementation treatment each)
LEAVES     : ONE unit built, written up on the wiki, its issue closed with evidence,
             pushed; the session ended
==============================================================================

WHEN TO USE
-----------
Use this to build the next new feature. New features are GitHub issues: an `idea`
until write-intake-document scopes it, then `scoped` (the treatment is the issue's body
and comments). Bugs are GitHub issues too and go through fix-bug instead.
One run builds ONE unit. Never start a second one in the same conversation. The owner
clears context and runs this again for the next one, because the next unit's classes,
pages and tests have nothing to do with this one's. The one exception is hers to make:
pieces of ONE treatment that share a screen and a test class may be one run if she says
so when asked (step 5). Then they are one commit and one session log.

This file is the routine, not the queue. Read the issue list fresh every run.

BEFORE YOU START
----------------
1. `git pull --ff-only origin main`; cloud routines push to main too.
   Read one issue first (mcp__github__issue_read, or the local way fix-bug reads
   them). If issues cannot be read, stop and say so: never fall back to files for a
   unit that is an issue.
   If the owner names a unit by number, read that issue.
2. `git status --short`. Untracked files in intake/ are the owner queuing material:
   commit around them, and never flag, add or delete them.
3. Run `node wiki/tools/check-roadmap-execution.mjs`.
4. Search the way look-it-up describes, for the whole run.

STEPS
-----
1. List the units.
   A unit is the smallest thing that ships alone: one open issue.
   - Query: open issues labelled `scoped`, and separately those labelled `procedure`,
     not `in-progress`, paginated 5-10 at a time (mcp__github__search_issues, e.g.
     `is:issue is:open label:scoped -label:in-progress`, then the same with
     `label:procedure`). Read the header lines of each body (Release, Open, Depends
     on, Owning page, Sized), never the whole treatment.
   - Size and impact are labels (size:S|M|L, impact:finishes|unblocks|new). Owner calls
     are the needs-owner label or an Open: line. Dependencies are the Depends on line.
   - A piece of a multi-piece treatment is a sub-issue of a `tracking` parent. A
     tracking parent is not a unit; its sub-issues are. An issue labelled
     `procedure` is a unit even while it is an `idea` (it is written by
     procedures/FORMAT.txt, not scoped). Every other `idea` is not a unit: scoping it is
     write-intake-document, not this. `survey` issues are evidence, never units.
   - A unit edited since its Sized: date (the issue's timeline shows it), or never
     sized, is re-sized: read its header and its "What already exists" section, then
     rewrite the labels and the Sized: line. If more than a handful need it, hand it
     to an Explore agent.
   These are not units, so leave them alone:
   - intake/README.txt;
   - potential-assets/. Use anything in it freely for the unit you are building:
     copy, crop, recolour or transform it, without asking. Log each use in that pack's
     USAGE.txt, add THIRD_PARTY_NOTICES.md on a pack's first use, and never put a
     whole pack in git or a release;
   - tools/ and any *-draft/ folder.
2. Throw out what is already done.
   For each unit you might pick, grep wiki/session-log/ and wiki/text/ for its
   keywords, and look for its classes in the code. Date the unit before deleting it.
   Get the date it was written (the issue's created and last-edited dates) and the date the matching work landed. A unit written after that work asks for more than was
   built, so it is still open.
   Also grep for the MECHANISM, not only the treatment's own words: a treatment can
   miss code already doing half of it under another name (the realm breeding pause was
   already HorseRealmRepro's offset clock, 2026-10-02). Then the unit is only the
   remainder, and any clash with what was built is an owner question for step 5.
   If a unit is already done, close it as in step 8 (completed, with the commit that
   did it) and say so in the session log. That closing is not this run's unit: carry on
   and pick one.

3. Score every remaining unit, as a table in your reply:
   - SIZE: S, M or L (the size: label).
       S = one screen or class, one test class, a few regenerate rows.
       M = one session: a new gene or system slice, several bakes.
       L = the treatment says it takes several sessions, or other units are waiting
           on it as a foundation (a new part kind, a shared base class, a sheet
           region, a structure bake, an entity type).
   - IMPACT, highest first:
       a. finishes something that has already shipped;
       b. unblocks other units;
       c. new content.
       A unit the owner flagged in her own words ("most important", "next") goes to
       the top of its tier. A unit she NAMES in the command's arguments is the pick; if a
       foundation it depends on has not shipped, ask once (question tool) whether to
       build the foundation first in this same run - two commits, one session log.
   - OWNER: can it be built without her? The answer is No if any of these is true:
       - it has an Open: line that is a design call;
       - it says "confirm with the owner";
       - it designs or redesigns a breed (see design-a-breed);
       - it touches wiki/philosophy.html.
       Art from potential-assets/ never needs her. UNVERIFIED lines need the source
       read, not the owner. "Recommended" lines may be taken as written.
   - DEPENDS ON: a unit that needs another unit's foundation cannot go first.

4. Pick, in this order:
   Tier 1 - small and high impact: size S, impact a or b. Owner questions are allowed
            only if they fit in one round (step 5).
   Tier 2 - anything you can do without her: size S or M, no owner design calls, and
            its dependencies have shipped.
   Tier 3 - the big ones: size L, or open design calls. Build its foundation or first
            slice only. If it is not on a wiki Roadmap tab yet, routing it there is
            part of the unit.
   Break ties by: unblocks the most units, then fewest regenerated artefacts, then
   oldest issue by creation date.
   Say in one line what you picked, its tier, and why the runner-up lost. Then claim
   it: add the in-progress label to the issue and comment "picked, tier, why" (the same
   line), before any code. Carry on without waiting, unless step 5 asks something.

5. Ask once, up front, or not at all.
   If the pick has owner calls, ask all of them in one question-tool round before any
   code: 2-4 concrete options each, with the treatment's Recommended line first. If she
   does not answer, or her answers open new questions, drop to the best Tier 2 unit and
   comment the unanswered questions on its issue, add needs-owner, release the claim
   (remove in-progress), and say so.
   Anything you decide without her goes in the session log under "Calls made without
   the owner", and on wiki/decisions.html if it is a design call.

6. Build it.
   - Before editing, write one sentence of hypothesis and one check that could disprove
     it. Run that check straight after the first edit. If the check needs NeoForge
     runtime state, write the exact manual reproduction on the owning page's
     Verification tab, rather than widening the search.
   - Resolve every UNVERIFIED line the unit relies on from the 26.1.2 sources or a
     gametest. Grep for every API or past case the treatment cites: treatments have
     named things that do not exist.
   - Read the owning wiki page, then only the classes the treatment names.
   - Shape: put the rules in common/, returning typed results, never chat text. The
     NeoForge side does config, chat, persistence, navigation and rendering.
     Gameplay config is server-authoritative. Extend the existing path rather than
     adding a second one beside it. Throttle a refusal reported to a player: once per
     meaningful attempt, never once per tick.
   - Follow hard rules 1-10. Rule 10 is the one a feature breaks without noticing:
     anything saved that the unit changes ships with its migration, and with a test
     that loads the old shape. If the spawn-egg screen or the designer is involved,
     change both (rule 5).
   - Comment on the issue as you go (full commentary, owner's choice): the hypothesis
     and its check, the check's result, what shipped, what is left. Questions for the
     owner still go through the question tool, never into the issue. Every commit says
     `Refs #N`, except the one that finishes the unit, which says `Closes #N`. Never put
     `Closes` on a commit that finishes only a piece of a unit, or one that names a
     tracking parent.
   - Run tests by name only (--tests '*XTest'), never the full suite. Break the new
     test on purpose once, to prove it can fail.
   - Run every rebake row the change touched.
   - If the unit turns out bigger than its score, ship the part that stands alone and
     put the rest back as its next piece (edit the issue body, or open a new sub-issue
     under the same parent). Do not widen the run.
   - A plan-only unit (Roadmap lines or a Roadmap-only page) has no test to break. Its
     hypothesis is that the plan is not written anywhere yet: grep wiki/*.html for its
     key words (wiki/text/ bakes no Roadmap tab). Grep the code for every fact a plan
     line states, so the plan does not describe machinery that does not exist.

7. Write it up on the wiki.
   - What shipped goes on the owning page's Gameplay and Coding tabs.
   - What nobody has seen in a game goes on its Verification tab.
   - What is still planned goes on its Roadmap tab. For a plan-only unit that is the
     whole write-up: nothing moves to Gameplay or Coding.
   - If the subject has no page, write one.

7b. Pictures. If the unit can be seen (a part, a gene, a breed, an item, a screen, a
    page), show the owner pictures of it by photograph-horses.txt, "PICTURES FROM OTHER
    PROCEDURES", and write what they showed on the Verification tab (a picture is
    never a pass). A plan-only or invisible unit says "no pictures" in the report.

8. Close it on evidence.
   Close the unit's issue as completed, never delete anything: the closed issue is the
   record, and its edit history and comments are the history the owner reads.
   - The finishing commit's `Closes #N` closes it on push to main. A cloud session on a
     branch closes it when the branch merges.
   - Remove the in-progress label. Comment the closing evidence: the commit, the
     release tag (or "unreleased, carried by the next tag"), the wiki anchor it now
     lives on, and what is newly waiting on a Verification tab. Assign the milestone of
     the release that carries it, if that milestone exists.
   - A piece of a multi-piece treatment -> close that sub-issue only. Closing the last
     sub-issue: close the tracking parent by hand, with a comment listing the pieces.
   - Not the last piece, and later pieces refer to it -> edit their bodies to point at
     the wiki anchor where it now lives.
   - An already-done unit found in step 2 is closed the same way, citing the commit.
   - Leave no strike-through or "done" edit in the body: the label and state say it.
9. End the session with end-session. A finished feature counts toward release step 1's
   bar; it does not cut a release by itself, and the owner decides. The issue's
   Release: line refines what counts:
   - "patch on the last piece", and this is not the last piece -> does not count yet;
   - "rides with <other>" -> does not count; it goes out with that one;
   - "compat bump" -> the release procedure confirms it with the owner before cutting;
   - "held until <release>" (the ports are "held until 1.0.0") -> does not count toward
     the offer bar until that release; it is built and closed normally, and the release
     it names carries it;
   - no Release: line (an older treatment) -> counts as one feature.

10. Write the session log by procedures/write-session-log.txt (a new timestamped file;
    end-session step 4b runs it). Under its sections, make sure it has:
    - the owner's request, quoted;
    - Done: the unit (issue number), the commit, what is green, and the issue closed;
    - Calls made without the owner;
    - Found on the way;
    - Tests run by name, and what a full :common:test run would still check;
    - Where to look first in game: the Verification tab anchors.

DONE WHEN
---------
The unit is pushed, written up and its issue closed, the session has ended cleanly, and you
have reported:
1. what shipped, and its tier;
2. what is newly waiting in wiki/verification.html, and the pictures from step 7b;
3. the next unit by this ranking, with its tier and any owner question it will need,
   so she can answer it before the next run.
Then stop. Do not start that next unit.

NEVER
-----
- Never build two units in one conversation, unless the owner said so for pieces of one
  treatment (WHEN TO USE).
- Never pick anything that needs the owner's live server.
- Never design a breed without her (design-a-breed).
- Never treat an UNVERIFIED line as true because the treatment sounds confident.
- Never start code before the in-progress label and the "picked" comment are on the
  issue: that is the only thing keeping a second session off the same unit.
- Never delete an issue, a comment or a label's history to retire a unit: close it.
