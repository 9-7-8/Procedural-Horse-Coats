PROCEDURE  : Create a new release
COMMAND    : /release
SAY        : "ship a release", "cut a release", "push a release", "release it",
             "new version", "tag it", "is it worth a release"
RUNS       : local only (the jar cannot build in the cloud sandbox)
TAKES      : a substantial batch of unreleased work on main, and the owner's yes
LEAVES     : every code test green, README.md brought up to date, photos of every new part
             committed under release-photos/v<new>/, a tag, a GitHub release with the jar
             and those photos in its note, the same note on wiki/releases.html, and a
             Discord post with the photos
==============================================================================

WHEN TO USE
-----------
Use this in two cases:
- when the owner asks for a release - cut it, whatever the size;
- when another procedure reaches its release step (process-intake, fix-bug, whats-next,
  end-session's summary). There it only decides whether to OFFER one (step 1).
A session never cuts a release on its own. Owner, 2026-10-01: "a single fixed bug, or
even two or three or five, is not enough for a release". The one exception is a
replacement for a release that is itself broken (step 10).
Real players install these jars: testers, and the owner's server. They cannot rebuild
from source or read the session log, so "builds green here" is not "playable there".
THE VERSION IS 0.<COMPAT>.<PATCH> (owner, 2026-10-01):
- PATCH, the third number: every ordinary release moves it, without asking WHICH number.
  WHETHER to release at all is the owner's call (step 1).
- COMPAT, the second number: a compatibility indicator. It moves only for a substantial
  new feature that cannot be made back-compatible with saves (CLAUDE.md hard rule 10).
  A release that moves it is the only kind that may break saves.
Releases are cut by hand, in a local session, with a jar and a server boot behind them.
A scheduled self-releasing job was tried once and retired by the owner.

BEFORE YOU START
----------------
1. `git fetch` FIRST. Cloud routines push to main while a local session works, and a
   release cut from a stale main is rejected at push time, after the tag has gone up.
   If main moved, read what landed and reconcile. Never force-push over it.
2. Read mod_version in gradle.properties and compare it with `git tag --sort=-creatordate`
   and `gh release list`. The working version is often already ahead of the last tag:
   if so, ship that number rather than bumping again.
3. List what is on main since the last tag: `git log --oneline v<last>..origin/main`.

STEPS
-----
1. If the owner did not ask for this release, decide whether to OFFER one. Never cut
   one unasked. Offer only when main holds a SUBSTANTIAL batch of player-facing work
   since the last tag:
   - roughly ten or more player-facing bug fixes; or
   - a substantial finished feature that changes how the game plays - not one small
     item, config option or tweak; or
   - a mix of the two that a player would call worth updating for.
   Five fixes is below the bar. Below it, say nothing about a release: the work waits.
   Crash and stuck-player fixes batch like the rest. The one exception is a replacement
   for a release that is itself broken: it goes at once, without asking, and its note
   says "replaces <version>".
   Docs, issue scoping, test-yard or debug-only work (debug tools are off in a real
   jar) and unfinished features do not count toward the bar.
   To offer: one AskUserQuestion naming what has piled up since the last tag, with
   "not yet" as an option. Cut only on a yes. On "not yet" or "hold" ("before you cut,
   implement X too"), hold, and do not offer again until substantially more has landed.

2. Decide which number moves.
   a. The patch number, in almost every case.
   b. The compat number ONLY when a substantial new feature truly cannot keep saves
      loading. Rule 10 asks for a migration first, so a compat bump means the migration
      was tried and cannot be written. Confirm with the owner in one question before
      cutting: it breaks every existing world on every server. Then the note leads with
      "no longer back compatible with saves created under 0.<old>", and the new series
      starts its own promise on wiki/releases.html#saves.
   c. Any change to a world players already have, in a patch release, must be a built and
      tested migration, never "the note will warn them".
   Ask the owner only what the history and this procedure do not answer, such as a
   title she may want to lead with. Say in the summary what was cut.

3. Run the RELEASE SET from test-tiers: every code test, cheapest first, and stop at the
   first red. After the full :common:test run, record its slowest classes in test-tiers'
   tier 3 (read common/build/test-results/test/*.xml), so tiers rest on measured times.
   This needs updating only when the list changes. That means every tier-0 node check, the full :common:test suite,
   :neoforge-26.1.2:test, :neoforge-26.1.2:runGameTest, every headless browser check,
   and a server boot to "Done (" run and grepped exactly as launch-game step 8 says
   (copy the owner's logs and configs aside first; grep the level markers, not a bare
   ERROR). Two warnings there are known and harmless: "<file>.toml is not correct.
   Correcting" for any phc/ settings file (server.toml, breed-spawning.toml) whose copy
   in run/phc/ predates keys added since - it fires even in a release that adds none -
   and the stasis_chamber recipe's "empty ingredients" (wiki/api-notes.html#recipe-empty-ingredients). A red result blocks the release until it is
   fixed or the owner waives it.
   Ask what a PLAYER hits that this machine does not: a brand-new world, a survival
   inventory, a horse in view, a client that never saw the previous format.

4. Set the number: 0.5.037 -> 0.5.038 for a patch, or 0.5.0xx -> 0.6.000 for a compat
   bump (the third field restarts at 000). A number is never reused, and never reissued
   with different bytes. Bump mod_version in
   gradle.properties only: neoforge.mods.toml interpolates it.

5. Write the release note by auditing the WHOLE range from the previous tag, never from
   what this session remembers building. One note covered a tenth of its range and had
   to be rewritten after testers had the jar. Run these against v<prev>..HEAD:
     git log --oneline v<prev>..HEAD                       (and --stat for the shape)
     git diff v<prev>..HEAD -- '*/lang/en_us.json'         (new items, blocks, keys, UI)
     git diff --name-status v<prev>..HEAD -- '*/data/horsegenetics/recipe/'
     git diff --name-status v<prev>..HEAD -- '*/src/main/java/**' | grep '^[AD]'
     git diff v<prev>..HEAD -- '*Config*.java' | grep -E '^\+.*(define|comment)'
   Hand the session-log read for the date range to a subagent, and have it mark each
   item player-facing or dev-only.
   Also list the feature and bug issues closed since the previous tag (search closed
   issues by date, or the release milestone) and cross-check them against the log: a
   closed feature with no commit in the range, or a commit with no issue, is a gap
   to read before you write the note.
   - Cut everything dev-only. debug.tools is off in a real jar.
   - A commit subject can describe code that does not exist. Run `git show --stat` on
     every commit you mention.
   House style:
   - a lede that names the range's breadth, then one section per subject;
   - "What this does to a world you already have": migrations that ran, removals,
     changed defaults, changed breed frequencies. Lead with a warning box when anything
     here could surprise a server owner;
   - "Not played yet" / "Known rough edges", pointing at wiki/verification.html and
     opening with the open GitHub bug issues;
   - when replacing a broken release, the "replace <version>" line, and whether saves
     made under it are damaged.

5b. Bring README.md up to date, BEFORE the build and the tag, so the README in the tagged
   commit describes the release. It is the page every new player sees first. Use the note
   you just wrote as the checklist:
   - plain player-facing language, as it is now: what a player can do, never genes-as-code,
     class names or how it is built (the wiki holds that);
   - every player-facing feature in the range is in "What you can do", in the same voice and
     one short paragraph each; fold a small one into a paragraph that exists;
   - nothing in it describes something unbuilt. Move a finished feature out of "Still being
     built"; never add a planned one to the body;
   - the numbered facts still hold: the Minecraft and loader lines, the install steps, the
     `phc` folder and settings files and their key names (grep the config classes), the
     "Your saves carry forward" baseline against wiki/releases.html#saves, and a new compat
     series if step 2b moved it;
   - links resolve (check-links.mjs covers wiki pages; look at the GitHub ones by eye).
   Commit it with the version bump (step 4) so the tag points at a README that is true.

5c. Photograph the new parts, BEFORE the build and the tag (owner, 2026-10-05: ship every
   release with photos of all the new parts, in the GitHub note and in the Discord post).
   a. List every NEW PART in the range that has a look: a gene or coat, a grown part, a
      breed, an item, a block, a screen. Use the step 5 audit as the checklist. Each gets at
      least one photo; a part that only changes behaviour has nothing to photograph and is
      named as "no photo" in the summary, not silently skipped.
   b. Run photograph-horses for horses and parts. Give a breed its own founder shot. For
      an item, block or screen, take an in-game screenshot the same way (DebugPhotoShoot
      has no item stage: extend it, or screenshot by hand with the owner's world closed
      per launch-game). Name files plainly: <subject>.png, e.g. back-sail.png.
   c. Look at every picture with Read. Retake any that is empty, mis-framed, or hides the
      part. Then CROP each one to the part that matters (owner, 2026-10-05: full-widescreen
      shots leave a lot of empty space at the sides). Crop to the subject's bounding box
      plus a modest margin - the whole horse, the whole part, the whole item - never so
      tight that the part's edge, a horn tip or a translucent fringe is cut. Prefer a
      portrait or squarish frame over widescreen. First try moving the camera in
      (stage()); crop only what that leaves. Crop a copy, never the file in run/. Find the
      box by detecting where the picture differs from the stage background, or by eye;
      do it with Pillow (a wheel sits in the repo root) or any image tool. Look at each
      cropped result with Read before it goes in. Do not scale a crop up past its
      native pixels. A diagram is never a photo: if a part cannot be photographed yet, say so in the
      note, do not draw one in its place.
   d. Copy the keepers from run/screenshots/ into release-photos/v<new>/ (one NEW folder
      per release; never reuse or overwrite an old one). Keep each file under about 1 MB:
      downscale a larger one. Commit the folder with the version bump (step 4)
      and push main BEFORE the release is created, so the note's image links resolve.
   e. In the GitHub note (step 5), embed each photo under its subject with
      ![<what it shows>](https://raw.githubusercontent.com/9-7-8/Procedural-Horse-Coats/main/release-photos/v<new>/<file>.png)
      Use the main path, not the tag path: the note is written before the tag exists.
      A short caption under each says what to look at.
   f. Write the Discord post as a file beside the photos,
      release-photos/v<new>/discord-post.md, in the format of the earlier posts (see
      intake/discord-command-whistle/): a "FOR THE DISCORD BOT" header, messages each under
      2000 characters, an "ATTACH: <file>" line per photo (Discord cannot show inline
      markdown images), Discord markdown only, no tables, and the release link. The bot or
      the owner posts it. A session cannot post to Discord: hand the owner the file and say
      so in the summary.

6. Build the jar from a CLEAN tree whose HEAD is the commit you will tag:
   `./gradlew :neoforge-26.1.2:build`. Open the jar to confirm its version and the new
   classes.

7. Tag and publish. FIRST `git fetch origin main` and look at `git log HEAD..origin/main`
   as its own step. If it lists anything, merge it (a merge commit), rebuild and stop to
   re-read the note, and only then tag. Never chain the fetch and the tag in one command:
   on 2026-10-03 a relicensing landed between the jar and the tag, the push of main was
   rejected, and the tag and release went up from a commit not yet on main.
     git tag -a v<new> -m "<title>"
     git push origin main --tags
     gh release create v<new> <jar> --title "<title>" --notes-file <note>
   Check the tagged commit with `git rev-list -n 1 v<new>`. `git rev-parse` returns
   the tag object, not the commit.

8a. Milestone. Create the milestone v<new> if it does not exist, assign it to every
   issue closed since the previous tag that has no milestone (features and bugs), and
   close it. This is what the owner reads as "what each release built".

8. Verify that the jar is downloadable: `gh release view v<new> --json assets`. Do not
   ask for an isLatest field: it does not exist, and the whole call fails. A pushed tag
   is not a release, because testers download from the release page.

9. Put the same note on wiki/releases.html as a new <h2 id="v0-5-0xx"> section, with the
   same photos (the same raw.githubusercontent links, or a relative path if the wiki ships
   them). Then
   run build-search-index.mjs, bake-agent-text.mjs and check-links.mjs, and commit and
   push.

10. If a release turns out broken: fix it, and ship the replacement at once. Retitle the
    broken one on GitHub as "superseded by <version>, do not use". Write in the new note
    what a world that ran the broken one needs.

DONE WHEN
---------
Either no release was offered (below the step 1 bar) or the owner declined or held it,
and the summary says which; or:
- the release set is green;
- `gh release view` lists the jar;
- the wiki note matches the GitHub note;
- README.md was reviewed against the range and is in the tagged commit;
- release-photos/v<new>/ holds a photo of every new part with a look, was pushed before
  the release was created, and the GitHub note, wiki note and Discord post all show them;
- release-photos/v<new>/discord-post.md exists and the owner has it;
- main and the tag are pushed, and the tree is clean.

NEVER
-----
- Never cut a release the owner did not ask for or say yes to, except a replacement for
  a broken one.
- Never offer a release below the step 1 bar: a handful of fixes is not one.
- Never cut a release the owner has said to hold.
- Never move the compat number for anything but a substantial feature that cannot keep
  saves loading, and never without confirming with the owner.
- Never reuse a version number, or reissue one with different bytes.
- Never skip the release set: the full suite runs before every release.
- Never publish a release note whose image links do not resolve: push the photos first.
- Never put a diagram or mock-up in a note as if it were a photo.
- Never commit photos from run/ to anything but release-photos/v<new>/.
- Never tag with a README that is out of date: it is the first thing a new player reads.
- Never stop at a pushed tag.
- Never write the note from memory instead of the tag range.
- Never release from the cloud.
- Never ship a patch release that breaks saves made under its series.
