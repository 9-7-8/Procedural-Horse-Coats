PROCEDURE  : Create a new release
COMMAND    : /release
SAY        : "ship a release", "cut a release", "push a release", "release it",
             "new version", "tag it", "is it worth a release"
RUNS       : local only (the jar cannot build in the cloud sandbox)
TAKES      : main with bug fixes or a new feature since the last tag
LEAVES     : every code test green, a tag, a GitHub release with the jar, and the same
             note on wiki/releases.html
==============================================================================

WHEN TO USE
-----------
Use this in three cases:
- when the owner asks for a release;
- when another procedure reaches its release step: process-intake, fix-bug, or
  end-session's summary;
- whenever main holds a bunch of bug fixes or a new feature that are not released yet.
Real players install these jars: testers, and the owner's server. They cannot rebuild
from source or read the session log, so "builds green here" is not "playable there".
THE VERSION IS 0.<COMPAT>.<PATCH> (owner, 2026-10-01):
- PATCH, the third number: a session may ALWAYS bump it, without asking. Do it whenever
  main holds a bunch of bug fixes or a new feature.
- COMPAT, the second number: a compatibility indicator. It moves only for a substantial
  new feature that cannot be made back-compatible with saves (CLAUDE.md hard rule 10).
  A release that moves it is the only kind that may break saves.
Releases are cut by hand, in a local session, with a jar and a server boot behind them.
A scheduled self-releasing job was tried once and retired by the owner.

BEFORE YOU START
----------------
1. `git fetch` FIRST. Cloud routines push to main while a local session works, and a
   release cut from a stale main is rejected at push time, after the tag has gone up.
   If main moved, read what landed and reconcile. Never force-push over it.
2. Read mod_version in gradle.properties and compare it with `git tag --sort=-creatordate`
   and `gh release list`. The working version is often already ahead of the last tag:
   if so, ship that number rather than bumping again.
3. List what is on main since the last tag: `git log --oneline v<last>..origin/main`.

STEPS
-----
1. Decide whether a release is due. Cut one, without asking, when main holds:
   - A NEW FEATURE, finished, that a player will notice. One is enough; size is no bar.
   - A BUNCH OF BUG FIXES. One fix is enough when it is a crash, a join-blocker, lost
     data or a stuck player on a released jar: players are waiting on those, and they
     have gone out within the hour of the report. A replacement for a broken release
     goes at once too, and its note says "replaces <version>".
   Docs, intake planning, test-yard or debug-only work (debug tools are off in a real
   jar) and unfinished features are NOT a reason on their own. They ride along with the
   next release.
   If the owner has said to hold a release ("before you cut, implement X too"), hold it.
   She often batches one more thing in.

2. Decide which number moves.
   a. The patch number, in almost every case.
   b. The compat number ONLY when a substantial new feature truly cannot keep saves
      loading. Rule 10 asks for a migration first, so a compat bump means the migration
      was tried and cannot be written. Confirm with the owner in one question before
      cutting: it breaks every existing world on every server. Then the note leads with
      "no longer back compatible with saves created under 0.<old>", and the new series
      starts its own promise on wiki/releases.html#saves.
   c. Any change to a world players already have, in a patch release, must be a built and
      tested migration, never "the note will warn them".
   Ask the owner only what the history and this procedure do not answer, such as a
   title she may want to lead with. Say in the summary what was cut, and why it was due.

3. Run the RELEASE SET from test-tiers: every code test, cheapest first, and stop at the
   first red. That means every tier-0 node check, the full :common:test suite,
   :neoforge-26.1.2:test, :neoforge-26.1.2:runGameTest, every headless browser check,
   and a server boot to "Done (" with the log grepped for
   'ERROR|Couldn.t parse|Invalid|missing'. A red result blocks the release until it is
   fixed or the owner waives it.
   Ask what a PLAYER hits that this machine does not: a brand-new world, a survival
   inventory, a horse in view, a client that never saw the previous format.

4. Set the number: 0.5.037 -> 0.5.038 for a patch, or 0.5.0xx -> 0.6.000 for a compat
   bump (the third field restarts at 000). A number is never reused, and never reissued
   with different bytes. Bump mod_version in
   gradle.properties only: neoforge.mods.toml interpolates it.

5. Write the release note by auditing the WHOLE range from the previous tag, never from
   what this session remembers building. One note covered a tenth of its range and had
   to be rewritten after testers had the jar. Run these against v<prev>..HEAD:
     git log --oneline v<prev>..HEAD                       (and --stat for the shape)
     git diff v<prev>..HEAD -- '*/lang/en_us.json'         (new items, blocks, keys, UI)
     git diff --name-status v<prev>..HEAD -- '*/data/horsegenetics/recipe/'
     git diff --name-status v<prev>..HEAD -- '*/src/main/java/**' | grep '^[AD]'
     git diff v<prev>..HEAD -- '*Config*.java' | grep -E '^\+.*(define|comment)'
   Hand the session-log read for the date range to a subagent, and have it mark each
   item player-facing or dev-only.
   - Cut everything dev-only. debug.tools is off in a real jar.
   - A commit subject can describe code that does not exist. Run `git show --stat` on
     every commit you mention.
   House style:
   - a lede that names the range's breadth, then one section per subject;
   - "What this does to a world you already have": migrations that ran, removals,
     changed defaults, changed breed frequencies. Lead with a warning box when anything
     here could surprise a server owner;
   - "Not played yet" / "Known rough edges", pointing at wiki/verification.html and
     opening with the open GitHub bug issues;
   - when replacing a broken release, the "replace <version>" line, and whether saves
     made under it are damaged.

6. Build the jar from a CLEAN tree whose HEAD is the commit you will tag:
   `./gradlew :neoforge-26.1.2:build`. Open the jar to confirm its version and the new
   classes.

7. Tag and publish:
     git tag -a v<new> -m "<title>"
     git push origin main --tags
     gh release create v<new> <jar> --title "<title>" --notes-file <note>
   Check the tagged commit with `git rev-list -n 1 v<new>`. `git rev-parse` returns
   the tag object, not the commit.

8. Verify that the jar is downloadable: `gh release view v<new> --json assets`. Do not
   ask for an isLatest field: it does not exist, and the whole call fails. A pushed tag
   is not a release, because testers download from the release page.

9. Put the same note on wiki/releases.html as a new <h2 id="v0-5-0xx"> section. Then
   run build-search-index.mjs and check-links.mjs, and commit and push.

10. If a release turns out broken: fix it, and ship the replacement at once. Retitle the
    broken one on GitHub as "superseded by <version>, do not use". Write in the new note
    what a world that ran the broken one needs.

DONE WHEN
---------
Either the release was not due (or the owner held it), and the summary says why; or:
- the release set is green;
- `gh release view` lists the jar;
- the wiki note matches the GitHub note;
- main and the tag are pushed, and the tree is clean.

NEVER
-----
- Never cut a release the owner has said to hold.
- Never move the compat number for anything but a substantial feature that cannot keep
  saves loading, and never without confirming with the owner.
- Never reuse a version number, or reissue one with different bytes.
- Never skip the release set: the full suite runs before every release.
- Never stop at a pushed tag.
- Never write the note from memory instead of the tag range.
- Never release from the cloud.
- Never ship a patch release that breaks saves made under its series.
