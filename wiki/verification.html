Open checks

Every page of this wiki that has an open check, alphabetically, in the one sentence each of those pages says about itself. Checks may be runtime, defect, design, documentation or compatibility work. The checklists themselves are not here — each lives on a Verification tab of the page for the thing it concerns.

Nothing on this page is written by hand

node wiki/tools/bake-verification-index.mjs scans every page in wiki/ for a Verification tab and harvests the one-sentence summary box each of them opens with. A page joins this list by growing that tab, and leaves it by losing it — the same way a gene is on the census by existing. The counts beside each row are the panel's own checklist tally, computed at bake time, so a list that shrinks says so without anybody editing this page.

So a checklist is written where the thing is documented. Add a panel to the page, re-run the bake, and the row appears:

wiki/<the thing>.html, last panel in article.doc
<section id="verification" class="tab-panel" data-tab="verification"
         data-tab-label="Verification"
         data-tab-hint="Open checks">

<div class="note verify-summary">
    <span class="label">What needs verifying here</span>
    <p>One sentence saying what is built and unconfirmed.</p>
</div>
...
</section>

The bake refuses to write rather than produce a wrong index: a verification tab with no summary box, two of either, or a summary box loose on a page all fail it by name. An index that quietly omits a page is worse than no index.

Nothing is ever hand-written onto this page. Not a checklist, not an exception, not “just this one, it spans several pages”. If a check has no page to live on, that is a missing page, not a reason to write it here. Everything between the markers below is harvested; everything above them is this page's own standing rules.

An open check MOVES when it is resolved, it is not ticked. It comes off the Verification tab and onto the Coding or Gameplay tab of the same page, written as what became true, when, and on what evidence. A page whose last check is resolved loses the tab and drops off this index by itself. Work not started at all belongs on the roadmap.

How every checklist is ordered: "does it look right" goes LAST

Owner's rule, 2026-09-13. Rank every open test by whether it can be wrong invisibly. A gene that paints wrongly announces itself the moment anybody looks at it. A gene that behaves wrongly, damages a save, costs tick time, or silently does nothing does not — and that is what her time in the game is worth spending on.

The tell is that six visual confirmations were cleared in about twenty minutes on the day this rule was written, while the holy ward needed a warded chamber and an unwarded control thirty blocks from where she stood, the weather loci needed an attribute readout built first, and the lava speed needed a log line before anyone could tell a dead feature from a slow one. Cheap checks should not occupy the top of a list that exists to spend the scarcest thing in the project.

So: behavioural, structural and unattended tests first; "look at it and say" last, and retired outright the moment it is confirmed.

The test kit

Spawn Test Horse World (DebugTestWorldHandler.fillInventory) hands out one hotbar at a time: themed batches covering the work indexed below, a batch deleted once worked through, batch 1 on login. Behaviour first (owner, 2026-09-11: test “stuff that isn't just does this look pretty in-game”) - batches 1 and 2 rank what fails badly rather than visibly, and most of batch 1 is left running rather than watched and the rest with /testkit n (/testkit alone lists them; each batch's legend ends with a clickable link to the next). Swapping a batch empties the hotbar only. Its preset eggs carry a genotype and no epigenome, so every horse from one egg rolls its own numbers - knob-placed marks land somewhere new each time. Every batch that tames carries a stick, every one that breeds carries golden carrots. Two clickable /tps on login go to the nearest plains village and dark forest. Four of those tests need files the kit cannot make, so the dev run's run/phc/ was prepared for them on 2026-09-11 and a dedicated server confirmed all four load: breeds/kit_forest_paint.json (chestnut paints, dark forest), kit_night_cremello.json (dark forest, night only), kit_broken_gene.json (logs a missing-gene warning, loads anyway), kit_zz_duplicate_friesian.json (refused); genes/aurora.json (the example gene, “1 dropped in”); and breed-spawning.toml with the Friesian moved to dark forest only and the Morgan switched off. Delete them to put the dev run back. Those six files are in the repo now, at neoforge-26.1.2/tools/testkit/ — whose README.txt is also the one-page answer to “how do I start testing”: the button, the /testkit commands, the fixed plains seed and the two things that waste an hour (rebuilding under a live client; runServer while the client holds run/). It has a note saying how to put the drop-ins back — they had only ever existed in the .gitignored run/phc/, which is to say on one laptop, so a fresh clone could not reproduce any of the four checks.
