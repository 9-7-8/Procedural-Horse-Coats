Project / how to turn plans into small shippable slices

Roadmap execution

The roadmap says what is not built. This page says how to choose the next slice without making a later session rediscover the dependencies, decisions and checks. It is an execution guide, not a second backlog: the owning page remains the source of truth for each feature.

Route every request first

Before implementation, give each request one owner and one state. There are two queues, and each has its own routine. Something built but wrong is a bug: it is a GitHub issue labelled bug. The cloud session files it by procedures/report-bug.txt (/report-bug), the yard's “run tests” routine files what it finds, and /fix-bug fixes one issue per session. Something not built yet is a feature: it is scoped into an implementation treatment in intake/ by procedures/write-intake-document.txt, and /process-intake builds one piece of it per session. intake/ holds features only, never bugs. A question whose answer changes the design belongs in Design decisions. Something built but unseen belongs on the owning page’s Verification tab. A plan with an agreed shape that nobody is building yet belongs on that page’s Roadmap tab.

Open-gap routing audit

Known gaps is no longer a backlog. Every record on it has moved to the page it belongs to, and the page is kept only so old #gap-N links still resolve. There is nothing left to route from it. Open work now lives in three places: bugs in GitHub issues, unseen behaviour on each page’s Verification tab (collected on Open checks), and plans in intake/ treatments and on Roadmap tabs (collected on the roadmap).

check-roadmap-execution.mjs still fails if a record on Known gaps is marked Open and is not linked from this section. That is the guard against the page quietly becoming a backlog again. If it fires, move the record to its page, or file it as an issue if it is a bug. Do not list it here.

What is left of the fix pass

This section was the order for clearing the defects reported up to 2026-09-24. Most of it has shipped since, and is unplayed rather than unbuilt. New defects no longer join this list: they are GitHub issues, ranked and taken one at a time by /fix-bug. What is written here is what remains of the original six stages. Each one is still worth doing before new content on the same code, because a defect hidden inside a new system is harder to find.

1. Persistent identity and record retrieval - not built

A browser listing, a live entity, a client record and an ancestry record must all resolve to the same horse UUID. There is still no server request for a record by UUID: HorseRecordSyncPayload is keyed by entity id. HorseInfoScreen still opens an unrelated horse through FamilyTreeRequestPayload, and the roster is capped at HorseRosterPayload.MAX_ENTRIES. server/HorseRoster scans the ancestry table, because there is no registry (gate 1). The required hardening matrix

Whatever stage or issue is being worked, it is incomplete until its tests pass across these states:

  • loaded and unloaded;
  • tracked and untracked;
  • alive, dead and sold;
  • owned, transferred and unowned;
  • owner online and offline;
  • one horse and many horses;
  • success and refusal;
  • menu open and menu closed;
  • save and reload between actions;
  • singleplayer and dedicated server.

Use the same matrix for the H menu, the info screen, breeding, notifications and equipment, rather than inventing a partial checklist for each.

New-content vertical slices in dependency order

These are the recommended clusters. Each slice should cross the relevant common model, server behaviour, client surface and tests when those layers apply. Do not build a large foundation without one player-visible proof using it. New features arrive as intake/ treatments and are built by /process-intake. The clusters below are where those pieces land.

Foundations and decision gates

Several roadmap pages are not good starting points because their shared foundation is still unsettled. Resolve these in order:

  1. Owned-horse registry before browser actions, historical rows, notifications or teleport.
  2. Gear attachment and render contract - partly settled. The worn-gear attachment, the Dress window and the gene part layer (horn, ram horns, antlers) are proven. The worn-side hook, which lets a gear item draw through the part layer, is still needed before shoes, wings or pads.
  3. Trait/effect shape before storm-fed, magic-grab and other long-lived per-horse abilities.
  4. Cart bench components before multi-horse draught, because the latter changes the vehicle shape rather than adding a new vehicle.
  5. Undead gene decision - settled (the breed sets the bundle): undeath is the visible locus, and the breed pins diet, temper and stats.

A gate is finished only when its answer is written on the decision page or the owning page, and the losing alternatives are removed from the implementation plan. Otherwise the next session will spend its first hour reopening the same question.

The execution loop

  1. Choose one slice. Name the player-visible outcome and its owning page.
  2. Read the gate. Check decisions, the open GitHub issues on the same code, and nearby Verification items before touching code.
  3. Find the narrowest owner. Put rules in common/ when they are game-free; keep NeoForge as translation and orchestration.
  4. Make the smallest end-to-end edit. Prefer one real item, one query, one notification or one behaviour over an empty framework.
  5. Run the cheapest falsifying check immediately. Use a focused test, fixture, parity check or narrow build before expanding the slice.
  6. Regenerate every derived artefact. Follow the build table, especially golden coats, WASM, generated wiki pages and search indexes.
  7. Update the owning page. Move shipped work off Roadmap, record what was seen on Coding, and leave only genuinely unbuilt work behind.
  8. Stop at a clean boundary. Record the next blocked gate and the one best next check in the session log.

The slice brief

Before implementation, write this compact brief on the owning page or in the session notes:

Outcome: one sentence a player can observe.
Owner: one wiki page and one primary code owner.
Decision gate: the answer that must already be settled.
Prerequisites: existing data, attachment, payload or UI contract.
First proof: the smallest complete path from input to visible result.
Acceptance: observable pass conditions, including refusal and failure cases.
Checks: the cheapest focused test, then required regeneration commands.
Out of scope: adjacent ideas deliberately left for a later slice.
Roadmap — plans by owning page Design decisions Open checks Session log
The next session should be able to begin from the slice brief, run its first focused check, and know which page to update when the work ships.
