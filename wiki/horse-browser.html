The horse browser

The horse browser is the mod’s own index of everything you own and everything it knows — an H-key screen carrying a list of your horses, a searchable gene database, the recipes, the alleles, the breeds and a breeding preview. Part of it ships. This page is, for now, only the plan: the half that exists is written up on Breeding & pedigree, under client sync, the information screen and the family tree.

The horse browser

The H-key screen is a real container menu; the horse list and the gene database are built. The full plan is six tabs, and what is left is the vial inventory, the herd view, the bonding view, the generated crafting tree and an event Log tab, plus out-of-band actions (teleport a horse to a stall, whistle for bonded horses, recall to a holding pen).

The owned-horse index is still owed, and the horse list is running without it

The expensive part was never the UI. A proper per-player owned-horse registry — updated on tame, breed, death and transfer, holding enough denormalised data (name, sex, age, genotype, bond, herd) that horses in unloaded chunks still appear — does not exist. The My horses tab ships on HorseRoster instead, which walks the whole ancestry table on request, cuts the result at HorseRosterPayload.MAX_ENTRIES and sends it, and the client sorts and filters what it got. What is owed is the registry, with sort and filter running server-side over it, and pagination. HorseQuery is already game-free, so the same predicate can run on the server the day the index exists.

The tab the owner has asked for

The bonding tab. The bond level with each horse, the tier it is at, and concrete guidance on how to raise it — which sources are available, what the daily cap is, how close the next tier is. This is the surface bond is missing. My horses shows the number and sorts by it, which is not the same thing: it says where you are and not how to move.

The Log tab

The Log tab is a chronological, newest-first history of the player’s horse events: every successful or failed cover, birth, death, taming, purchase, sale, transfer and other ownership-changing action. It is a record of events, not a second horse roster, so each row carries the event time, event type, horse identity and the useful reason or result.

  • Server-backed history. Record events where the authoritative action happens, keep them across unloaded chunks and reconnects, and send a bounded page or delta to the client. A client-only list would miss natural covers, deaths and purchases that happen while the menu is closed.
  • One filter model. Filter by event type (coverage, birth, death, taming, purchase, sale, transfer and future event kinds), with an All option and newest-first ordering preserved after filtering. Failed covers must retain their refusal reason. That vocabulary already exists: CoverNotice.Reason (the chat line) is the set of refusals a natural cover can end in, and the Log tab’s rows should be those same constants rather than a second list of strings that can drift from them.
  • Registry prerequisite. The event record should reference the same horse identity and ownership state as the owned-horse registry, so sold or dead horses remain understandable instead of becoming anonymous log rows.

Tabs that keep working as the menu grows

The H menu needs a horizontal scroll bar for its tab strip. The selected tab must remain visible while scrolling, keyboard focus must move through only visible tab buttons, and the scroll position must not change the server-side menu state. This is layout infrastructure, so build it before adding more tabs such as Log, rather than solving overflow separately on each new screen.

The rest

  • A row should open the horse. Clicking a My horses row selects it and fills the footer; it should reach the information screen and the family tree. Both want a HorseRecord and the roster deliberately does not carry one (it carries a HorseListing, a tenth of the bytes), so this needs a fetch-one-record round trip.
  • FamilyTreeScreen should become a tab rather than stay a separate screen. Row portraits exist — client/HorsePortrait, used by the My horses table and both breeding pickers — but they are a second copy of the tree's drawHorseModel rather than a shared one (gap 78), and merging them is part of this. It is also the working reference for a from-scratch retained-mode screen in this codebase, scissor clipping and entity draw included — with the standing warning: build the render state from a throwaway client-only Horse, and never touch ClientCoatCache.
  • The crafting-tree tab goes stale on contact with a modded gene. Generate it from the recipe manager at runtime; do not hard-code the graph.
  • Teleport, recall and whistle need the stall and pen definitions above, plus answers for a destination that no longer exists and for whether any of it crosses dimensions.
  • A natural / magical filter on the Breeds tab. Breed.magical() is already on every breed, so the filter is a toggle beside the list and a clause in HorseBrowserScreen.drawBreedList. Build it with the first magical breed, so it can be seen doing something.

The horse menu — acting on a horse, not only reading about one

The browser's remaining tabs are a separate and larger job; this is the smaller, sharper set of asks about the screen as it stands. The thread running through all of them: the menu is a report today, and every one of these turns it into a console.

Teleport the horse to you, from the Where column

The column exists and is inert. “Where” is the twelfth column on My horses and already prints overworld 118, 71, -204, built server-side by HorseRoster.where. Clicking it should attempt to bring the horse to you.

  • “Use /tp” was the ask, and the mechanism deserves a second look rather than a literal reading. The mod already teleports horses properly — the ender whistle moves a bound horse across dimensions, and tickets send one to a stall. Routing the button through the same code is better than issuing a command: a command needs permissions the player may not have, silently does nothing for them if they do not, and skips every check the whistle makes.
  • It must answer the unloaded case, which is most rows. HorseRoster.entry() only fills Where for a horse in a loaded chunk; everything else reads not loaded, and those are exactly the horses you would want to summon. data/HorseWhereabouts already exists as a SavedData of last-seen dimension, position and death, and the roster does not read it — wiring that in is the prerequisite and improves the column whether or not the button is built.
  • It needs a cost or a gate. A free summon-any-horse-from-anywhere button makes whistles, tickets and holding pens redundant in one stroke. Whatever gates it — a bond tier, a cooldown, an item — should be decided before the button, not retrofitted after players have it.

A waypoint column, when a map mod is running

A checkbox per horse that drops a waypoint on the player's minimap and refreshes it every thirty seconds.

Nothing in the repo touches any map mod today — no Xaero, no JourneyMap, no waypoint code of any kind — so this is a new integration from zero, and it is the one item here with a third-party API at the end of it. Two things to settle first: which map mods (their waypoint APIs are unrelated to each other, so each is its own integration and the column should appear per-mod rather than as one checkbox), and where the thirty-second refresh runs, since it has to keep updating while the screen is closed and therefore cannot live in the screen. The fail-soft rule applies as everywhere else: absent map mod, absent column, no crash and no hard dependency.

Refresh on its own

Asked for on three events — screen opened, a foal born, a horse died. Today there is a Refresh button and a lazy first fetch: HorseBrowserScreen.init() requests the roster only if the client has never received one, and HorseRoster.sendTo has exactly one caller, the payload handler. So a player who breeds a horse and opens the menu sees the world as it was when they last pressed a button.

  • On open is trivial — drop the !received() guard, at the cost of a round-trip every time the screen opens.
  • Birth and death are pushes, not pulls, and that is the actual work. The server has to notice and send, which means a hook in the foaling and death paths and a payload that says what changed. Re-sending the whole roster on every birth in a big stable is the version to avoid; ClientHorseRoster is already a UUID-keyed cache with a version counter, so it is built for a delta rather than a replacement.
  • Transfer and taming belong on the same list, even though they were not asked for — they change the roster for exactly the same reason, and adding them later means touching the same code twice.

RideHUD, and stats while you ride

Wanted integrated rather than assessed. The mod has one GUI overlay today — client/FlightHudLayer, a single line above the hotbar naming the dismount key while flying, and itself unverified at runtime — plus JumpBarCooldownMixin, which tints a vanilla bar. There is no stats readout anywhere outside a screen you have to open.

That makes this the first real HUD in the mod, and the design question is restraint rather than capability: every number already exists on HorseInfoScreen, and the reason to show speed, jump, health and bond while riding is that opening a screen mid-gallop is not a thing anyone does. Keep it to what changes while you ride.

Leave My Bars Alone was read, and the call was to fold it in here rather than rebuild it

Leave My Bars Alone (Fuzs, MPL-2.0) does exactly two things, and it was read from source on 2026-09-21 because it is one of the very few mods on this page with a branch targeting our own Minecraft version. It re-adds the food bar as an extra stacked GUI layer anchored to VEHICLE_HEALTH — it does not move the mount's health bar — and it narrows when vanilla is allowed to swap the XP bar for the jump-charge bar, via one @ModifyVariable into nextContextualInfoState, so XP stays visible unless you are actually mid-charge. Two config booleans, both default on, no keybind, two files in the whole mod.

The owner's call was not to rebuild either half. We do not touch vanilla bars separately; instead this section is designed so that our readout does not add to the clutter in the first place, and the vanilla bar problem stays solved by a maintained mod that already solves it. One thing to check when this is built: JumpBarCooldownMixin already modifies the same vanilla jump bar, so the two want testing together before either is claimed to work.

A different look for the menu — explicitly not committed

The owner likes Biology Dictionary's UI and raised it as “maybe as an option or alternative style”, with “not a requirement, not committed to” said outright. Recorded here so the idea survives, and flagged so nobody builds it as a decision that was made. Worth knowing what it would cost before anyone is tempted: HorseBrowserScreen is a single 3,430-line Screen with its layout inline, so a second skin means extracting a layout seam first — which is real work with no user-visible result, and is the kind of thing that only pays if the restyle is actually wanted.
