Horse stasis: chambers and the bank

A cheap way to hold horses without them costing server tick time. A stasis chamber is a single-use item that a horse goes into; a Horse Stasis Bank is a block that holds many chambers and gives them a browsable UI. The whole point is the cheapest tier, so a server with hundreds of horses can put most of them somewhere that costs nothing, instead of every horse being a real, ticking entity forever. None of it is built. This page was taken whole from the repo's intake to-do list.

Nothing on this page exists in the game

Everything below is a plan, written up here rather than left in the intake file so it gets a Verification and a Roadmap tab like everything else once work starts. When a piece of this ships, it comes off the Roadmap tab and is written up on a Gameplay and a Coding tab here instead.

What is still planned here

Four tiers of stasis-chamber item (Basic through Spacer, each the last plus one ingredient), a Horse Stasis Bank block with a two-tab menu to store and browse them, an Emergency Horse Stasis Chamber that self-triggers below 10% health, and the entity capture/restore path all of it depends on — none of which exists anywhere in the mod yet.

The four stasis-chamber tiers

Each tier is the previous item's recipe plus one more ingredient, and each tier unlocks one more thing the bank's Browse tab can do with a horse stored in it. The recipe intentionally gets more expensive exactly as the capability gets more powerful, but the bottom tier has to stay cheap — the entire point is that a player with 200 horses can afford to shelve most of them at the bottom tier.

ItemRecipeUnlocks (see Bank Browse tab below)
Basic Horse Stasis Chamber Glass bottle + wheat + a bucket of water (any modded water container matches by tag, not by item) + a horse hair. The bucket/container is not consumed. Storage only — no searchable information.
Intermediate Horse Stasis Chamber Basic chamber + an eye of ender. All of the horse's information becomes searchable.
Advanced Horse Stasis Chamber Intermediate + a gold ingot. The bank passively collects the horse's milk/drops into its 9-slot buffer.
Spacer Horse Stasis Chamber Advanced + a diamond. The horse can be bred while still inside the bank — the other parent must also be in a Spacer chamber — and the foal pops out into the world.
The bucket-not-consumed rule needs a real recipe mechanism

Vanilla shaped/shapeless recipes always consume every input unless the item defines a remainder (the way a water bucket in a cake recipe returns an empty bucket). A tag-matched "any modded water container" input makes this harder: the remainder has to be that same container, emptied, not always a vanilla bucket. This is exactly the kind of match-by-tag-return-drained-container problem the compatibility page's survey of other mods' fluid items already has to solve for water troughs; reuse whatever that ends up being rather than inventing a second remainder rule.

Emergency Horse Stasis Chamber

A basic stasis chamber surrounded by ender pearls (exact shaped recipe still to decide). Held or carried passively by its owner, it watches every horse that player owns and automatically captures one into it the instant that horse's health drops below 10% — the player does nothing, the capture is the save. A horse cannot take damage while it is inside any stasis chamber, so entering one is a hard stop against dying.

Open question: what happens on a second trigger

If the emergency chamber already holds a horse and a second one crosses the 10% threshold, does the player need a second emergency chamber, does the mechanic refuse and let the second horse take its chances, or does it queue and swap at the next opportunity? This has to be settled before the item is built, alongside how "every horse that player owns" is watched at server scale — see watching health cheaply below.

The Horse Stasis Bank

Crafted from 5 wood in a U along the bottom row, an ender pearl in the centre, an iron ingot in each of the two top corners, and a horse hair in the top-centre slot. It is a block entity with a menu that opens with two tabs, the way the Equine Research Shelf's menu already does: a Storage tab to put/take stasis-chamber items, and a Browse tab to look up the horses currently stored.

  • Storage tab is a plain slot grid for stasis-chamber items, plus the 9-slot milk/drops buffer that Advanced+ chambers feed. Nothing here needs to know a horse's internals — it is exactly a chest with a filtered slot predicate.
  • Browse tab lists every horse currently stored in the bank and shows, per horse, only what its own chamber's tier unlocks: nothing searchable for Basic, full search for Intermediate+, a "collect" affordance for Advanced+, and a breeding UI for Spacer-in-Spacer pairs.
  • Passive healing: if the bank has a supply of food and water (its own small input slots, separate from the chamber grid), it slowly heals every horse stored inside it. This is the one exception to "a horse in stasis does not tick" - healing only, never hunger, growth, or ageing.

What "does not tick" has to mean

A horse inside a stasis chamber must not be a loaded entity at all — the goal is server cost near zero, not merely "out of render distance". That means capture has to fully discard the live Horse entity and keep everything about it as data, and release has to re-summon a real entity from that data. No part of the mod currently does this: every existing horse-in-an-item mechanic (transfer papers, breed spawn eggs, the stallion seed jar) names or spawns a horse, it never freezes and later resumes a specific *living* one that had bond, a pregnancy in progress, cooldowns, and gear on it at the moment of capture.

Everything a capture has to carry

A horse's live state is spread across one attachment for its identity and several more for everything non-genetic riding beside it - see architecture.html's attachment table. A stasis capture has to snapshot all of the ones that matter and skip the ones that are legitimately session-only:

AttachmentCarry into stasis?
horse_record (genome, pedigree, names, breed)Yes - this is the horse.
horse_gear (worn tack)Yes - it is worn, it should come back worn.
horse_care (bond, herd)Yes - bond is exactly what an owner is protecting.
horse_social (age, natal band, relationships)Yes.
horse_repro (cycle, pregnancy, nursing)Yes, and carefully - a pregnancy frozen mid-gestation is exactly the case the Spacer chamber's in-bank breeding has to reconcile with.
horse_cooldowns, armed_carrots, passification, cowboy_brandYes, they are all already copyOnDeath-style state meant to survive a re-summon.
Health/hungerHealth: yes, capture it (the emergency chamber's whole point is capturing at a specific health). Hunger: no - stasis horses do not get hungry, so on release start fed.

Watching health cheaply, for the emergency chamber

The emergency chamber needs a per-tick check on "every horse this player owns", which is exactly the kind of per-tick server-wide scan the whole stasis system exists to avoid doing elsewhere. In practice this only has to watch loaded, ticking horses (an unloaded one cannot be taking damage), so it is a hook on the existing damage/health-change path for owned horses, not a scan of the world. Whatever handler already watches for the intake to-do list's "buck off below 20% health" escape-behaviour entry is the natural place to add a second, lower threshold that captures instead of fleeing.

Anticipated files

Nothing here is settled, but this is the shape the existing codebase's own conventions point to - one file per concern, following the pattern the research shelf and the transfer papers already use:

  • common/src/main/java/com/example/horsegenetics/common/horse/StasisSnapshot.java - the pure-data record capturing everything in the table above, with its own codec, next to HorseRecord.java and TransferDeed.java in the same package. This has to live in common/, not the NeoForge module, so the web horse designer and a future 1.12.2 port can both read a stasis-chamber save file.
  • neoforge-26.1.2/.../item/StasisChamberItem.java - one item class parameterised by tier (mirrors how TicketItem.java takes a tier enum rather than being four classes), holding a StasisSnapshot data component.
  • neoforge-26.1.2/.../item/EmergencyStasisChamberItem.java - the self-triggering variant; likely needs a tick or damage-event hook rather than living purely as passive item data.
  • neoforge-26.1.2/.../data/ModDataComponents.java - add the STASIS_SNAPSHOT component, following the existing STORED_GENOME / HORSE_DEED entries in that file.
  • neoforge-26.1.2/.../block/HorseStasisBankBlock.java and HorseStasisBankBlockEntity.java - modelled on EquineResearchShelfBlockEntity.java: a chamber-item grid, the 9-slot drop buffer, and food/water input slots for passive healing.
  • neoforge-26.1.2/.../menu/HorseStasisBankMenu.java and neoforge-26.1.2/.../client/HorseStasisBankScreen.java - the two-tab Storage/Browse menu, modelled on ResearchShelfMenu.java's setStoreTab(boolean) pattern and ResearchShelfScreen.java's client-side Tab enum.
  • A capture/release service - most likely neoforge-26.1.2/.../server/HorseStasisHandler.java, sitting beside HorseRoster.java (the existing "the horse doesn't have to be loaded to know about it" tracker) - the one piece with no existing analog anywhere in the mod, since nothing today discards a specific live entity and later re-summons that same one.
  • Recipes under neoforge-26.1.2/src/main/resources/data/horsegenetics/recipe/ for all five items and the bank, picked up automatically by bake-recipe-reference.mjs (see the Build & test table in CLAUDE.md).

Example code: the shape of a snapshot and its capture

Sketches only, to show the shape rather than the final design - field names and codec wiring will follow whatever HorseRecordCodecs and ModAttachments actually expose by the time this is built. 

// common/horse/StasisSnapshot.java - one immutable capture of a horse, tier-tagged.
public record StasisSnapshot(
        HorseRecord record,
        HorseGear gear,
        HorseCareAttachment care,
        HorseSocialAttachment social,
        Reproduction repro,
        double health,
        StasisTier tier) {

    public static final Codec<StasisSnapshot> CODEC = RecordCodecBuilder.create(i -> i.group(
            HorseRecordCodecs.CODEC.fieldOf("record").forGetter(StasisSnapshot::record),
            HorseGear.CODEC.fieldOf("gear").forGetter(StasisSnapshot::gear),
            HorseCareAttachment.CODEC.fieldOf("care").forGetter(StasisSnapshot::care),
            HorseSocialAttachment.CODEC.fieldOf("social").forGetter(StasisSnapshot::social),
            Reproduction.CODEC.fieldOf("repro").forGetter(StasisSnapshot::repro),
            Codec.DOUBLE.fieldOf("health").forGetter(StasisSnapshot::health),
            StasisTier.CODEC.fieldOf("tier").forGetter(StasisSnapshot::tier)
    ).apply(i, StasisSnapshot::new));
}

// neoforge/server/HorseStasisHandler.java - capture and release, sketch only.
public final class HorseStasisHandler {

    // Called once, at the moment of capture - never re-run against a live entity.
    public static ItemStack capture(Horse horse, StasisTier tier) {
        StasisSnapshot snap = new StasisSnapshot(
                horse.getData(ModAttachments.HORSE_RECORD),
                horse.getData(ModAttachments.HORSE_GEAR),
                horse.getData(ModAttachments.HORSE_CARE),
                horse.getData(ModAttachments.HORSE_SOCIAL),
                horse.getData(ModAttachments.HORSE_REPRO),
                horse.getHealth(),
                tier);
        horse.discard(); // no EntityLeaveLevelEvent block-state work - see api-notes.html
        ItemStack chamber = new ItemStack(tier.chamberItem());
        chamber.set(ModDataComponents.STASIS_SNAPSHOT, snap);
        return chamber;
    }

    // Called on release from a bank or a broken chamber - re-summons a live entity.
    public static Horse release(ServerLevel level, BlockPos pos, StasisSnapshot snap) {
        Horse horse = EntityType.HORSE.create(level, EntitySpawnReason.LOAD);
        horse.setPos(Vec3.atBottomCenterOf(pos));
        horse.setData(ModAttachments.HORSE_RECORD, snap.record());
        horse.setData(ModAttachments.HORSE_GEAR, snap.gear());
        horse.setData(ModAttachments.HORSE_CARE, snap.care());
        horse.setData(ModAttachments.HORSE_SOCIAL, snap.social());
        horse.setData(ModAttachments.HORSE_REPRO, snap.repro());
        horse.setHealth((float) snap.health());
        level.addFreshEntity(horse);
        return horse;
    }
}
Suggested build order

1. StasisSnapshot + capture/release for the Basic tier only, tested by hand with a single horse, before any block exists - this is the one genuinely new mechanic and everything else is UI on top of it. 2. The Horse Stasis Bank block/menu/screen with the Storage tab only (a filtered chest), so chambers can be stored and taken back out. 3. The Browse tab, gated to what each tier already unlocks per the table above, starting with Intermediate's search since Basic needs none. 4. Passive healing from the bank's food/water slots. 5. Advanced's drop buffer, then Spacer's in-bank breeding, since both need the bank to actively act on a horse that is not a loaded entity - the hardest UI problem in the whole feature, and worth doing last once capture/release is trusted. 6. The Emergency Horse Stasis Chamber, once the health-threshold hook exists and the double-trigger question above is answered.
