Implementation priority — cross-cutting foundations first

Ranked by how many other sections each unblocks. Everything above a line should be built before anything below it; within a rank the order is flexible. §20 is the same work seen as a dependency chain — this is the same work seen as blast radius.

2. Gene priority and processing order

Shipped 2026-09-03 — gene priority, derived orderings, genotype-as-list

Every Gene now declares int priority(); codeOrder() / naturalOrder() / magicalOrder() are all one derived sort on (priority, key) over built-ins and SpecGenes together; the genotype and epigenome are gene-keyed, tolerant code strings (a missing gene reads as wild type, an unregistered gene is dropped). The two-priorities distinction, the band convention, the absolute-setter-before-dilution rule and the reserved built-in numbers are written up on Genetics model § Gene priority and Writing a gene. Owner-verified in-game (coats render, the paper genome dump works).

What is still open in this section: the per-genotype founder-frequency / chaos-carrot chance tables below, and the future priority slots for the multi-allele physical-locus merges (§5.1) that the reserved-number table anticipates.

Founder spawn chance — per-genotype percentages

Shipped 2026-09-03 — FounderTable

Everything below is built, bar the chaos-carrot variant (§14.1), which reuses the same class. Gene.founderTable(FounderContext) replaces randomPair(rng); the table is sparse (an unlisted combination never occurs, which is how the test gene forbids its own homozygote); one nextFloat() per gene per founder; genome-aware distributions get a FounderContext that throws if asked about a gene not yet rolled. See Genetics model § Founder frequency.

Every gene declares the percentage of founder horses that carry each of its genotypes. A two-allele gene declares three numbers — e.g. 50% wild type, 40% n/Pfwl, 10% Pfwl/Pfwl; an n-allele gene declares one per unordered pair. This replaces the “1 in N per allele” frequency each gene hand-rolls today.

  • The percentages must sum to 100. If an author’s numbers do not, they are normalised proportionally — a warning, not an error.
  • The draw is one weighted pick over the declared distribution, per founder, in sorted gene order so it stays deterministic given the RNG stream.
  • Declaring it per genotype rather than per allele means the author controls the homozygote rate directly — no second question about whether a draw is per-copy or per-horse.
  • The chance may still be genome-aware — a gene handed the partial genome built so far can return a different distribution (“champagne twice as likely on a chestnut”). Sound only because founders roll in priority order, so a gene can read only lower-priority genes; asking about a higher-priority one is a programming error the registry should catch.
  • This is what lets a tier-1 declarative gene exist without any probability code: it is just a table.

The ordering constraint is an authoring rule, and needs writing down

Phase 1 is multiplicative restriction, which is commutative — except where a gene sets pigment absolutely. BayCoat sets its points absolutely, and the whole PigmentField.dilute design exists because the dilutions have to run after that. So the reserved band is not just a list of numbers, it is a dependency order: absolute setters get low numbers, dilutions get higher ones.

The Gene.priority() Javadoc now states this; keep it on PigmentField too, or the next gene added at the wrong number will produce a bay whose mane does not dilute and nobody will know why.

3. Adding a gene: the modder-facing API

Partly built. Tier 1 shipped — and as a JSON file, not the fluent builder this section originally sketched: a simple gene needs no code and no rebuild. See the gene file format and the gene creator that writes it; every gene — built-in and drop-in SpecGene — sorts into one (priority, key) order (§2, shipped), so registration order cannot decide how a horse looks. What is left: tier 2 below (the abstract base classes for a Java gene), the mod-bus registration hook so another mod can add a Java gene at all, and the genotype-code-segment policy at the bottom of this section — which the drop-in path makes more pressing, since a player can now change the code’s shape by moving a file.

The tiers, for a Java gene

A hand-written gene is still a class implementing an eight-method interface, with three hand-written orderings to edit in step. Most backlog genes are one line of maths and should not need that.

Tier 1 — declarative

Shipped as the file format. A fluent Gene.natural(…) builder would still be the right shape for a Java gene wanting the same brevity — alleles, dominance, a wild frequency, one restrictBlack(0.55f)-style call — covering uniform dilutions, uniform restrictions, and “no coat effect at all” (the performance and health genes in §6). Not built for Java; low priority while the file path covers the common case.

Tier 2 — abstract base classes

For a gene with real logic but a normal shape. AbstractNaturalGene and AbstractMagicalGene take the alleles, dominance and frequency in their constructor and pre-answer everything the interface asks except the one method that matters. An AbstractPatternGene on top adds the BodyNoise boilerplate and the “pull N epigenetic knobs off the expressing copy” helper that GreyCoat and BayCoat both hand-roll today.

Tier 3 — raw Gene

Still there for anything unusual. Nothing is taken away; the tiers just mean a modder rarely reaches this far.

What the base classes absorb, all of it boilerplate today: building the Allele objects, their keys and their slot orders, fromToken, a two-allele founderTable from a declared frequency, the “wild type plus one visible outcome” expression pair, and handing you the seeded RNG instead of making you find it.

An open registry

  • Genes becomes a real registry: register during startup, freeze, then serve. Frozen means codeOrder() and friends can be computed once and cached — they are on the hot path for every code parse.
  • The registration hook lives in neoforge-26.1.2/, not common/ — a mod-bus event (RegisterHorseGenesEvent) or a DeferredRegister-alike that calls into common’s plain-Java registry. That rule does not bend for this.
  • Load order must not matter — orderings are sorted, never registration order.
  • Genes need a namespaced key <modid>.<gene>; the existing convention already does this, so it is a validation rule, not a new format.

The allele rules and the contract a modder has to honour are already written up on Writing a gene — they are live rules, not future ones.

What third-party genes break

The genotype-set change is settled (§2, §21): the genotype is a list keyed by gene, so adding a gene means every earlier horse reads it as wild type and removing one means that gene is dropped — each just triggers a coat regeneration. No segment-count problem, no padding, no back-compat parsing. What still needs care:

  • The dimension stops caring once §8’s revert to random pens lands. A modded gene does still widen the per-pen sign, which is the one place a new gene shows up in the world.
  • CoatTextureId encodes the whole genotype into an Identifier path, so more genes means longer paths (§10) — this is the one place the list still has to serialise, and it needs the hash keying §10 describes.

4.5 Magical genes — the to-do list

Invented genes, phase 3, priority 100+. Unlike 4.1–4.4 this list has no upstream source to be complete against — add to it freely. Each needs a priority, an allele set with n as wild type, a spawn chance, and a delta function. Two ship already (magic zebra, pink hair); coat/pattern/BodyStripes came out of zebra and is the shared stripe helper the natural zebra locus, dun’s leg barring and brindle should reuse.

Cutie marks — the one still on the list

An emblem on each flank, mirrored left and right. It breaks new ground:

  • Placement needs a flank/haunch region in body space, mirrored across z = 0. CoatRegions has no such helper; it is a natural addition, useful to any gene wanting a patch in a specific place.
  • The mark itself can come from a sprite atlas or from procedural shapes. An atlas is far easier to make look good and is what the fiction wants — but it makes this the first gene with a texture dependency. common/ must stay Minecraft-free, so the atlas has to arrive as an int[] the way GradientLut already does, and a modder adding their own marks needs a way to register theirs.
  • How is the mark chosen? Allele per mark (each mark is a heritable, breedable thing — a family line has its mark) or one gene plus epigenetics (the mark varies continuously). The first is the more interesting breeding game and fits the philosophy better; the second scales to hundreds of marks without hundreds of alleles. A hybrid — alleles for mark families, epigenetics for variation within one — is probably the answer.
  • Colour is separate from shape and could be its own gene, making mark and colour independently heritable. More fun, one more locus.
  • Scale check: many alleles at one locus is exactly the case §5.1 has to support anyway, so this gene should come after multi-allele support.

Capability tests rather than planned genes: “add a red border to every white area” and “turn all the black to pink”. Neither is a committed gene; both are the acceptance test for whether a magical gene can actually see what is underneath it.

5. Loci that are not one-gene-two-alleles

Three structural assumptions get in the way, and all three are worth fixing before the gene rollout rather than during it.

5.1 Three or more alleles per locus

Shipped 2026-09-03 — the combination table

DominancePattern is deleted. A gene declares its distinct outcomes as Expressions — each with a name, a human-readable description, a wildType flag ("changes nothing"), a masks flag and its own paint function — and one function maps any AllelePair to one of them. Several pairs sharing an expression is what "dominant" meant; only the double-variant landing on a non-wild-type outcome is what "recessive" meant; two variant alleles each with an outcome plus a third for the pair of them is codominance. None of it needs a name or a special case, and it works for any n.

The open detail this section flagged — how the gallery decides which pairs look alike — answered itself: distinctPairsOf groups pairs by the expression they land on (every wild type counting as one group, since "changes nothing" is one look), which is exact rather than an approximation. randomPair(rng) was replaced by the per-genotype FounderTable in the same change (§2), and breeding updated in step.

Written up on Genetics model § Alleles, combinations and expressions, Writing a gene and the gene file format.

5.2 One physical gene, several traits

KIT carries sabino 1 and the whole numbered W series. MITF carries SW1, 3, 5, 6, 8; PAX3 carries SW2 and 4. MATP carries cream and pearl. EDNRB carries frame.

Tobiano is not one of them. It is a large inversion near / downstream of KIT, not a KIT variant, and roan maps to the region with an unresolved causal change — so both stay their own genes and both can co-occur with anything at KIT. An earlier draft of this section had all three sharing a locus; that would have been wrong, and would have made a tobiano-plus-W20 horse impossible.

Settled (§21): one Gene per physical locus, many alleles. Biologically honest, kills the impossible genotypes, and shrinks the genotype. There is no dominance-per-pair cost — the gene’s own expression table handles every allele combination directly (§5.1).

MATP shipped 2026-09-03

Cream and pearl are one locus with three alleles, six combinations and four outcomes — see MATP. A horse can no longer be Cr/Cr and prl/prl; CreamPearlDilution is gone (the dose table is a six-row switch on the gene); the genotype code lost a segment and the gallery lost 8,192 duplicate pens.

KIT, MITF, PAX3 and EDNRB shipped 2026-09-04

The white-pattern rewrite finished this section. KIT is one gene with eight alleles — sabino 1, five W variants, the W20 booster and N — thirty-six combinations, eight outcomes, and four homozygotes ruled out by canOccur as embryonic lethals. It absorbed the old horsegenetics.white and horsegenetics.sabino, which had been modelling two alleles of one gene as two independent genes and so allowed a horse to be homozygous sabino and dominant white at once.

Splash split the other way, into MITF and PAX3, because it really is two genes — and that is a gain, not bookkeeping: a horse carrying one copy at each is markedly whiter than either alone, a genotype the single splash gene could not express at all. Frame became EDNRB and gained its lethal-white outcome.

Left over from the change: the catalogue is now 2,064,387 pens, which forced MAX_GALLERY_PENS and a lazily-computed GenotypeCatalog — see §8 and §10.

5.3 Sex-linked genes — the two non-autosomal exceptions

Brindle (MBTPS2) is the driving case — a real coat gene, and a real X-linked one. Mares are X/X and carry two copies; stallions are X/Y and carry one. So a stallion is never a carrier, and he passes his X to every daughter and no son. A mare shows a recessive X-linked trait only when homozygous. That asymmetry is the whole appeal: a trait that runs visibly down one side of a pedigree. Y-linked genes are also in (settled, §21) — passed father to son only, never to a daughter, expressed by every colt that carries one.

Sex itself becomes a gene — built

Shipped 2026-09-03

SexGene is registered at priority 1 with alleles X / Y; a mare is X/X, a stallion X/Y, and Y/Y is ruled out by a new Gene.canOccur(AllelePair) that GenotypeCatalog.allPairsOf filters on. Both outcomes are wild types, so the gallery does not widen at all; only totalGenotypes() doubles. A new derived Gene.affectsCoat() plus Genotype.coatCode() keep a gene that never paints out of the texture key, so a mare and a stallion of the same colour still share one baked texture.

HorseRecord.sex is gone as a field and derived from the code (Genotype.sexOf(String), which skips a full parse); the "sex" codec key and StoredGenome’s sex component went with it, and HorseRecords.randomSex is deleted — a foal’s sex now comes out of the ordinary breedWith draw. Founders that need a chosen sex use Genotype.withSex(Sex). Full write-up: the sex gene page.

Still to do below: everything from “Hemizygous notation” on — the inheritance mode on Gene, the two breedWith cases, the reserved-slot storage, and the hemizygous surfaces.

Sex registered like any other locus, alleles X and Y, at priority 1 so it is always resolved first. A stallion carries a real X and a real Y — both slots occupied, so an X-linked gene reads his X copy and a Y-linked gene reads his Y copy. This is the change that makes the rest cheap:

  • Sex inheritance falls out of ordinary Mendelian breeding with no special case. A mare is X/X and can only pass X; a stallion is X/Y and passes one or the other 50/50 — exactly what the existing two nextBoolean() per gene already does.
  • It resolves the ordering problem by construction. X-linked genes need the foal’s sex before they can segregate, and at priority 1 the sex gene is already decided.
  • HorseRecord.sex should become derived, not stored alongside the genotype. Two sources of truth for the same fact is a bug waiting to happen. Keep Sex as the enum the rest of the code reads; compute it from the locus.
  • It gets sex into the genotype code, which the custom spawner and the family tree both want anyway.

Hemizygous notation

A hemizygous allele displays with an X- or Y- prefix — brindle’s Brn renders as X-Brn. Because - is the gene separator and can never appear inside an allele token, the prefix is unambiguous on sight. The code string is unaffected: the token stays Brn, and the game knows from the gene’s declared inheritance mode how to render it.

Storage — settled

For an X-linked gene, a stallion’s second slot holds the reserved Y allele meaning “this locus is not on the Y”; for a Y-linked gene it is the mirror — the first slot holds a reserved X. Either way AllelePair stays two-slotted (no structural change to Genotype) and Epigenome alignment is untouched — the reserved slot just carries epigenetics nothing reads. A stallion’s brindle locus reads Brn/Y, displayed X-Brn.

What still has to change

  • Gene declares its inheritance mode — autosomal (default), X-linked, or Y-linked.
  • breedWith grows two cases: an X-linked gene has the sire give his X to a filly and his Y to a colt; a Y-linked gene has him give his Y to a colt and his X to a filly. The dam is unchanged in both.
  • Expression gets simpler, not harder. A hemizygous stallion has one real allele, so it expresses — no dominance question, no epigenetic-priority tie-break.
  • GenotypeCatalog would otherwise produce nonsense pairs (Y/Y, or an X/X mare at a Y-linked locus). Gene.canOccur is the seam and already rules out Y/Y; the sex-linked cases need it to consult the mode as well.
  • The founder percentage table has to respect sex: a colt at an X-linked locus draws one allele, a filly two; the reverse for Y-linked.
  • Surfaces: the info panel and paper dump want hemizygous wording and the X- / Y- prefix, not a fake homozygote; a punnett square for a sex-linked gene is a different square.

Not planned: imprinting, mosaicism.

6. Non-coat genes: performance, size, health

6.1 The shape of the change

Add capability interfaces a gene may additionally implement, rather than widening Gene with methods most genes ignore: 

interface StatContribution { void contribute(AllelePair, TraitBuilder); }  // speed, health, jump
interface BodyContribution { void contribute(AllelePair, BodyBuilder); }  // overall + per-part scale
interface ViabilityRule    { Viability check(AllelePair, Genotype); }     // lethal at conception / birth
interface ConditionRule    { void conditions(AllelePair, ConditionSink); } // CSNB, MCOA, deafness

Plus a common/horse/HorseTraits resolver that walks the genotype once and produces a plain-data Traits record (stats, body scale, conditions, viability). Same discipline as the coat: all of it in common/, with the server adapter translating to Minecraft attributes the way it already does for speed and health. It is also the tier-1 case from §3 — a performance gene has no coat effect, so declaring alleles plus one stat contribution should be the whole gene.

6.2 Stats become (partly) Mendelian

Target: the genetic contribution comes from HorseTraits, and the random roll survives only as environmental noise on top. Consequences: HorseRecord gains fields (jump, endurance, height — not stamina, which is not a resource, §21); the breeding page would need a substantial rewrite; and backfillStatsIfMissing becomes “recompute from genotype”, which is better — it stops being a guess.

6.3 Polygenic traits — cut

Settled (§21): the mod does Mendelian and sex-linked inheritance only. PDK4, CKM and the jumping QTLs are polygenic in reality; here each becomes one atomic gene with a handful of alleles and an additive weight into a performance stat. Atomic genes are legible — a player can breed for one — where a hidden sum of anonymous markers reads as a dice roll, which is exactly what the philosophy says not to do. No marker-set subsystem, no TraitRule-with-a-sum. Group traits (§6.5) stay, because they are still Mendelian epistasis, not polygenic weighting.

6.4 Health: fewer hearts, and foals that do not make it

Aging is out — a firm no

Horses do not get older, do not grey out over time, do not accumulate age-related conditions and never die of old age. This is not deferred — it is settled (§21). Two consequences: grey’s fixed progression is the design, not a gap, and flea-bitten grey and melanoma are cut with it.

Sub-lethal: fewer hearts

A health gene lowers the horse’s max-health attribute, so an affected horse visibly has fewer hearts. This lands on an existing path — applyStatsToEntity already sets the MAX_HEALTH base value from the record — so the genetic contribution just becomes another input via HorseTraits. Cheapest possible mechanic, no new subsystem.

  • Watch the interaction with fullHeal: a foal born with a low max health should start at its max, and a reload must not heal it. The existing flag already draws that line correctly.
  • hasStats() treats 0.0 as “not recorded yet”, so a genetic health value must never resolve to exactly zero — clamp to a minimum (half a heart) and let the damage path do the killing.

Lethal: the foal dies shortly after birth

The foal is born — it gets a record, a name and a place in the family tree — and then takes damage until it dies. Mark it at birth from its ViabilityRule, and have a tick handler apply a small recurring damage over a few seconds rather than instantly, so the player sees what happened.

  • Needs a data attachment for the condition, a tick handler, and a damage source that reads as “genetic defect” rather than an unexplained death.
  • Give the player feedback — a chat line naming the condition beats a foal that silently drops dead.
  • HorseAncestryData already tolerates ancestors it cannot find, so a short-lived foal in the pedigree is fine.

Embryonic lethal (MET)

Checked at conception: if the drawn foal genotype is inviable, no foal is produced. The foal genotype is drawn before the check, so Genome.breedWith stays untouched and the check just reads its result.

Config toggle

A server/common setting, the mod’s first ServerConfig (ClientConfig exists but is the wrong side). Three positions: full genetics with foal deaths (the default); genetics and reduced hearts but no deaths; off. All the health genetics get built regardless — the toggle only governs the deaths.

Carrier display

The wording already exists and nothing reads it. A carrier combination is an Expression marked wildType with its own name and description — MATP’s pearl-carrier, pink hair’s pink-carrier, mushroom’s mushroom-carrier — so the info panel needs to show a sentence, not compute one. It becomes far more valuable once recessive lethals exist: the difference between a breeding programme and a lottery. A punnett / expected-foal display is the natural companion, and reads the same table.

6.5 Traits that come from a group of genes

Wanted, and distinct from the cut polygenic idea: two or more genes, each with their own alleles, that only together trigger an outcome. This is epistasis / complementation — still fully Mendelian — and it needs a home:

  • It is not a gene, so it cannot live on the Gene interface. It wants a separately registered thing — a TraitRule — that declares which gene keys it reads and is handed those pairs.
  • It is still Mendelian. Each gene inherits normally and independently; the rule just reads the result. No new inheritance code.
  • It may affect the coat — settled. That means a coat-affecting rule needs the same things a gene needs: a phase and a priority. Which argues strongly for modelling a TraitRule as a pseudo-gene: same delta function, same ordering, same determinism rules, differing only in that its inputs are several pairs instead of one. Reusing the gene pipeline wholesale is much cheaper than a parallel one, and the spawner UI and the coat cache need no special case.
  • The one thing it cannot inherit from Gene: it has no alleles of its own, so it contributes nothing to the genotype code and never appears in an allele lookup. Keep it out of codeOrder().
  • Determinism: rules must be sorted like genes, and a rule reading an unregistered gene has to fail loudly rather than default.
  • Visibility to the player. A trait with no single gene behind it is invisible in a genotype code and unguessable in a punnett square. It needs a UI surface of its own or it will read as randomness — exactly what the philosophy says not to do.

Cream + pearl looks like this case but is not: they are one physical locus modelled as two genes, and §5.2 merges them rather than writing a rule.

6.6 Status effects — to be specified

The third kind of gene effect is a list of “status-y” traits that has not been written down yet. The known ones are above; this is a placeholder for the rest, and the capability interfaces in 6.1 should not be considered final until it lands.

A first slice is built — a data-driven gene can carry an effects block (six verbs: traversal, attribute, emitter, mob_effect, yield, glow, with boolean when conditions), documented on gene effects. What is left is everything else on the trait & effect architecture — triggers, selectors, auras, resource pools, goals, trait relations, and the 0–1 scalar conditions the built version approximates as booleans — plus wiring the one parsed-but-inert verb (attribute). The capability interfaces in 6.1 should not be considered final until that lands.

7. Horse care: milking

Gated healing shipped — a hurt horse regenerates only near both water and food, sharing one slow tick with §13. Full machinery on horse care. Two things it left for other sections: a lethal foal (§6.4) must out-damage that regen, and an info-panel line naming “what is missing” would beat particles alone.

Milking is not built. Right-click an adult mare with a bucket, get milk. Neither genetic, but it hooks the genetics: it requires full health, and a horse only reaches full health through the healing gate above.

  • The sex is already there — a record lookup plus an age check, not new state.
  • Goes in HorseInteractionHandler, which already handles the clock and the stick. The trap it already documents: EntityInteract fires on both sides, and any item used on a tamed horse is otherwise turned into a mount by vanilla — so cancel on the client too, and do the bucket swap server-side.

The rules, settled

  • The mare must be tamed. An untamed mare is not a dairy animal.
  • The mare must be at full health — at its own max, so a genetically frail horse is milkable at 4 hearts, not the species max. This is what ties milking to the healing gate.
  • Once per Minecraft day (24 000 ticks — the mod’s standard time gate, §21). Needs per-horse state: a small attachment holding the game time of the last milking (not a countdown, so it survives a reload).
  • Milking a stallion gets you kicked: about half a heart of damage. Better than a silent no-op, and it makes the sex of a horse something the player learns by doing.
  • Foals do nothing — but say something, or it reads as a bug.

8. The horse dimension: back to random pens

Revert the gallery. The catalogue-driven dimension goes back to random genotypes per pen. Keep the two things worth keeping: pairs (a mare and a stallion with the same genome) and a sign out front listing the genome.

This also resolves the combinatorial problem in §10 — a random corridor does not care that the genotype space is 1019, so the gallery stops being the thing that blocks adding genes.

What changes in the code

  • buildPen goes back to rolling a genotype per pen. Randomness here is legitimate: these are foundation horses with no parents, which is exactly where the determinism contract allows a draw.
  • The corridor stops having an end. LAST_SEGMENT_INDEX (now pinned by the MAX_GALLERY_PENS cap at 9,999 segments, giving 70,000 blocks) and buildEndCap go away, or become an arbitrary length. The walk-ahead extension stays.
  • The entrance tally sign no longer means anything — drop it, or replace it with something true of a random corridor.
  • The per-pen sign stays.
  • The sign-fits test changes shape. It currently asserts every catalogue entry fits three 15-char lines. With random genotypes there is no finite list, so it becomes a property test over many random draws, or an assertion that wrap truncates gracefully. Do not just delete it — a sign that silently drops a gene is exactly the bug it was written for.
  • GenotypeCatalog itself can stay. The distinct-pair reduction is useful to a punnett display and to tests; it just stops driving the dimension.
  • One thing to re-check: “a rebuilt plot is byte-identical, so an X slot handed back to the free list can be overwritten in place” is no longer true once pens are random. Either air-fill on teardown, or confirm that overwriting a different random corridor leaves nothing stale — leftover signs from a longer previous corridor are the likely artifact.
Settled: the pair shares a genotype, not an epigenome

Both horses are independent founder rolls with only the genotype pinned, so a pen shows one genotype twice, differently. That is what the catalogue version already does, so buildPen needs no change here.

9. The custom horse spawner (creative only)

A creative-mode screen for building a horse gene by gene and spawning it.

Partly built. A dev custom_horse_spawn_egg ships: it opens an age / sex / genome editor (client/CustomHorseSpawnScreen), spawns through SpawnCustomHorsePayload with the server re-checking the sender, and a gene only appears if it is registered. What is left: the live 3D preview, the per-allele epigenetics editor (reroll + type-in), gating on creative rather than a dev build, and round-tripping a pasted genotype code. The rest of this section is that remaining work.

What it does

  • Every registered gene, every allele. One row per gene, both allele copies selectable. Built off the registry, so a modded gene appears without the screen knowing about it.
  • Per-allele epigenetics. Each copy gets its priority and seed shown, a reroll button, and a type-it-in field for an exact value. The first place epigenetics become directly visible — a debugging tool as much as a creative one.
  • A live preview that redraws as the genotype changes.
  • Spawn.

Building it

  • Creative only, checked on the server. The screen opens client-side, but the spawn arrives as a payload and the server must re-check that the sender is in creative before acting. A client-side-only check is bypassable, and this payload spawns arbitrary entities.
  • The preview already has a proven technique. FamilyTreeScreen.drawHorseModel builds a render state from a throwaway client-only Horse and injects the coat straight onto the render state, deliberately without touching ClientCoatCache. Reuse it exactly — polluting the cache from a preview would leak edited horses into the world’s rendering.
  • The preview needs a coat per edit. Debounce, and reuse the texture key so an already-baked combination is free — the cache key is a pure function of the genome, which is exactly what makes this cheap.
  • The screen must scale to an unknown gene count. Nine genes fit on a screen; twenty-seven do not, and a modded install has no upper bound. Scrolling plus grouping from the start, not retrofitted.
  • 26.1.2’s GUI layer is retained-mode. FamilyTreeScreen is the working reference for a from-scratch screen in this codebase, including scissor clipping and the entity draw.
  • How is it opened? A creative-only item, a keybind, or a command. A keybind is closest to the existing pattern — but this should be gated on creative mode, not on a dev build, so it needs its own gate.
  • Round-trip the code. Paste a genotype code in, get the horse; copy the current horse’s code out. Nearly free once the screen exists, and it turns every bug report into something reproducible.

10. What breaks at scale

The master table is ~27 loci against today’s 11, several with many alleles, and third-party genes make the count open-ended. That is not a linear change.

  • The genotype space. Now 3^15 × 6 × 6 × 2 = 55,099,802,880 (twelve two-allele genes, three-allele MATP, dun and PAX3, four-allele MITF, eight-allele KIT, and the two-combination sex locus) — it was 3^11 = 177,147 before the seven visual genes shipped, the multiplier in miniature. With the full table the raw product is on the order of 1019.
  • The gallery has effectively died — and it is being reverted anyway. The white-pattern loci took the catalogue to 2,064,387 pens, whose corridor would be about 7.2 million blocks — a quarter of the way to the world border, leaving room for four plots in the whole dimension. That is what forced MAX_GALLERY_PENS (20,000, about 70,000 blocks), which is a lid on the symptom and not a fix; the entrance sign now says how many pens it is showing out of how many exist. The catalogue itself is computed on demand rather than materialised (a two-million-entry List<Genotype> is hundreds of megabytes), so it costs nothing until walked (lazily built, so it doesn’t hang, but it is no longer a thing a player walks). The argument for §9 has now fully arrived. If a systematic gallery is ever wanted again, the shape that scales is a wing per locus: each gene’s pairs on a fixed wild-type background, bounded by alleles rather than by their product, extending naturally to a modded gene adding its own wing.
  • The genotype code string. 27+ segments with tokens like SW10 / W36 puts a code in the low hundreds of characters. Everything carrying it grows in step — the record, the attachments, both sync payloads, and the epigenome code, which is already the fatter of the two. Worth a compact binary encoding for the payloads at that point; keep the string form for saves and debugging.
  • CoatTextureId and path length. The encoding expands (A-Z → 2 chars, anything else → 5), so a 300-character code becomes a >1,000-character path, which Identifier will not accept. The fix is to key the texture on a hash plus a short prefix, keeping the existing KEY_BY_ID tripwire — which caught the original flat-white-horse bug and would become load-bearing rather than paranoid, so give it a real collision-resolution path (append a counter) instead of throwing.
  • Wild-spawn frequency. With a dozen recessive lethals in the pool, founder frequencies need a pass: rare enough that wild horses are healthy, common enough that a breeder eventually meets one.
  • Display. At 27 loci the sign approach caps out; the info panel needs grouping (colour / pattern / performance / health) and probably scrolling.
  • Composer cost. Phase 1 is O(genes × texels) at 16,384 texels per sheet. 27 genes is still trivial; the pattern genes’ BodyNoise sampling is the real cost. Coats are cached per texture key, so this only bites on first bake — but the gallery bakes hundreds at once.

12. Horse hair, shearing and the crafting economy

The material floor for every recipe the two documents add. Cheap, self-contained, and it blocks the carrots, the vials and the villager, so it goes early.

12.1 Shearing

  • Right-click an adult horse with shears, get 1–3 horse hair, regrowing on a cooldown. It belongs in HorseInteractionHandler beside milking (§7) and hits the same trap that file already documents: EntityInteract fires on both sides, and any item used on a tamed horse is otherwise turned into a mount by vanilla. Cancel on the client too, do the drop server-side.
  • Regrowth is per-horse state — the same attachment shape as milking’s cooldown, and the same gate: once per Minecraft day (§21). Store the game time of the last shear (a stored timestamp gives the shearProgress ramp the documents want for free).
  • The sheared look is a render-layer overlay (settled, §21) — it only has to read as vaguely different, not look good, so no coat-variant texture and no extra bake cost.
  • Bond gives +5 per shear (§13), so shearing is the one interaction that is both an economy and a relationship input. This is one of the two unwired bond sources.

12.3 Collision-proofing, and the one part that is not free

The stated rules — every recipe takes at least one modded item, every output is a modded item, everything is shapeless — cost nothing and are worth keeping as written. The layer that is work:

A recipe that must match a specific research paper is not a vanilla shapeless recipe

Vanilla ingredient matching is item plus, at best, a component predicate. “A research paper whose gene component is peafowl” as an ingredient, with the gene copied onto the output carrot, needs a custom recipe type — one recipe parameterised by the paper it is given, not N generated recipes.

This matters more than it looks. With one parameterised recipe, a third-party gene gets its carrot for free the moment it registers. With generated per-gene recipes, every modded gene has to ship a datapack — which contradicts the drop-in gene file that already shipped (§3).

  • Do not invent a second identifier space. The documents key papers on a short symbol (PFWL) and specify it as case-insensitive-but-exact. Genes already have a validated namespaced key, <modid>.<gene> (§3). Use it. A symbol can stay as a display string; it must not be what a recipe matches on, or two mods will collide on PFWL in exactly the way the rest of this design is trying to prevent.
  • Papers are consumed on craft, and must be in the inventory to craft. That is the ordinary behaviour of an ingredient, so nothing special is needed — the “knowledge key” framing is philosophy, the implementation is just an ingredient.

13. Bond and herds

Partly built. The core shipped: a per-horse bond number (0–100) with four behaviour tiers driven by one BondFollowGoal (face / approach / follow, real pathfinding), an emergent herd id, and the shared 30-tick scan §7 called for. Gains wired: proximity, riding, feeding; cap +15 per 24 000-tick day; a foal in a herd gains double. The tier table, the gain rates and the herd formation rule are documented on horse care.

What is left

  • Bond sources not yet wired: shearing +5 (blocked on §12 — there is no shearing) and sleeping nearby +1/night.
  • Nothing consumes the herd alpha. It is not stored — a consumer would compute “oldest or highest-bond, with an explicit tiebreak” on demand — but there is no consumer yet: no herd-wide behaviour, no alpha-follows, no display.
  • The comfort buff stays as passive regen. The source documents specify reduced stamina drain + faster regen; the mod is not getting a stamina resource (§21), so herd members simply keep the +1 extra passive regen they already have. Nothing more to design here — it is done bar play-testing.
  • Herd membership is invisible outside the inventory panel’s “• herd” flag — no herd view (that is §17), no world-side indication.

14. Breeding modifiers: the carrot family

Three kinds of consumable, all fed to a parent before breeding: four general breeding carrots, one magic carrot per gene, and combinations of both. They are the mod’s first mechanism for influencing inheritance, which makes them the first thing to touch the determinism contract.

Where the effect is applied decides whether this is sound

A carrot must bias the gamete the fed parent contributes, not rewrite the parent’s own genotype. Rewriting silently mutates a horse the player spent generations breeding for, and it makes the horse’s displayed code stop matching its history. Every carrot below is a modifier on the draw.

Timing is settled (§21): a fed carrot behaves like a vanilla golden carrot — it puts a temporary window on the horse (the same shape as breeding-mode love), consumed when the pair breeds and gone when the window lapses. During the window the effect is stored on the horse, synced and part of the determinism input; there is no permanent stored carrot state. Each carrot type shows a differently-coloured heart particle when fed, as feedback.

14.1 The four breeding carrots

14.2 Magic gene carrots

One per gene. Feeding it makes the game treat that parent as n<Gene> (heterozygous, the default) or <Gene><Gene> (homozygous) for that one gene when its gamete is drawn. Normal Mendelian rules then apply, so two heterozygous-carrot parents give the ordinary 25/50/25.

  • The recipe is standardised: golden carrot + research paper + horse hair + a rarity item + at least one flavour ingredient. Rarity item by tier: iron, gold, diamond, emerald, netherite ingot, nether star. Keep the tier on the gene and the tier→item mapping in one table, so retuning the economy is a one-line change and a modded gene cannot invent its own currency. A gene that declares no rarity defaults to the gold-ingot tier (§21).
  • A gene can opt out of having a magic carrot at all (settled, §21) — sex (§5.3) and the recessive lethals (§4.4) are genes for which one is nonsense or hostile. The built-ins’ existing exceptions (extension, agouti have no carrot) become that flag instead of a hard-code.
  • It needs metadata that does not exist: rarity, behaviour, flavour ingredients, descriptions. That is §19, and it lands first.

14.3 Combination

  • Multiple carrots crafted together become one carrot carrying all the effects. A component holding a list, no visual change, tooltip enumerating them, no cap on count.
  • Contradictory combinations are unspecified. Stabilizer plus magnifier; two magic carrots for the same gene with different behaviours. Define the resolution — reject at craft time is clearer than last-one-wins, because the player can see it happen.
  • Expiry is settled (§21): a fed carrot lasts exactly as long as vanilla breeding-mode love and is consumed on breeding — the same rule for the plain path and the seed-jar path.

15. Assisted reproduction: vials, embryos, cloning

15.1 The seed jar flow

Partly built. A cut-down flow works: put a tamed stallion in breeding mode, right-click with an empty_seed_jar → a filled jar carrying a GenomeSample (genotype + epigenome) plus the donor’s sex / UUID / name / stats in the stored_genome data component; right-click a breeding-mode mare with the jar → a foal, bred through the same applyBredFoal path natural breeding uses, drawn at impregnation from the stored genotype — which resolves the “genotype, not a frozen gamete” question in this section’s favour. Code: server/StallionSeedJarHandler, data/StoredGenome, common/genetics/GenomeSample.

What is left

  • The real breeding-carrot gate. The gate is currently vanilla love (isInLove()) standing in for “fed a breeding carrot”. Needs the carrots (§14) to do anything first; the carrot window itself is the timed window (§14, §21), so no separate timer.
  • Gestation — the genuinely new part. The foal appears immediately, like vanilla. A gestation state means an attachment plus a tick, and answers for: the mare is killed, the chunk unloads, the world reloads mid-term, the mare is bred normally while carrying.
  • Carrot effects on the jar. A jar should capture the fed stallion’s carrot effects and apply them at impregnation (§14). None are carried today.
  • The donor cooldown — once per Minecraft day (§21) — is not applied; only the mare gets the vanilla breeding cooldown.
  • The pedigree edge is settled (§21): the jar must store enough of the sire’s record — not just his UUID — that the family tree can render his node. Today it stores name / sex / stats already; confirm that is sufficient and wire it into the synthetic sire record.
  • A collectedFrom marker on the jar — player-made vs villager-sold (§18) — and the recipe restriction “no magic carrot on a jar” are both trivial once the above exists.

15.2 The later tiers

Embryo extraction, gene screening, gene splicing, cloning, cross-species. Each is a block with an inventory and a screen, and each is endgame by intent. Three notes that change how they should be scoped:

  • The gene sequencer is not new work — it is the browser (§17) or the family-tree screen pointed at a vial or an embryo. Build it as a view, not a machine with its own UI.
  • Gene splicing is the first thing in the mod that writes an arbitrary genotype in survival. It needs the same validity predicate the creative spawner (§9) needs — is this allele pair legal, does this locus exist — and that predicate should be written once and shared. Splicing also interacts with the lethals (§6.4) in an obvious way that wants deciding: can a player splice a horse into a lethal genotype.
  • Cross-species is much larger than its row. Donkeys and mules are separate vanilla entity types, mules are sterile by design, and neither carries any of this mod’s genetics. Extending the genome to another species is a project, not a tier. Scope it separately or cut it.

16. Knowledge: the gene database and research papers

16.1 The database

A per-player set of discovered genes, filled by taming a horse carrying one, breeding a foal with one, sequencing, or reading a paper. Per gene it holds the symbol, name, descriptions, inheritance type, which allele variants have been seen, whether the carrot recipe is unlocked, and where it was first met.

  • It is per-player, per-world saved data, synced to the client for the UI. The documents propose a JSON file per player uuid; use whatever saved-data path the mod already uses rather than a bespoke file, and never store it client-side, since it gates crafting.
  • The description text does not exist for any gene. Name, blurb, visual effect, gameplay effect — none of it is in the gene format today, and a third-party gene will not have it either. §19.
The database hides nothing — settled

It is a plain progressive record: entries populate as a player meets genes, which keeps a list of a hundred-plus genes from overwhelming a new player. It is not a fog of war — the info panel, the pen signs and the genotype code keep showing every gene a horse carries, always. The only thing discovery actually gates is the magic-carrot recipe.

16.2 Research papers

  • An item with a gene component. Reading it adds the gene to the database and unlocks its carrot recipe; crafting the carrot consumes it.
  • Three sources: loot chests, other players, and writing one from your own database at the cost of one book. The third is what makes knowledge shareable rather than hoardable, and it is the cheapest of the three to build — a button in the database tab.
  • Loot injection is a global loot modifier on the NeoForge side, weighted by rarity tier (§19). Not common/ work.
  • The villager sells papers at two tiers (§18) — the “no villager” line was from an older design and is dead.

17. The horse browser, and the creative egg

One screen on the H key with five tabs: horse list, gene database, vial inventory, herd view, and a crafting tree. Plus the out-of-band actions — teleport a horse to a stall, whistle for bonded horses, recall to a holding pen.

  • FamilyTreeScreen is the working reference for a from-scratch retained-mode screen in this codebase, including scissor clipping and the entity draw — the same note §9 makes about the spawner. It should probably become a tab rather than stay a separate screen, and its drawHorseModel is what row portraits use. The same warning applies: build the render state from a throwaway client-only Horse, and do not touch ClientCoatCache.
  • The expensive part is not the UI — it is the index. There is no list of a player’s horses today. It needs a per-player owned-horse registry, updated on tame, breed, death and transfer, holding enough denormalised data (name, sex, age, genotype, bond, herd) that horses in unloaded chunks still appear and can be sorted. Design that before the tabs.
  • Sort and filter by gene run server-side over that index, and the result paginates. Do not sync every horse’s genome to the client to filter it there.
  • Teleport, recall and whistle need the stall and pen definitions that §11 says are missing, plus answers for a destination that no longer exists and for whether any of it crosses dimensions — which matters because the horse dimension (§8) exists.
  • The crafting tree tab goes stale on contact with a modded gene. Generate it from the recipe manager at runtime; do not hard-code the graph.
The “limited custom egg” is §9’s spawner, in a worse form

A creative-only item that sets extension and agouti plus one heterozygous custom gene is a strict subset of what the custom horse spawner already plans to do, with its own validation code to maintain. Recommend cutting it — and if a placeable, giftable object is genuinely wanted for events and contest prizes, give the spawner an “export as spawn egg” output instead. One screen, one validator, one code path.

18. The Horse Master villager

It exists (settled, §21) — a villager profession with a workstation, five tiers and sixteen trades, selling random magic carrots, research papers and seed jars. It is a good way to get rare horse items to players; the “removed as unthematic” line in the older design document is dead. Cut / legendary / mythic genes are still never sold.

18.1 What it needs

  • A profession, a workstation and a POI. Horse Trader’s Post: 3 hair cloth + 2 braided rope + 2 fence. Spawns where horses do — plains, savanna, meadow.
  • Random trades cannot be plain offers. A vanilla trade offer is a fixed ItemStack. “A random rare magic carrot”, “a random paper”, “a vial with a rolled genotype” each need a custom listing that rolls when the offer is generated — which means the roll is per restock, not per purchase. That is already what the documents want: their “stock refreshes every in-game day” is vanilla restock. Say so and delete the separate stock system.
  • Buying back player-made vials needs component matching on collectedFrom (§15.1), which a vanilla trade cannot express either — the same custom listing does it.
  • Random vials and random papers need the rarity field (§19), and a pool per tier that a third-party gene joins automatically.
  • Legendary and mythic are never sold — a rarity check in the listing, and the reason the rarity tier has to be a real enum rather than a display string.
  • The custom gossip type (HORSE_TRADER, for discounts) is unverified — gossip types are not obviously extensible. Check before designing around it, and fall back to vanilla gossip if not.
  • Use vanilla’s tier names. The document’s ladder is Apprentice (Novice) / Journeyman / Adept / Expert / Master; vanilla’s is Novice / Apprentice / Journeyman / Expert / Master. Five either way, so this is purely a naming fix, but “Adept” does not exist.

19.1 The gene creator already is most of the “web gene editor”

The system summary describes a browser-based visual gene designer as a future, post-launch system. Its export half already exists — the gene creator writes the JSON a gene needs and the registry loads it without a rebuild (§3). The genuinely new parts of that section are narrower than they look:

  • Rarity, carrot behaviour, flavour ingredients and descriptions become fields on the existing form, plus a schema version bump. Small.
  • A visual expression designer — SVG upload, shapes and curves for maximal expression, deletion down to minimal expression, per-part colour ranges and gradients, glow and particles scaled by expression — is a much larger claim than the rest of that document and effectively a second product. Scope it separately. It also assumes an expression→part-rendering model the coat pipeline does not have; the epigenetics that exist select a seed, not a percentage that scales parts.
  • Gameplay effects authored per gene already have a home: the effects block and its verbs (§6.6). The editor should emit that, not a parallel format.

19.2 Attached model parts

  • The proposal is GeckoLib plus Blockbench, with an attached render layer whose bones are children of the horse’s body bone so they inherit every animation, conditional on the horse’s genes.
  • This is a new runtime dependency and the mod’s first non-texture visual. The coat pipeline is texture-only and common/ is Minecraft-free, so common/ can only declare that a gene wants a part, by id; the renderer resolves it — the same shape as GradientLut arriving as an int[].
  • Check whether a plain render layer parented to the existing model part does the job before taking the dependency. Animation inheritance is the entire argument for GeckoLib, and a horn does not animate independently of the head.
  • Saddle, armour and any third-party tack render at the same time. Layer order and z-fighting are the predictable bugs.

20. Suggested order of work

Each step is useful on its own and unblocks the next.

The three-phase pipeline and the first two magical genes are done and drop off the front of this list; the rest, in order:

  1. Gene priority + derived orderings (§2). Small, self-contained, and it deletes the three hand-maintained lists that make every later step annoying. Add the determinism tests alongside it.
  2. The gene-authoring tiers (§3) — the abstract base classes and the mod-bus registration hook (the Java declarative builder is optional; the file path covers the common case). Doing it here means every gene from the next step onward is written the easy way instead of being rewritten later.
  3. Multi-allele support (§5.1) + merge cream and pearl into MATP. Smallest real multi-allele locus, with an existing resolver to fold in. Also unblocked dun’s third allele, which shipped straight after it.
  4. Health, the cheap half (§6.4): genetic contribution to max health. No new subsystem, visible immediately as hearts, and it makes the health genes worth carrying.
  5. Trait framework proper (§6.1) with MSTN as its first consumer, then the size genes once the entity-scale question is answered.
  6. Revert the dimension to random pens (§8) — small, and it unblocks adding genes freely. Could just as well go first; it is independent of everything above.
  7. Lethals (§6.4) — MET first (a conception check only, no death behaviour to design), then the born-and-dies path with its config toggle and carrier display, then frame’s Ov/Ov. Note the ordering dependency on §7's healing gate: a lethal foal has to out-damage the shipped regen.
  8. Sex as a gene, then sex-linked scaffolding, then brindle (§5.3). Registering X/Y at priority 1 is small and worth doing early. The scaffolding touches breedWith and GenotypeCatalog, so do it while the breeding tests are still small. Brindle is its proof.
  9. LP (leopard complex) and PATN1 — the one pattern family the white-pattern rewrite deliberately left alone, and the largest gene job remaining. It needs a spot field and a blanket mask, neither of which WhitePattern’s two shapes cover, and PATN1 is the model’s first modifier gene.
  10. Face markings as a shared family before adding more white-pattern alleles: every locus currently draws its own centreline stripe, and a star is not a narrow blaze.
Worth pulling early

The custom horse spawner (§9), as soon as the registry from step 4 exists. It is the fastest way to look at any genotype without breeding for it, so every gene after it is quicker to build and check.

Independent of the whole chain, doable whenever: milking (§7). It does not touch the genetics, and its full-health rule now has the shipped healing gate to lean on.

Cut: aging and everything downstream of it — grey progression over time, flea-bitten grey, melanoma (§21). Eye colour as a channel is not cut, just independent of everything above; it unblocks tiger eye and blue-eyed creams whenever it is convenient.

The gameplay layer — a second chain, largely independent

§§11–19 touch the genetics in only three places: the carrots bias a gamete draw (§14), the vials carry a genome (§15), and the database and carrot recipes read gene metadata (§19). Everything else — hair, bond, herds, the browser, the villager — is ordinary Minecraft work that can proceed in parallel with the gene rollout above.

  1. Settle the one prerequisite before writing anything: the custom-entity question (§11) — a subclass vs attachments. It is a decision, not work, and it invalidates a lot of code if answered late.
  2. Gene metadata (§19) — rarity, the carrot block, the description fields, and the creator form that writes them. Everything downstream reads it, and adding it later means retrofitting every gene file.
  3. Hair and shearing (§12), including the custom parameterised recipe type. It is the material floor for every other recipe, and shearing lands beside milking in a file that already documents the trap.
  4. The carrots (§14) — the four breeding carrots first, since they need only the gamete hook; magic carrots second, once §19 exists; combination last.
  5. Finish the seed jar (§15.1) after the carrots — the real carrot gate, then gestation (the genuinely new part), then carrot effects on the jar.
  6. Finish bond and herds (§13) whenever — the shearing and sleeping bond sources, plus an alpha consumer. The core, the shared scan and the comfort buff are done.
  7. Database and papers (§16), which is mostly UI once §19 is done.
  8. The browser (§17) — the owned-horse index first, the tabs second. FamilyTreeScreen should move into it rather than be duplicated.
  9. The villager (§18) last.
  10. IVF tiers 2–6 (§15.2) and attached model parts (§19.2) are endgame; cross-species should be re-scoped or cut before it is scheduled at all.
Build the spawner first anyway

§9 was already worth pulling early for the gene work. It is worth more now: every system in §§13–18 needs a horse with a known genotype to test against, and the alternative is breeding for one each time. It also makes the “limited custom egg” (§17) redundant before anyone builds it.

21. Decisions still open

Settled — do not reopen

Kept here briefly so a later session does not relitigate them:

Coat pipeline

  • Phase 3 is a signed add/subtract on unclamped int channels, capped only at conversion, applied over the natural result — zebra is a large negative contribution, not a special case.
  • Context-aware phase-3 genes are intended, not a compromise: a magical gene reads the accumulated result and adds relative to it. Order matters, and that is fine — every gene has a fixed priority number it is processed at, so the outcome is fully deterministic. Magical genes are allowed to be physically unrealistic.
  • A magical gene can paint a dominant-white horse (white is natural, magical runs after) and does see both the natural coat and the accumulated magical deltas.
  • One gene cannot act in both phases.
  • 100 is magical, and all three-digit priorities are magical; the 0–99 band is convention with a log warning, not enforcement.
  • Group traits may affect the coat, so they get a phase and a priority like a gene.

Genetics model

  • Inheritance is Mendelian with two exceptions: X-linked and Y-linked genes. Crossing over, maternal inheritance, imprinting, mosaicism and polygenic traits are all out — the mod does Mendelian and sex-linked inheritance and nothing else.
  • Sex is itself a gene at priority 1 — built, see its page. A stallion carries a real X allele and a Y allele (two occupied slots, no structural change to AllelePair / Epigenome), so both X-linked and Y-linked genes are expressible. A hemizygous allele displays with an X- / Y- prefix; the code keeps the bare token.
  • A physical locus with many patterns is one gene (KIT, MITF, MATP) with a large allele set. There is no dominance property at all — the gene declares an Expression per distinct outcome and maps every allele combination to one of them. DominancePattern is deleted, not demoted to a hint: "which combinations share an outcome" is the whole of what it said, and the table says it exactly, for any number of alleles. Grouping alleles onto one locus is a modelling choice, not linkage (linkage: settled no).
  • Determinism, masking and "changes nothing" are per combination, not per gene and not per allele — they are fields on the expression. An Allele therefore carries no visible / deterministic hint at all, only a token, a label and a slot order.
  • Every wild type is one look. A gene may declare several (MATP’s pearl-carrier reads differently from its plain wild in the gene dictionary), but the gallery collapses them into one pen, because "changes nothing" is one appearance.
  • The epigenome lives on HorseRecord, beside the genotype, not on a separate entity attachment. Both are heritable facts assigned once at birth; storing the genotype twice was one fact in two places, and keeping the epigenome off the record is why the family tree used to draw ancestors from an invented seed.
  • Founder frequency is per genotype, declared by the gene author. A two-allele gene might declare “50% wild type, 40% n/Pfwl, 10% Pfwl/Pfwl”. The percentages must sum to 100; if they do not, they are normalised proportionally. This replaces the old “1 in N” per-allele frequency. Founder draws stay deterministic given the RNG stream (roll in sorted gene order).
  • The chaos carrot has its own per-gene distribution — the chaos chance function (§14.1, §19), the same shape as the founder table but separate, so an author can (say) let it only ever produce heterozygotes. Optional; omitted → uniform over the gene’s pairs.
  • The genotype is stored as a list keyed by gene, not a positional string. Each gene carries its own order number, so the processing / display order can be recomputed at any time. Adding or removing a gene is therefore cheap: a missing gene reads as wild type, an unknown one is dropped, and either just triggers a coat regeneration. No segment-padding, no back-compat handling — the mod is pre-release and keeps no saves.
  • A foal inherits each allele copy’s epigenetic seed verbatim (breeding) — no re-roll.
  • Allele tokens are alphanumeric, 1–128 chars, wild type n.

Health & aging

  • Aging is out entirely. No coats that change over time, no death of old age. This is not “deferred” — it is a firm no. Grey’s fixed progression and flea-bitten / melanoma being parked follow from it.
  • Health is fewer hearts (a max-health contribution), plus lethal foals. All the health genetics get built; the foal deaths sit behind a config toggle that is on by default. Three positions: full genetics + deaths (default), genetics + reduced hearts but no deaths, off.

Care, bond, gameplay

  • Pen pairs share a genotype only.
  • Gated healing is built (near water + food); the bond / herd core is built — see horse care. Hand-feeding bypasses the healing gate.
  • Every time-gated action is once per 24 000-tick Minecraft day unless there is a specific reason otherwise — bond’s daily cap, milking, the seed-jar donor cooldown all use it.
  • Milking needs a tamed, full-health mare.
  • The herd comfort buff is passive health regen (the +1 extra it already has). Stamina is not becoming a real resource.
  • The Horse Master villager exists — it is a good way to get rare horse items to players. The earlier “removed as unthematic” line was from an older design and is dead.
  • The gene database is a plain progressive record, not a fog of war. Entries populate as a player meets genes (which keeps a 100-gene list from overwhelming a new player); nothing is ever hidden in the info panel or the code. Discovery gates only the magic-carrot recipe.
  • A magic carrot behaves like a vanilla golden carrot for timing: its effect is a temporary breeding-mode-style window on the fed horse, consumed on breed, gone when the window lapses — not a permanent stored effect. During the window it is on the horse and part of the determinism input. Different carrot types show differently-coloured heart particles as feedback.
  • The mutinogenic carrot re-rolls epigenetics for every allele copy the fed parent passes on — expressing and non-expressing. One parent fed → half the foal’s copies re-rolled; both fed → all of them.
  • The seed jar stores enough of the sire’s record (not just his UUID) to place him correctly in the family tree. It also stores the genotype, not a frozen gamete — the draw is at impregnation, exactly like natural breeding.
  • A sheared horse gets a render-layer overlay — it only has to read as vaguely different, not look good; no coat-variant texture.
  • A gene that declares no magic-carrot rarity defaults to the gold-ingot tier, and a gene can opt out of having a magic carrot at all (sex, the recessive lethals).
