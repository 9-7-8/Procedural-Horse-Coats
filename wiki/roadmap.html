Shipped 2026-09-02. This was the architectural prerequisite for almost everything else here. What it is now lives on the pipeline page.

What is still open, and belongs to other sections:

  • Two magical genes stacked — settled 2026-09-02 by magic zebra and pink hair (§4.5). Straight signed add stays the blend; what changed is that magicalOrder() matters more than this section assumed, because a gene aiming at a specific colour reads the accumulator first and is order-dependent by choice.

2. Gene priority and processing order

Two priorities, at two levels

They are easy to confuse, so the names should stay distinct in code and docs.

1. Gene priority — hard-coded, per gene, decides processing order

  • Every Gene declares a fixed int priority. It is a constant of the gene, not data on a horse, and never varies between horses.
  • The phase is declared separately. Priority orders genes; it does not choose the phase.
  • 0–99 is the natural band by convention — where this mod’s real-world genes live.
  • 100 and up is the magical band. 100 itself is magical, and every three-or-more-digit priority is magical. The number inside the band is the author’s choice.
  • The band is a convention, not a constraint. Registering outside it logs a warning and carries on. The warning exists so a modder who squats on 50 finds out, not so the game refuses to start.
  • The engine walks all natural genes first, in ascending priority, then all magical genes. Because the bands are only a convention, the phase separates the two passes, not the number.
  • Ties break alphabetically by gene key, so two mods that both pick 5000 still produce one fixed, reproducible order. Arbitrary, but deterministic — which is the requirement.
  • The same order rolls a founder’s genes, so a gene can only ever look at genes with a lower priority than its own.

2. Epigenetic priority — per allele copy, decides which copy expresses

This one already exists and already works. It selects a seed, never an order. It cannot move a gene in the processing queue, and it must never be allowed to.

Founder spawn chance, and why it uses the same order

Every gene declares a flat 0–100% chance of appearing in a random founder, replacing the frequency each gene currently hand-rolls inside randomPair.

The chance may be genome-aware: a gene is handed the partial genome built so far and returns its own probability, so “champagne is twice as likely on a chestnut” is expressible without either gene knowing the other’s internals. That is only sound because founders are rolled in priority order, which means a gene can inspect only genes with a lower priority — so every magical gene can see every natural one, but not vice versa, and asking about a higher-priority gene is a programming error the registry should catch.

  • Multi-allele semantics need pinning down. “A 5% chance the gene appears” is clear for two alleles. With five it has to mean something like “5% chance this horse carries a non-wild-type allele, then a weighted second draw picks which” — and whether that draw is per allele copy or per horse changes how often homozygotes turn up.
  • The draw must stay deterministic given the RNG stream, so the roll order is the sorted order and nothing else.
  • This is the natural home for the weighted-allele helper §5.1 wants, and it is what lets a tier-1 declarative gene exist without any probability code.

What exists today

  • Processing order is two hand-written lists in Genes. Adding a gene means editing them, the ordering is not visible from the gene class, and a third-party gene cannot insert itself at all. Magical order stopped being cosmetic when pink hair started reading the accumulator, so this matters more than it did.
  • AlleleEpigenetics.priority works as described. Under this design that stays its only job — the planned second use (reordering genes) is explicitly rejected, and the Javadoc should say so.

The concrete changes

  • Gene gains int priority() — no default, so every gene has to answer.
  • Genes sorts. naturalOrder(), magicalOrder() and all() become derived: one sort on (priority, geneKey) at registry-freeze time. Keep the method names so callers do not change; make the lists a result, not a source.
  • codeOrder() uses the same comparator. A hand-written segment order is fine for a closed registry but breaks the moment a third-party gene exists — the code has to read the same on every install regardless of load order. Half of this is already live: drop-in genes (the file format) declare a priority and are sorted on (priority, key) after the built-ins, precisely so load order cannot matter. What is left is giving the eleven built-ins real priorities and deriving their order too, rather than keeping them as a hand-written prefix.
  • Check the band at registration, and only warn. Duplicate gene keys, by contrast, are a hard failure — that one really is unrecoverable.

The ordering constraint is an authoring rule, and needs writing down

Phase 1 is multiplicative restriction, which is commutative — except where a gene sets pigment absolutely. BayCoat sets its points absolutely, and the whole PigmentField.dilute design exists because the dilutions have to run after that. So the reserved band is not just a list of numbers, it is a dependency order: absolute setters get low numbers, dilutions get higher ones.

Document the constraint on PigmentField and on the priority field, or the next gene added at the wrong number will produce a bay whose mane does not dilute and nobody will know why.

3. Adding a gene: the modder-facing API

Partly shipped, 2026-09-02

Tier 1 exists, and it went further than the builder sketched below: a simple gene is now a JSON file rather than a fluent call, so it needs no code and no rebuild — see The gene file format and the gene creator that writes it. The registry is open for those: Genes.register(SpecGene) appends after the built-ins, sorted by declared priority then key, so registration order cannot decide how a horse looks.

Still open in this section: tier 2 (the abstract base classes), the mod-bus registration hook so another mod can add a Java gene, the built-in orderings being derived rather than hand-written (§2), and the genotype-code question at the bottom of this section — which the drop-in path makes more pressing, not less, since a player can now change the code's shape by moving a file.

A stated goal: adding a gene should be easy, for this mod and for other mods. A gene is still a hand-written class implementing an interface with eight methods, and three separate hand-written orderings have to be edited in step. §2 removes one third of that; the rest is this section.

Three tiers, so simple genes stay simple

Most genes on the backlog are one line of maths. Silver dapple is “multiply eumelanin by 0.45 and leave phaeomelanin alone”. It should not need a class.

Tier 1 — declarative shipped, as a file

What actually shipped is the file format, not this builder. Kept here because the builder is still the right shape for a Java gene that wants tier-1 brevity, and because the roadmap should show what was traded for what.

a builder for the common cases — no class at all
Gene.natural("mymod.silver")
    .priority(45)
    .alleles("Z", "z")          // most dominant first; last is wild type
    .dominance(DOMINANT)
    .wildFrequency(1, 60)       // 1 in 60 carries the variant
    .restrictBlack(0.55f)       // the whole coat effect
    .build();

Covers uniform dilutions, uniform restrictions, and “no coat effect at all” — the performance and health genes in §6, which only need alleles, inheritance and a trait contribution.

Tier 2 — abstract base classes

For a gene with real logic but a normal shape. AbstractNaturalGene and AbstractMagicalGene take the alleles, dominance and frequency in their constructor and pre-answer everything the interface asks except the one method that matters. An AbstractPatternGene on top adds the BodyNoise boilerplate and the “pull N epigenetic knobs off the expressing copy” helper that GreyCoat and BayCoat both hand-roll today.

Tier 3 — raw Gene

Still there for anything unusual. Nothing is taken away; the tiers just mean a modder rarely reaches this far.

What the base classes absorb, all of it boilerplate today: building the Allele objects and their keys, precedence, fromToken, randomPair from a declared frequency, the isVisible / isDeterministic defaults, the dominance metadata, and handing you the seeded RNG instead of making you find it.

An open registry

  • Genes becomes a real registry: register during startup, freeze, then serve. Frozen means codeOrder() and friends can be computed once and cached — they are on the hot path for every code parse.
  • The registration hook lives in neoforge-26.1.2/, not common/ — a mod-bus event (RegisterHorseGenesEvent) or a DeferredRegister-alike that calls into common’s plain-Java registry. That rule does not bend for this.
  • Load order must not matter — orderings are sorted, never registration order.
  • Genes need a namespaced key <modid>.<gene>; the existing convention already does this, so it is a validation rule, not a new format.

The allele rules and the contract a modder has to honour are already written up on Writing a gene — they are live rules, not future ones.

What third-party genes break

Open question: the genotype code gains a segment when a gene mod is added

Existing horses’ codes then have the wrong segment count. The mod’s standing rule is “no legacy / back-compat code” — but that rule was written for a single dev changing his own format, and “player installs a mod” is a different, normal event.

Needs a policy: pad missing segments with wild type on parse (forgiving, hides genuine corruption) or reject and re-roll (clean, loses the horse). Leaning toward padding, since it is exactly what “this horse does not carry that gene” means. Removing a mod is the mirror case: drop unknown segments, warn once.

  • The dimension stops caring once §8’s revert to random pens lands. A modded gene does still widen the per-pen sign, which is the one place a new gene shows up in the world.
  • CoatTextureId encodes the whole code into an Identifier path, so more genes means longer paths (§10).

4.5 Magical genes — the to-do list

Invented genes, phase 3, priority 100+. Unlike 4.1–4.4 this list has no upstream source to be complete against — add to it freely. Each needs a priority, an allele set with n as wild type, a spawn chance, and a delta function.

Shipped 2026-09-02

Magic zebra (Mzeb, dominant) and pink hair (Pihr, recessive — deliberately named “hair” rather than “mane and tail”). Magic zebra is explicitly not the natural zebra locus, which is still to come as a phase-1 gene.

Two things they settled: the unclamped signed model works in the negative direction exactly as sketched, and a magical gene that wants a specific colour has to read before it writes. coat/pattern/BodyStripes came out of zebra and is the shared stripe helper dun’s leg barring and brindle should use.

Cutie marks — the one still on the list

An emblem on each flank, mirrored left and right. It breaks new ground:

  • Placement needs a flank/haunch region in body space, mirrored across z = 0. CoatRegions has no such helper; it is a natural addition, useful to any gene wanting a patch in a specific place.
  • The mark itself can come from a sprite atlas or from procedural shapes. An atlas is far easier to make look good and is what the fiction wants — but it makes this the first gene with a texture dependency. common/ must stay Minecraft-free, so the atlas has to arrive as an int[] the way GradientLut already does, and a modder adding their own marks needs a way to register theirs.
  • How is the mark chosen? Allele per mark (each mark is a heritable, breedable thing — a family line has its mark) or one gene plus epigenetics (the mark varies continuously). The first is the more interesting breeding game and fits the philosophy better; the second scales to hundreds of marks without hundreds of alleles. A hybrid — alleles for mark families, epigenetics for variation within one — is probably the answer.
  • Colour is separate from shape and could be its own gene, making mark and colour independently heritable. More fun, one more locus.
  • Scale check: many alleles at one locus is exactly the case §5.1 has to support anyway, so this gene should come after multi-allele support.

Capability tests rather than planned genes: “add a red border to every white area” and “turn all the black to pink”. Neither is a committed gene; both are the acceptance test for whether a magical gene can actually see what is underneath it.

5. Loci that are not one-gene-two-alleles

Three structural assumptions get in the way, and all three are worth fixing before the gene rollout rather than during it.

5.1 Three or more alleles per locus

Mostly already supported, and better than expected:

  • AllelePair + Gene.precedence(allele) already order any number of alleles.
  • GenotypeCatalog.allPairsOf(gene) already enumerates n(n+1)/2 pairs for any n.
  • The code string already tolerates arbitrary tokens.

What does not hold:

  • Gene.dominance() is per gene, not per pair. With D/d1/d2, or W1…W36, different pairs at the same locus have different dominance relationships. DominancePattern needs to become a function of the pair — or a per-allele dominance rank plus a pairwise override table. GenotypeCatalog.distinctPairsOf is the caller that changes, and it is also the one that decides how big the gallery is.
  • randomPair(rng) is hand-rolled per gene, with the wild frequency baked into the draw. With 5 or 39 alleles that becomes a weighted table: declare an allele frequency weight and let one shared helper draw from it. That helper is also what tier-1 genes need in order to exist at all. A weighted draw changes founder draws only, not breeding draws — but the breeding page must be updated in step.

5.2 One physical gene, several traits

KIT carries dominant white, tobiano and sabino 1. MITF carries SW1, 3, 5, 6, 8, 10; PAX3 carries SW2, 4, 7, 9. MATP carries cream and pearl.

OptionTrade-off
(a) One Gene per physical locus, many allelesBiologically honest, gets linkage for free, and shrinks the genotype code. Costs the dominance-per-pair work, and a KIT class expressing many visually unrelated patterns.
(b) Keep them as separate genesWhat cream/pearl does today — and accept that impossible genotypes exist.

Recommend (a), starting with the cream/pearl merge: smallest case, and it already has a shared resolver (CreamPearlDilution) to fold in.

5.3 Sex-linked genes — the one non-Mendelian exception

Brindle (MBTPS2) is the driving case — a real coat gene, and a real X-linked one. Mares are XX and carry two copies; stallions are XY and carry one. So a stallion is never a carrier, and he passes his X to every daughter and no son. A mare shows a recessive X-linked trait only when homozygous. That asymmetry is the whole appeal: a trait that runs visibly down one side of a pedigree.

Sex itself becomes a gene

XX / XY registered like any other locus, alleles X and Y, at priority 1 so it is always resolved first. This is the change that makes the rest cheap:

  • Sex inheritance falls out of ordinary Mendelian breeding with no special case. A mare is X/X and can only pass X; a stallion is X/Y and passes one or the other 50/50 — exactly what the existing two nextBoolean() per gene already does.
  • It resolves the ordering problem by construction. X-linked genes need the foal’s sex before they can segregate, and at priority 1 the sex gene is already decided.
  • HorseRecord.sex should become derived, not stored alongside the genotype. Two sources of truth for the same fact is a bug waiting to happen. Keep Sex as the enum the rest of the code reads; compute it from the locus.
  • It gets sex into the genotype code, which the custom spawner and the family tree both want anyway.

Hemizygous notation

A hemizygous allele displays with an X- or Y- prefix — brindle’s Brn renders as X-Brn. Because - is the gene separator and can never appear inside an allele token, the prefix is unambiguous on sight. The code string is unaffected: the token stays Brn, and the game knows from the gene’s declared inheritance mode how to render it.

Proposal for the storage question (not yet decided)

Let the stallion’s second slot hold the reserved Y allele, meaning “this locus does not exist on the Y chromosome”. Then AllelePair stays two-slotted (no structural change to Genotype), Epigenome alignment survives untouched — the Y slot simply carries epigenetics nothing ever reads — and a stallion’s brindle locus reads Brn/Y, displayed X-Brn.

What still has to change

  • Gene declares its inheritance mode — autosomal (default) or X-linked.
  • breedWith grows one case: for an X-linked gene the sire contributes his X to a filly and his Y to a colt, rather than a free coin flip. The dam is unchanged.
  • Expression gets simpler, not harder. A hemizygous stallion has one real allele, so it expresses — no dominance question, and no epigenetic-priority tie-break.
  • GenotypeCatalog would otherwise produce nonsense pairs like Y/Y. It needs to know the mode.
  • The founder spawn chance has to respect sex: a colt gets one draw, a filly two.
  • Surfaces: the info panel and paper dump want hemizygous wording and the X- prefix, not a fake homozygote; a punnett square for an X-linked gene is a different square.

Not planned: Y-linked genes, imprinting, mosaicism.

6. Non-coat genes: performance, size, health

6.1 The shape of the change

Add capability interfaces a gene may additionally implement, rather than widening Gene with methods most genes ignore: 

interface StatContribution { void contribute(AllelePair, TraitBuilder); }  // speed, health, jump
interface BodyContribution { void contribute(AllelePair, BodyBuilder); }  // overall + per-part scale
interface ViabilityRule    { Viability check(AllelePair, Genotype); }     // lethal at conception / birth
interface ConditionRule    { void conditions(AllelePair, ConditionSink); } // CSNB, MCOA, deafness

Plus a common/horse/HorseTraits resolver that walks the genotype once and produces a plain-data Traits record (stats, body scale, conditions, viability). Same discipline as the coat: all of it in common/, with the server adapter translating to Minecraft attributes the way it already does for speed and health. It is also the tier-1 case from §3 — a performance gene has no coat effect, so declaring alleles plus one stat contribution should be the whole gene.

6.2 Stats become (partly) Mendelian

Target: the genetic contribution comes from HorseTraits, and the random roll survives only as environmental noise on top. Consequences: HorseRecord gains fields (jump, stamina, height); the breeding page would need a substantial rewrite; and backfillStatsIfMissing becomes “recompute from genotype”, which is better — it stops being a guess.

6.3 Polygenic traits — on the fence, may be cut

PDK4, CKM and the jumping QTLs are not single loci in reality. The model that fits the existing machinery is a marker set: N unlinked biallelic loci, each an ordinary tier-1 gene with an additive weight and no coat effect, summed by HorseTraits. No new inheritance code; the cost is N extra segments in the genotype code and an N-fold catalogue blow-up.

The argument against, and it is a good one

Atomic genes are more fun. A gene that does one legible thing is a gene a player can breed for. Five anonymous markers that sum into a hidden speed number are five segments nobody can aim at, and they push against the “a player should be able to plan” principle — a trait you can only influence statistically is exactly the kind of thing that reads as a dice roll. Atomic genes also give more customization surface in the spawner UI, and they are simpler for modders.

Three ways this can land:

  1. Cut polygenic entirely. Every performance trait becomes one atomic gene with a handful of alleles. Loses realism, gains legibility, removes a whole subsystem. Currently the leaning option.
  2. Keep it only where the realism earns it — the racing QTLs and nothing else.
  3. Fold it into group traits (§6.5), which are wanted regardless. A polygenic trait is the additive special case of a group trait.

Option 3 is worth checking before deciding option 1 — it may be that “polygenic” is just a TraitRule with a sum in it, in which case there is nothing to cut. Decide before the performance genes get written, since they are its only consumers.

6.4 Health: fewer hearts, and foals that do not make it

Aging is out of scope

Horses do not get older, do not grey out over time and do not accumulate age-related conditions — simulating that risks feeling bad for players who get attached to a horse. The option is deliberately left open (the composer would need an age input), but nothing here should assume it. Two consequences: grey’s fixed progression is a decision, not a gap, and melanoma is parked.

Sub-lethal: fewer hearts

A health gene lowers the horse’s max-health attribute, so an affected horse visibly has fewer hearts. This lands on an existing path — applyStatsToEntity already sets the MAX_HEALTH base value from the record — so the genetic contribution just becomes another input via HorseTraits. Cheapest possible mechanic, no new subsystem.

  • Watch the interaction with fullHeal: a foal born with a low max health should start at its max, and a reload must not heal it. The existing flag already draws that line correctly.
  • hasStats() treats 0.0 as “not recorded yet”, so a genetic health value must never resolve to exactly zero — clamp to a minimum (half a heart) and let the damage path do the killing.

Lethal: the foal dies shortly after birth

The foal is born — it gets a record, a name and a place in the family tree — and then takes damage until it dies. Mark it at birth from its ViabilityRule, and have a tick handler apply a small recurring damage over a few seconds rather than instantly, so the player sees what happened.

  • Needs a data attachment for the condition, a tick handler, and a damage source that reads as “genetic defect” rather than an unexplained death.
  • Give the player feedback — a chat line naming the condition beats a foal that silently drops dead.
  • HorseAncestryData already tolerates ancestors it cannot find, so a short-lived foal in the pedigree is fine.

Embryonic lethal (MET)

Checked at conception: if the drawn foal genotype is inviable, no foal is produced. The foal genotype is drawn before the check, so Genome.breedWith stays untouched and the check just reads its result.

Config toggle

A server/common setting, so it would be the mod’s first ServerConfig (ClientConfig exists but is the wrong side). Three positions, not two: full genetics with deaths; genetics and reduced hearts but no deaths; off.

Carrier display

Gene.dominance() already exists and is read only by GenotypeCatalog. “Carrier of X” wording in the info panel becomes far more valuable once recessive lethals exist — it is the difference between a breeding programme and a lottery. A punnett / expected-foal display is the natural companion.

6.5 Traits that come from a group of genes

Wanted, and not the same as §6.3’s additive marker sets: two or more genes, each with their own alleles, that only together trigger an outcome. This is epistasis / complementation, and it needs a home:

  • It is not a gene, so it cannot live on the Gene interface. It wants a separately registered thing — a TraitRule — that declares which gene keys it reads and is handed those pairs.
  • It is still Mendelian. Each gene inherits normally and independently; the rule just reads the result. No new inheritance code.
  • It may affect the coat — settled. That means a coat-affecting rule needs the same things a gene needs: a phase and a priority. Which argues strongly for modelling a TraitRule as a pseudo-gene: same delta function, same ordering, same determinism rules, differing only in that its inputs are several pairs instead of one. Reusing the gene pipeline wholesale is much cheaper than a parallel one, and the spawner UI and the coat cache need no special case.
  • The one thing it cannot inherit from Gene: it has no alleles of its own, so it contributes nothing to the genotype code and never appears in an allele lookup. Keep it out of codeOrder().
  • Determinism: rules must be sorted like genes, and a rule reading an unregistered gene has to fail loudly rather than default.
  • Visibility to the player. A trait with no single gene behind it is invisible in a genotype code and unguessable in a punnett square. It needs a UI surface of its own or it will read as randomness — exactly what the philosophy says not to do.

Cream + pearl looks like this case but is not: they are one physical locus modelled as two genes, and §5.2 merges them rather than writing a rule.

6.6 Status effects — to be specified

The third kind of gene effect is a list of “status-y” traits that has not been written down yet. The known ones are above; this is a placeholder for the rest, and the capability interfaces in 6.1 should not be considered final until it lands.

A first slice landed — the trait & effect architecture

A data-driven gene can already carry an effects block: a closed set of five verbs (traversal, attribute, emitter, mob_effect, yield) with boolean when conditions. The NeoForge translator runs three of them today (walk-on-water, particle trails, milk-a-mare — see the Waterborn example). The full behaviour system it is a slice of — triggers, selectors, auras, resource pools, goals, trait relations — is written up on that page and is otherwise unbuilt.

7. Horse care: milking and gated healing

Two features that apply to every horse, genes or no genes. Neither is genetic, but both interact with the genetics: health genes lower a horse’s max health, and healing is how it gets back to that max.

7.1 All adult mares can be milked

Right-click an adult mare with a bucket, get milk.

  • The sex is already there — a record lookup plus an age check, not new state.
  • Goes in HorseInteractionHandler, which already handles the clock and the stick. The trap it already documents: EntityInteract fires on both sides, and any item used on a tamed horse is otherwise turned into a mount by vanilla — so cancel on the client too, and do the bucket swap server-side.

The rules, settled

  • The mare must be tamed. An untamed mare is not a dairy animal.
  • The mare must be at full health. This is the hook into 7.2 — a horse that is not kept watered and fed does not heal, does not reach full health, and so cannot be milked. It also means a genetically frail horse is milkable at its max, not the species max.
  • Roughly an hour’s cooldown. Needs per-horse state: a small attachment holding the game time of the last milking. Pin down which hour — a real hour is 72,000 ticks; a Minecraft hour is 1,000, and a whole Minecraft day is 20 real minutes. Store the game time, not a countdown, so it survives a reload.
  • Milking a stallion gets you kicked: about half a heart of damage. Better than a silent no-op, and it makes the sex of a horse something the player learns by doing.
  • Foals do nothing — but say something, or it reads as a bug.

7.2 Horses only heal near water and food

A horse regains health only when near both a water source (water, flowing water, a water cauldron) and a food source (crops, grass, a hay bale).

  • Vanilla horses have no passive regeneration — they heal from being fed. So this adds a gated regen mechanic rather than gating an existing one.
  • Hand-feeding is exempt, and always works, with no water requirement. The gate is on passive regeneration only, so the player always has a direct, reliable way to heal a horse, and a stabled horse in a dry biome never becomes unhealable.
  • Use block tags, not a hard-coded list. horsegenetics:horse_water and horsegenetics:horse_food make the rule data-driven and let a pack or a modder add their own — the same extensibility argument as the gene registry.
  • Performance is the real design constraint. A block scan per horse per tick is not viable with a pen full of horses — and the horse dimension spawns them by the hundred. Scan on a slow interval (20–40 ticks), stagger the phase by entity id, cache the last answer on the entity, and keep the radius small.
  • The dimension’s pens already satisfy this by accident — every pen has a full water cauldron and a hay bale sunk flush with the grass. A free test bed, and worth not breaking when the pens change.
  • Interaction with the health genes: a horse heals toward its own max, so a frail horse with 4 hearts stops at 4. The lethal foals must out-damage this regen, or a lethal foal parked next to a hay bale never dies.
  • Player feedback: an unhealing horse is invisible until someone notices it is not recovering. Particles when it does heal, or a line in the info panel naming what is missing, turn a mystery into a mechanic.

8. The horse dimension: back to random pens

Revert the gallery. The catalogue-driven dimension goes back to random genotypes per pen. Keep the two things worth keeping: pairs (a mare and a stallion with the same genome) and a sign out front listing the genome.

This also resolves the combinatorial problem in §10 — a random corridor does not care that the genotype space is 1019, so the gallery stops being the thing that blocks adding genes.

What changes in the code

  • buildPen goes back to rolling a genotype per pen. Randomness here is legitimate: these are foundation horses with no parents, which is exactly where the determinism contract allows a draw.
  • The corridor stops having an end. LAST_SEGMENT_INDEX (currently 864, giving 6,055 blocks) and buildEndCap go away, or become an arbitrary length. The walk-ahead extension stays.
  • The entrance tally sign no longer means anything — drop it, or replace it with something true of a random corridor.
  • The per-pen sign stays.
  • The sign-fits test changes shape. It currently asserts every catalogue entry fits three 15-char lines. With random genotypes there is no finite list, so it becomes a property test over many random draws, or an assertion that wrap truncates gracefully. Do not just delete it — a sign that silently drops a gene is exactly the bug it was written for.
  • GenotypeCatalog itself can stay. The distinct-pair reduction is useful to a punnett display and to tests; it just stops driving the dimension.
  • One thing to re-check: “a rebuilt plot is byte-identical, so an X slot handed back to the free list can be overwritten in place” is no longer true once pens are random. Either air-fill on teardown, or confirm that overwriting a different random corridor leaves nothing stale — leftover signs from a longer previous corridor are the likely artifact.
Settled: the pair shares a genotype, not an epigenome

Both horses are independent founder rolls with only the genotype pinned, so a pen shows one genotype twice, differently. That is what the catalogue version already does, so buildPen needs no change here.

9. The custom horse spawner (creative only)

A creative-mode screen for building a horse gene by gene and spawning it. It is the tool the whole genetics system has been missing: today the only ways to see a specific genotype are to breed for it, walk the gallery, or bake samples outside the game.

What it does

  • Every registered gene, every allele. One row per gene, both allele copies selectable. Built off the registry, so a modded gene appears without the screen knowing about it.
  • Per-allele epigenetics. Each copy gets its priority and seed shown, a reroll button, and a type-it-in field for an exact value. The first place epigenetics become directly visible — a debugging tool as much as a creative one.
  • A live preview that redraws as the genotype changes.
  • Spawn.

Building it

  • Creative only, checked on the server. The screen opens client-side, but the spawn arrives as a payload and the server must re-check that the sender is in creative before acting. A client-side-only check is bypassable, and this payload spawns arbitrary entities.
  • The preview already has a proven technique. FamilyTreeScreen.drawHorseModel builds a render state from a throwaway client-only Horse and injects the coat straight onto the render state, deliberately without touching ClientCoatCache. Reuse it exactly — polluting the cache from a preview would leak edited horses into the world’s rendering.
  • The preview needs a coat per edit. Debounce, and reuse the texture key so an already-baked combination is free — the cache key is a pure function of the genome, which is exactly what makes this cheap.
  • The screen must scale to an unknown gene count. Nine genes fit on a screen; twenty-seven do not, and a modded install has no upper bound. Scrolling plus grouping from the start, not retrofitted.
  • 26.1.2’s GUI layer is retained-mode. FamilyTreeScreen is the working reference for a from-scratch screen in this codebase, including scissor clipping and the entity draw.
  • How is it opened? A creative-only item, a keybind, or a command. A keybind is closest to the existing pattern — but this should be gated on creative mode, not on a dev build, so it needs its own gate.
  • Round-trip the code. Paste a genotype code in, get the horse; copy the current horse’s code out. Nearly free once the screen exists, and it turns every bug report into something reproducible.

10. What breaks at scale

The master table is ~27 loci against today’s 11, several with many alleles, and third-party genes make the count open-ended. That is not a linear change.

  • The genotype space. Today 3^11 = 177,147 — it was 3^9 = 19,683 two genes ago, which is the multiplier in miniature. With the full table the raw product is on the order of 1.85 × 1019.
  • The gallery would have died — but it is being reverted anyway. Two genes quadrupling the corridor (434 pens / 1,519 blocks → 1,730 / 6,055) is the argument arriving early. If a systematic gallery is ever wanted again, the shape that scales is a wing per locus: each gene’s pairs on a fixed wild-type background, bounded by alleles rather than by their product, extending naturally to a modded gene adding its own wing.
  • The genotype code string. 27+ segments with tokens like SW10 / W36 puts a code in the low hundreds of characters. Everything carrying it grows in step — the record, the attachments, both sync payloads, and the epigenome code, which is already the fatter of the two. Worth a compact binary encoding for the payloads at that point; keep the string form for saves and debugging.
  • CoatTextureId and path length. The encoding expands (A-Z → 2 chars, anything else → 5), so a 300-character code becomes a >1,000-character path, which Identifier will not accept. The fix is to key the texture on a hash plus a short prefix, keeping the existing KEY_BY_ID tripwire — which caught the original flat-white-horse bug and would become load-bearing rather than paranoid, so give it a real collision-resolution path (append a counter) instead of throwing.
  • Wild-spawn frequency. With a dozen recessive lethals in the pool, founder frequencies need a pass: rare enough that wild horses are healthy, common enough that a breeder eventually meets one.
  • Display. At 27 loci the sign approach caps out; the info panel needs grouping (colour / pattern / performance / health) and probably scrolling.
  • Composer cost. Phase 1 is O(genes × texels) at 16,384 texels per sheet. 27 genes is still trivial; the pattern genes’ BodyNoise sampling is the real cost. Coats are cached per texture key, so this only bites on first bake — but the gallery bakes hundreds at once.

11. Suggested order of work

Each step is useful on its own and unblocks the next.

  1. Gene priority + derived orderings (§2). Small, self-contained, and it deletes the three hand-maintained lists that make every later step annoying. Add the determinism tests alongside it.
  2. Three-phase pipeline (§1). Done 2026-09-02 — and done before step 1, so the orderings are still hand-written lists waiting on it.
  3. The first magical genes (§4.5). Done 2026-09-02 — pink hair and magic zebra, with BodyStripes as the shared stripe helper. Cutie marks still come much later.
  4. The gene-authoring tiers (§3) — base classes first, the declarative builder second, the open registry third. Doing it here means every gene from step 5 onward is written the easy way instead of being rewritten later.
  5. Multi-allele support (§5.1) + merge cream and pearl into MATP. Smallest real multi-allele locus, with an existing resolver to fold in.
  6. Cheap coat genes, to bank wins: silver dapple, mushroom, roan — and to prove the tiers, silver should be about six lines.
  7. Health, the cheap half (§6.4): genetic contribution to max health. No new subsystem, visible immediately as hearts, and it makes the health genes worth carrying.
  8. Trait framework proper (§6.1) with MSTN as its first consumer, then the size genes once the entity-scale question is answered.
  9. Revert the dimension to random pens (§8) — small, and it unblocks adding genes freely. Could just as well go first; it is independent of everything above.
  10. Lethals (§6.4) — MET first (a conception check only, no death behaviour to design), then the born-and-dies path with its config toggle and carrier display. Note the ordering dependency on §7.2: a lethal foal has to out-damage the new regen.
  11. Sex as a gene, then sex-linked scaffolding, then brindle (§5.3). Registering X/Y at priority 1 is small and worth doing early. The scaffolding touches breedWith and GenotypeCatalog, so do it while the breeding tests are still small. Brindle is its proof.
  12. The pattern genes — tobiano, overo, LP, sabino — in ascending order of difficulty.
  13. Splash / SW series and KIT dominant white last: they need dominance-per-pair, they are the biggest combinatorial hit, and the two existing splash bugs should be fixed first.
Worth pulling early

The custom horse spawner (§9), as soon as the registry from step 4 exists. It is the fastest way to look at any genotype without breeding for it, so every gene after it is quicker to build and check.

Independent of the whole chain, doable whenever: milking (§7.1) and gated healing (§7.2). Neither touches the genetics, though 7.2 should land before the lethal foals, and milking’s full-health rule depends on 7.2 existing to be interesting.

Parked, and only worth doing if the decision changes: aging and everything downstream of it — grey progression over time, flea-bitten grey, melanoma. Eye colour as a channel is not parked but is independent of everything above; it unblocks tiger eye and blue-eyed creams whenever it is convenient.

12. Decisions still open

Settled — do not reopen

Kept here briefly so a later session does not relitigate them:

  • Phase 3 is a signed add/subtract on unclamped int channels, capped only at conversion, applied over the natural result — zebra is a large negative contribution, not a special case.
  • A magical gene can paint a dominant-white horse, because white is natural and magical genes run after.
  • A magical gene does see both the natural coat and the accumulated magical deltas.
  • One gene cannot act in both phases.
  • 100 is magical, and all three-digit priorities are magical; the 0–99 band is convention with a log warning, not enforcement.
  • Pen pairs share a genotype only.
  • Hand-feeding bypasses the healing gate.
  • Milking needs a tamed, full-health mare with a cooldown.
  • Allele tokens are alphanumeric, 1–128 chars, wild type n.
  • Group traits may affect the coat, so they get a phase and a priority like a gene.
  • Inheritance is Mendelian with exactly one exception — X-linked genes are in; crossing over, maternal inheritance and imprinting are not.
  • Sex is itself a gene (X/Y at priority 1), and a hemizygous allele displays with an X-/Y- prefix while the code string keeps the bare token.
  • Aging is out of scope; health is fewer hearts.
  • Linkage. Settled: no. Merging KIT still groups its alleles onto one locus, which is a modelling choice, not linkage.
