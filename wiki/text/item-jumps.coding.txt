Jumps
(Block / the yard)
A showjumping fence in three styles, and a real obstacle: like a fence, it cannot be stepped over . Place them side by side to widen it and on top of each other to raise it — there is no height setting, because the stack is the height — or set one directly, anywhere from a ground pole to double. One item : its height, its style, its two woods and its two coats of paint are all chosen after you put it down, by right-clicking it. And it is the first thing in the mod that makes a horse’s jump stat something you can watch rather than read.

Where it lives block/JumpBlock — the geometry, the connection rule, the VoxelShape , and the two use overrides that decide between stacking and opening the screen. block/JumpBlockEntity — the two woods, the client sync, and the implicit components that survive a break-and-replace. block/JumpMaterials — the pair itself, and the only place that knows it is two components on an item. block/JumpWoods — every wood a jump can be, the plank that stands for each, and what to call it. Read by the model, the screen, the item names and the tab. block/Jumps — the one item, and the placement hint. It registered twelve blocks and thirty-six items until 2026-09-20. menu/JumpMenu + client/JumpScreen — the two slots, the plank exchange, the dye, and the three style buttons. The menu carries the block’s position and reads it; see below for why it is not a ContainerData . client/JumpTintSource — the paint, as a block tint per half and an item tint per half. client/JumpModel — the custom block model that reads the two woods per position. See the API notes , because everything written before 1.21.4 is wrong about how one of these is built. tools/bake-jumps.mjs — every shipped asset, for vanilla’s woods, at author time. compat/GeneratedJumps — the same files for other mods’ woods, at run time. The woods are data, and the item carries two components Verified 2026-09-20, in play. The screen opens on a right-click, the style buttons change a placed jump, and a plank in a slot changes that half’s wood — owner, on the first build that had it: “the right click menu works (changing jump type, changing the color with new wood)”. Same session: “it works that the different jumps no longer connect”, so an oxer beside a vertical keeps both sets of standards. Still unseen: a jump whose two halves are different woods, which is the thing the whole rework exists for, and every part of the paint. See the Verification tab . The owner’s ask was that the standards and the rails be independently coloured. As blockstate properties that pair is 12 × 12 × everything else — 13,824 block states , every one allocated at registry bootstrap on the server as well as the client. So the woods are JumpBlockEntity data and the model reads them per position, which is what collapsed twelve blocks into one. On the item they are two separate string components , horsegenetics:jump_rails and horsegenetics:jump_standards , rather than one pair-valued component — and the reason is the icon. minecraft:select on minecraft:component matches the whole value of one component, so a pair would need a case per pair: a hundred and forty-four per style, for a sixteen-pixel picture. Split, the icon selects on the rails alone in twelve cases and is never wrong about the half it shows. Both are always present , oak included, on every jump the mod hands out — the recipes write them, the creative tab writes them, the loot table copies them off the block entity. An item with no components and an item saying “oak” are the same jump but do not stack, and a creative-tab jump that will not stack with a crafted one gets reported as an inventory bug. The round trip is four pieces and all four are needed. collectImplicitComponents puts the woods on the way out; minecraft:copy_components with "source": "block_entity" in the loot table is what asks for them; setPlacedBy puts them back into the block entity on placement; and removeComponentsFromTag discards the block-entity copy so the item does not carry the same woods twice and let the stale copy win. Miss any one and a birch-railed jump comes back oak — which reads as “the screen did not save”, not as a loot bug. Paint is a tint, and here that is the right tool The wood could never have been a tint — multiplying a colour over birch grain does not produce jungle grain, which is the reason the woods became block-entity data and a per-position model in the first place. Paint is the opposite case. It is a colour laid over a wood that still shows through, which is exactly what a multiply does, so the mechanism vanilla dyes leather with is the honest one here. It also cost almost nothing, because the two halves were already separate model parts. Tagging every rail face tintindex: 0 and every upright face tintindex: 1 is the entire model change. The tint index is a list index, in three places that nothing checks against each other. RegisterColorHandlersEvent.BlockTintSources.register takes a list of BlockTintSource and its position is the model’s tintindex — not the per-index lambda every older version and every tutorial has ( coding notes ). So the order in JumpTintSource.BLOCK_SOURCES , the RAILS_TINT / STANDARDS_TINT constants in bake-jumps.mjs , and the tints array in items/jump.json are one contract in three languages. A swap shows as a jump whose rails take the colour you painted its uprights, and logs nothing. colorInWorld runs on chunk-meshing worker threads , exactly as JumpModel.collectParts does and against the same region snapshot, so it reads the colours through getModelData rather than through getBlockEntity . That is the same reason JumpMaterials is an immutable record. The screen reads the block, because a ContainerData is 16 bits The menu carried a three-int ContainerData — style, and two indices into the wood list — and it worked until paint arrived and it could not. ClientboundContainerSetDataPacket reads and writes its value with readShort / writeShort , so every value in a ContainerData is silently truncated to sixteen bits , and an RGB colour needs twenty-four. Splitting each colour across two slots would have worked and would have been a lie about what a menu’s data vector is for. Instead the menu carries the block’s position , written into its opening packet by NeoForge’s extra-data menu factory ( IMenuTypeExtension.create ), and both sides read everything off the block: the style from its blockstate, the woods and the paint from its block entity. The client already has that block entity — it has to, because the model reads the woods — so the screen is showing the same values the model is drawing with by construction , rather than by two code paths agreeing. Stacking beats the screen, and that needed an override ServerPlayerGameMode.useItemOn calls a block’s useWithoutItem whenever its useItemOn returns TRY_WITH_EMPTY_HAND — the hand does not have to be empty , despite the name. Only a sneaking player with something in their hands suppresses it. So a block that opens a screen from useWithoutItem opens it even when the player is holding the block itself. For a chest that is fine. For a jump it is not: height is stacking , so putting one on top of another is the most common thing anybody does to this block, and it would have needed a shift-click forever. JumpBlock.useItemOn therefore returns InteractionResult.PASS — which is not a TryEmptyHandInteraction , so the dispatch skips the screen and falls through to the item’s own useOn — for a JumpItem and only for one. The collision box is taller than the model JumpBlock.getCollisionShape returns the same boxes as getShape but topped at 24/16 rather than 15 and 16 — vanilla’s own fence number. The outline and the model stay tight to the rail, so the block still looks right; only what you bump into is taller. Verified 2026-09-20, in play, and this is why it exists. The first build let collision follow the model, which put the rail under a horse’s 1.0 step height. Owner’s verdict: the jumps “look great, expand great”, but a horse walked straight over them and it “doesn’t feel immersive”. The fix is the fence trick and nothing else — no model change, no new state. Two consequences worth knowing before changing it. The render and collision shapes are built by one function with two different tops , and the rail and the standards do not share a top in the drawn shape (15 and 16) — collapsing those into one number quietly lops a pixel off every post. And the tall box applies to players as much as horses, so a course cannot be crossed on foot. That is intended, and it is what a fence does. The crossrails are not UV-locked The X is drawn with model element rotation , which vanilla caps at 45° about one axis — exactly enough for a crossrail and no more. A 16-long bar turned 45° projects to about 11 across, so it stays inside its own block. That is why crossrails do not run together the way the other two styles do: each is its own X. Intended, not a limitation waiting to be fixed. UNVERIFIED, and reasoning rather than observation: the crossrails blockstate sets uvlock: false where the other styles set true. UV-lock re-projects a face’s texture against the block axes after the blockstate’s y rotation, and on an element that is itself rotated 45° the two rotations fight and the grain shears. The axis-aligned styles lock cleanly. Worth looking at a crossrail facing each of the four ways before trusting it. The geometry is written three times This is the thing to be careful about. The same shape exists as boxes in bake-jumps.mjs , as a VoxelShape in JumpBlock , and again in GeneratedJumps for modded woods. Change one, change all three. Each drift fails differently and none of them logs. Model against shape gives you a jump you can see in one place and collide with in another. Baker against generator gives you a modded jump that is a purple cube while every vanilla one is fine. Left, right, and the suffix that was wrong LEFT and RIGHT are fence-style connection flags: true means another jump continues the rail on that side, so the standard there is not drawn. Left is facing.getCounterClockWise() , the same definition DoubleGates.partnerDirection uses — keep the two families agreeing about which way is left. Verified 2026-09-20, by check-block-models.mjs , on its first run. The blockstate composed its model suffix as (left?"_l":"") + (right?"_r":"") , giving _l_r , while the models were written _lr . Only the both-connected case differs, so a lone jump and a row of two were perfect and the middle of every row of three was a purple cube. Both generators now derive the suffix from one function rather than composing it, and the check is a repo tool: node neoforge-26.1.2/tools/check-block-models.mjs , which walks every blockstate, item definition and model parent and asserts the file is there. It covers the shipped assets only — the run-time generated pack is not on disk and is still guarded by nothing but the class docs. The axe tag is shared, so it merges mineable/axe holds the double gates as well, and a datapack has exactly one file per tag. Both bakers therefore merge into it rather than writing {values: ours} , and GeneratedGates.mergeBlockTag does the same for the run-time pack so it does not matter which generator runs first. Getting this wrong is worth describing because of how quietly it fails: the losing family keeps working, mines slowly, and drops nothing without an axe. That reads as a balance decision, not a bug, and could sit there for months. After running either baker, check both families are still in the tag. Unverified The look and the connection behaviour were confirmed in play on 2026-09-20 — they “look great, expand great”, and the row-of-three case that was broken drew correctly. The height ladder has not been ridden. It follows from a 1.5-block collision box and a horse’s 1.0 step height, and which rung a given horse stops at is exactly the thing still to be measured — along with whether it agrees with HorseUnits.jumpMetres .
