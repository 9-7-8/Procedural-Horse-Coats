Horse shoes
(Horse gear / hoof equipment)
Horse shoes are the first true hoof item in the accessories system: one item per hoof, each with its own material, enchantment and durability, yet all of them living under the same attachment-backed gear model the rest of the horse gear uses. They are not a special case on the horse; they are four independent stacks sharing one shared rule set. Any metal can be used, and the tier of that metal is what decides how much the shoe increases the horse's movement stats.

Shared architecture The shoe system should sit directly on top of the gear model already built in Horse gear: the nineteen slots . The horse stores four worn stacks in the same attachment-backed pattern; the slot roster names the four hoof slots; the item stack holds the material and enchantments; and a horse-side effect manager aggregates the four shoe states into a single effective result. This keeps the logic parallel to the rest of the mod instead of inventing a separate inventory toy that is only valid for shoes. Slot layer The slot layer is the first part of the implementation. Add the four shoe slot keys to HorseTackSlot as their own entries, each with its own item tag and its own hoof anchor on the paper doll. That is the part that decides the horse can accept a real shoe item and refuses all other gear; it is not the effect system itself. Item layer Each shoe should be a genuine item stack carrying a material identity and enchantments. The horse attachment stores the stack only for the one hoof slot, and any effect calculations read the item from that stack rather than from a hidden shoe state elsewhere. This gives the system the correct shape for item-level enchantments and keeps the worn item as the source of truth. Effect layer The effect layer should aggregate the four shoe stacks into a single readout for the horse. It should ask: which shoes are present, what material are they, which enchantments are on them, and what is the total effect at this moment? The calculation must be additive but bounded: one shoe should not silently turn off the other three, and one enchantment should not overwrite the effect profile of another simply because it was the last shoe to be read. Render layer A shoe should render from the underside of the hoof, with four independent render roots. It should be slightly larger than the horse model's hoof so the rim is visible, and it should extend down into the ground by a small, deliberate amount. That intersection is part of the silhouette: the shoe should read as weight-bearing hardware seated under the foot, not as a floating ring or a plate pasted over the hoof. This is not a body-layer feature. The first pass should prove one front shoe and one hind shoe before adding the full set, because the hoof scale, ground intersection and body overlap are the parts most likely to look wrong in a way that is easy to miss in code review. Enchanting rules This is the design call I would make explicit before the first shoe item ships: each shoe is enchantable as an item, and the enchantment belongs to that item rather than to the horse as a whole. One front left shoe can be enchanted for grip while the right front shoe remains plain, and the horse-side logic sums what the actual worn stacks say. That means the shoe effect model is read from the item stacks themselves, while the material tier continues to provide the base motion bonus. Some enchantments are purely special abilities layered on top of the basic speed/jump bonus, while others may modify the effect profile of the shoe around a specific terrain or use case. Enchantments are per shoe. A horse has four separate shoe stacks, and each stack can be different. Effect legality must be slot-aware. Not every enchantment should be legal on every hoof, and not every enchantment should be legal on every material. Enchantments survive reloads. A shoe is data-bound to the horse attachment, not to a one-shot state flag, so the item stack remains the source of truth after a save and reload. Powered-snow behavior is universal. The powered-snow walk trait is a base feature of all shoes, regardless of metal or enchantment, so even a plain shoe is useful and not only a stat stick. First effects to implement I would start with a very small, mechanically clear set and not build a giant pencil-box of abilities in the same pass. The first systems worth shipping are: Base movement tier bonus. Each shoe grants a flat jump and speed bonus based on the metal tier, with the material profile defining the exact value. Grip on slick ground. The first real utility effect for a shoe: it gives a safe traction path on wet, icy or muddy ground without making every ride a friction puzzle. Reduced slipping. A modest horse-side effect that lowers slide and stabilizes footing on the same terrain families the mod already reasons about. Durability cost. Shoes are consumable gear, not free decorations. The effect should be felt in the wear profile the same way armour or equipment wear is felt elsewhere in the mod. This leaves space for a later expansion to stronger effect roots such as hot-ground protection, quiet movement, or a more explicit jumping / movement bonus if the project ever wants that level of mechanical complexity. In practice, the material tier already provides the base jump and speed boost, and enchantments layer on the special-case abilities without replacing the universal metal bonus. Bench and crafting path Shoe crafting should ride the same material-generation pipeline as the other tack items rather than be a separate one-off recipe list. The bench determines the material shape and style, the material scan decides what is legal, and the shoe item stack carries the result. That keeps shoe creation inside the same system as the rest of the gear architecture instead of making it a disconnected feature that only the horseshoe page understands.
