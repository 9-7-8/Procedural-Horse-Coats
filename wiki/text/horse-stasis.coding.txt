Horse stasis: chambers and the bank
(Gameplay / partly built)
A cheap way to hold horses without them costing server tick time. A stasis chamber is an item a horse goes into; a Horse Stasis Bank is a block that will hold many chambers and give them a browsable UI. The whole point is the cheapest tier, so a server with hundreds of horses can put most of them somewhere that costs nothing, instead of every horse being a real, ticking entity forever. The four chambers are built and work. The bank, and everything that depends on a bank, is not.

Capture and release: it is the lycanthropy swap This page used to say that capture/release of a live, specific entity was “new work with no existing analog in the mod” . That was wrong, and finding out it was wrong is most of why stage one was cheap. LycanthropyHandler has carried a whole horse through a night spent inside a wolf since the LYCAN gene shipped, and it does it with exactly two calls: horse.saveWithoutId(TagValueOutput) a CompoundTag , then horse.discard() . EntityType.HORSE.create(level, EntitySpawnReason.LOAD) horse.load(TagValueInput.create(...)) level.addFreshEntity(horse) . On NeoForge saveWithoutId carries the data attachments , and it stores the entity's UUID . That is the whole reason this shape is right and the one this page originally sketched was not: a released horse is the same horse down to the id that the ancestry database, every pedigree, every stall sign and every transfer deed key on. The sketch — a record enumerating horse_record , horse_gear , horse_care and friends by hand — would have lost the id, lost every vanilla field nobody listed (age, custom name, leash, the saddle in the vanilla slot), and rotted the first time somebody added a fifteenth attachment without thinking of that file. Where the snapshot had to live, against the plan The plan wanted StasisSnapshot in common/ so the web designer and a future 1.12.2 port could read a chamber. A tag-based capture cannot go there: CompoundTag is a Minecraft type and common/ imports none (hard rule 1). So the split is common/…/horse/StasisTier.java — the four tiers and their capability flags, the one part with no Minecraft in it, with StasisTierTest pinning the ladder — and neoforge/…/data/StasisSnapshot.java for the capture itself. Correct restoration beat portability; the portable half is the half that had something to port. What is where File What it does common/…/horse/StasisTier.java The four tiers and what each unlocks, as cumulative flags rather than a name the UI switches on. neoforge/…/data/StasisSnapshot.java Name, id and the horse's whole saveWithoutId tag, with its codec and stream codec. neoforge/…/data/ModDataComponents.java STASIS_SNAPSHOT . Absent means an empty chamber — that is the whole of the item's state machine. neoforge/…/item/StasisChamberItem.java One class, four registrations, parameterised by tier the way TicketItem is. Holds release ( useOn ) and the tooltip. neoforge/…/server/HorseStasisHandler.java Capture, release and the already-loose guard. neoforge/…/server/recipe/StasisChamberRecipe.java The Basic recipe, custom only so the water container comes back. neoforge/…/server/recipe/StasisUpgradeRecipe.java All three upgrades, custom so an occupied chamber keeps its horse. Why two of these are Java recipes Neither is a CustomRecipe for the fun of it, and both reasons are worth keeping: The water container is not consumed. A vanilla recipe eats every input. StasisChamberRecipe overrides getRemainingItems and hands back the input's own declared crafting remainder — which is how a vanilla water bucket returns an empty bucket, the same as in a cake. The ingredient is matched on c:buckets/water ( Tags.Items.BUCKETS_WATER ), so another mod's container crafts it without anyone naming it here. An upgrade must carry the horse. A shapeless JSON recipe builds its result from scratch and copies no components, so upgrading an occupied chamber would hand back an empty one and delete the animal — silently, with nothing in the log. StasisUpgradeRecipe copies the stasis_snapshot across. The JSON version of this feature is not a cheaper version of it; it is a data-loss bug with a crafting recipe attached. Both serializers are unit codecs, and that is load-bearing Each recipe has one INSTANCE shared by MapCodec.unit(INSTANCE) (the value overload) and StreamCodec.unit(INSTANCE) . A supplier-based map codec decodes a different object, the stream codec's identity check then throws, and because NeoForge sends the whole recipe set to every joining client as one payload, that is a login kick on every dedicated server — which shipped once, in v0.5.014. Singleplayer never encodes a recipe, so nothing short of a real join catches it. See api-notes.html . The every_recipe_encodes gametest is the cheap version of that join, and both of these pass it. The component syncs the whole tag, on purpose It is tempting to give STASIS_SNAPSHOT a lossy stream codec that sends only the name and the id, since that is all a tooltip needs, and keep the heavy tag server-side. That is wrong, and the reason is creative mode: a creative pick-block sends the client's copy of a stack back to the server, so anything the client was never told is anything a creative player can quietly erase. The whole tag goes over the wire. Bandwidth is therefore a real question for the bank, where fifty-four of them sit in one container — not for an item in a hand. Small decisions inside release Position comes from the chamber, not the tag. The tag remembers where the horse was captured, which may be a world away; where you open it is where it wakes up, with its velocity zeroed. It starts fed. Hunger is explicitly reset to Hunger.FULL , matching the hunger attachment's own rule that a re-summoned horse is not starving. It is also the only honest answer when the horse has been outside time. A horse that will not load stays in the chamber. If load throws, nothing is consumed and the chamber is unchanged, so a later build may still be able to read it. The alternative is destroying a pedigreed animal to tidy up an exception.
