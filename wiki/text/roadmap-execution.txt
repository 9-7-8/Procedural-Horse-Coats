It is an execution guide, not a second backlog: the owning page remains the source of truth for each feature. Route every request first The intake file is an inbox, not a plan. Before implementation, give each request one owner and one state. A sentence that describes something already built but wrong belongs in Known gaps . A question whose answer changes the design belongs in Design decisions . Something built but unseen belongs on the owning page’s Verification tab. Implementation handoff packet A new implementation session should not rediscover the repository. First run node wiki/tools/check-roadmap-execution.mjs , then read this page, the owning page named below, and only the listed anchors. Form one local hypothesis, run the listed focused check if it already exists, then edit the smallest owning slice. If the check cannot run because the behaviour is NeoForge-only, write the runtime reproduction before searching further. Token-saving session contract Do not reread every roadmap page, search every occurrence of a concept, or design the whole subsystem before the first focused check. Do not change production code merely to make a test seam convenient. If a required test cannot be written without a NeoForge harness, leave the production path untouched, record the exact runtime reproduction on the owning Verification tab, and continue with the next independently testable slice. Session start and closeout packet Copy this small packet into the session notes before implementation. It is deliberately shorter than a design document: its job is to preserve routing and evidence between sessions. Slice: Owner page: Production anchors: Hypothesis: Disconfirming check: First edit: Focused result: Tests added or run: Generated artefacts updated: Runtime checks still needed: Next blocked gate: Closeout is complete when the focused result is recorded, the owning page says what is now true, generated artefacts are current, and the next session can begin from the named blocked gate without rereading the whole project. A session that found only that the report was stale should record that result and stop; it should not invent a replacement feature. Fixes and tuning come first Before starting new content, clear the existing behaviour that players already depend on. The order below is by breadth of impact, not by how visible the symptom is. Each stage gets unit tests at its owning boundary and a small in-game matrix afterward. Do not hide a defect inside a new system just because the new system touches the same code. 1. Persistent identity and record retrieval Fix the widest shared seam first: a browser listing, a live entity, a client record and an ancestry record must all resolve to the same horse UUID. Add an explicit server request for a horse record by UUID. Do not reuse an entity-id request or assume that a family-tree request can answer for an unrelated horse. Make cache misses, unloaded horses, sold horses, dead horses, transfers and entity-id reuse deliberate states rather than silent no-ops. Unit tests: record lookup by UUID, cache hit and miss, stale entity-id rejection, transfer ownership, sold/dead historical rows, roster pagination, roster version refresh and filters over a horse beyond the old roster cap. The common query tests must cover gelding, exact genotype, carrier, sold, dead, unloaded and owner predicates. 2. Interaction routing and screen lifecycle Route every way into the information screen through one tested decision: H-menu row or portrait, family-tree link, breeding-picker row, vanilla inventory button, sneak-and-use, and the inventory key. A My Horses row must fetch its full record before opening, including when the horse is not loaded. Define the fallback when the record is unavailable. Then test the parent-screen stack, Escape, the inventory key, pending requests, disconnects, stale selections and the inspect-hold lease. Unit tests: HorseBrowserNavigationTest , HorseInfoInteractionTest , HorseRecordRequestTest and HorseScreenLifecycleTest . Their cases must cover plain click versus sneak-click, empty hand versus named items, main hand versus offhand, tamed versus wild horse, horse versus donkey/mule, branded horse, missing client cache, and singleplayer versus dedicated server. 3. Navigation failure and AI arbitration Make a failed bond path release MOVE rather than leaving the goal active while the horse stands still. Re-check canUse and canContinueToUse when the owner is behind a door or fence, outside follow range, offline, in another dimension, dead, or outside simulation distance. Then make the priority contract explicit for bond following, breeding, feeding, dropped-food pickup, herd movement, panic, low-health escape and fence avoidance. A horse that cannot reach its owner must resume normal behaviour. Unit tests: fake-navigation tests for route found, route refused and route lost mid-follow; goal arbitration tests for food versus taming, bond versus breeding, panic versus bond, and escape versus every other movement goal; and threshold tests for follow range, stop distance, healing back above the low-health threshold and dimension changes. 4. Breeding, food and boundary corrections Fix dropped diet food, crop eating through barriers, pasture-edge pushing and low-health escape as one movement/feeding pass. For breeding, make stallion coverage server-authoritative, configurable and repeatable each day; preserve line breeding; and report every refusal once per meaningful attempt rather than once per tick. Test two stallions racing for one mare, full capacity, changing capacity, pregnancy beginning, ownership changing, unload/reload and natural versus manual breeding. Unit tests: cover decision outcomes and refusal reasons, capacity and config authority, line-breeding acceptance, food-tag matching, barrier visibility, crop reachability, boundary steering and low-health panic transitions. Add a regression test that a failed cover cannot spam the same player indefinitely. 5. Ownership events, alerts and history Build the event path only after identity is stable. Record births, successful and failed covers, deaths, taming, purchases, sales and transfers at the server authority, with a stable horse UUID, timestamp, event type, result and refusal reason. Deduplicate damage/death hooks, target damage messages only to the owner, keep death announcements configurable, and retain sold/dead rows in family history. Persist enough history for reconnect and bound its size. Unit tests: event construction, ordering ties, deduplication, persistence, bounded retention, owner-only damage routing, server-wide death routing, transfer attribution, offline owner lookup and log filters. Include save/reload tests, not just an in-memory list. 6. UI and equipment actions Only after record retrieval and server actions are reliable, fix saddle placement, barn-name editing, duplicated naming, allele and exact-genotype filters, the H-menu row action, the horizontal tab strip, player inventory placement, and equip-all/unequip-all. Every action must resolve a UUID on the server, validate ownership and slot acceptance, and report a full inventory or rejected slot without deleting or duplicating items. Unit tests: layout bounds at narrow and wide GUI scales, tab hit testing and keyboard focus, filter parsing, family-name selection, slot acceptance, atomic equipment swaps, partial equip results, full-inventory handling, close-during-transfer and entity-id reuse. Re-test resized horses and all vanilla saddle/barding paths alongside custom tack. The required hardening matrix Each stage is incomplete until its tests pass across these states: loaded and unloaded; tracked and untracked; alive, dead and sold; owned, transferred and unowned; owner online and offline; one horse and many horses; success and refusal; menu open and menu closed; save/reload between actions; singleplayer and dedicated server. The same matrix should be used for the H menu, the info screen, breeding, notifications and equipment rather than inventing a new partial checklist for each feature. This pass is complete when every stage has a focused unit-test class, its integration matrix has been played, and any remaining behaviour is recorded as a deliberate decision or known gap. Only then should a session spend its main effort on new content. New-content vertical slices in dependency order After the fixes pass, these are the recommended clusters from the current intake. Each slice should cross the relevant common model, server behaviour, client surface and tests when those layers apply. Do not build a large foundation without one player-visible proof using it. Breeding and horse behaviour Owner: Fertility & gestation and Horse care . Combine stallion coverage, configurable local capacity, breeding failure messages, unrestricted line breeding, path-aware bond following, dropped-food eating and fence/crop avoidance into one behaviour pass. The slice is complete when an owned pen and a wild band both demonstrate the same explicit rules, the capacity is server-authoritative, and every refused cover has a reason visible to the relevant player. Gate: decide whether “no incest prevention” means no breeding restriction at all or only no automatic rejection; decide whether a full-pen refusal is a failed attempt or a blocked attempt. Test owner interaction, wild behaviour, config changes, unloaded horses and enclosed paths before adding polish. Owned horses and records Owner: The horse browser , with Villagers & transfer papers for selling and naming. Build the server-side owned-horse registry first. Then sold horses can remain greyed out, damage and death notices can target the owner, the barn can carry a name, and the browser can refresh on birth, death, taming and transfer without inventing separate ancestry scans. The H-menu Log tab — successful and failed covers, births, deaths, taming, purchases, sales and transfers, recorded while the menu is closed — shipped ahead of the registry (2026-09-24) by keying its own store on the owner's UUID rather than waiting for one; it is therefore not a reason to defer the registry, and the registry is still what the rest of this slice needs. First proof: register one horse, sell it, damage it, kill it and breed a new one while its chunk is unloaded. The browser must retain the historical row, show the correct owner-facing notifications and refresh from server state rather than from a client guess. Gear and visual attachments Owner: Horse gear , then Attached model parts and Flying for wings. Start with one complete attachment: stack data, valid-slot rules, network update, persistence, overview placement and a render layer. The first menu proof must also place the normal player inventory on the gear tab, support scrolling tabs and expose equip-all and unequip-all actions using the same server-side slot validation. Only after that proof should the project add horse wings, more tack, dyed variants or larger loot coverage. Elytra texture reuse is an art and model compatibility question, not a reason to bypass the horse attachment contract. Loot and acquisition Owners: Items & recipes and Villagers & transfer papers . Treat more common gene books, carrots and dyed armour as data-only loot work. Treat obtaining cowboy horses without emeralds as a separate gameplay decision with its own route, cost and ownership transition. This keeps a loot-table tuning pass from silently changing the cowboy economy. Horse discovery and naming Owner: The horse browser and Breeding & pedigree . Define the query language before the widgets: carries an allele, exact X/X genotype, sex-linked display, and owned, sold or dead status. Then implement server-side filtering and the family-name rule as data resolved once per listing. This makes the H-menu search, breeding pickers and future paper tools share one predicate instead of growing parallel filters. The H-menu additions are one browser slice. The tab-strip overflow control and the newest-first Log tab with event-type filters are both built; what is left here is the gear-tab inventory and bulk equipment actions. The Log tab's acceptance check — a successful cover, a failed cover, a birth, a death, taming and a purchase while the menu is closed, then reconnect, filtering and newest-first ordering — is written out on the browser's Verification tab and has not been played. A gate is finished only when its answer is written on the decision page or the owning page, and the losing alternatives are removed from the implementation plan. Otherwise the next session will spend its first hour reopening the same question. The execution loop Choose one slice. Name the player-visible outcome and its owning page. Read the gate. Check decisions, known gaps and nearby Verification items before touching code. Find the narrowest owner. Put rules in common/ when they are game-free; keep NeoForge as translation and orchestration. Make the smallest end-to-end edit. Prefer one real item, one query, one notification or one behaviour over an empty framework. Run the cheapest falsifying check immediately. Use a focused test, fixture, parity check or narrow build before expanding the slice. Regenerate every derived artefact. Follow the build table , especially golden coats, WASM, generated wiki pages and search indexes. Update the owning page. Move shipped work off Roadmap, record what was seen on Coding, and leave only genuinely unbuilt work behind. Stop at a clean boundary. Record the next blocked gate and the one best next check in the session log. The slice brief Before implementation, write this compact brief on the owning page or in the session notes: Outcome: one sentence a player can observe. Owner: one wiki page and one primary code owner. Decision gate: the answer that must already be settled. Prerequisites: existing data, attachment, payload or UI contract. First proof: the smallest complete path from input to visible result. Acceptance: observable pass conditions, including refusal and failure cases. Checks: the cheapest focused test, then required regeneration commands. Out of scope: adjacent ideas deliberately left for a later slice.
