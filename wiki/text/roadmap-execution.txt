Project / how to turn plans into small shippable slices Roadmap execution The roadmap says what is not built. This page says how to choose the next slice without making a later session rediscover the dependencies, decisions and checks. It is an execution guide, not a second backlog: the owning page remains the source of truth for each feature. Route every request first Before implementation, give each request one owner and one state. There are two queues, and each has its own routine. Something built but wrong is a bug : it is a GitHub issue labelled bug . The cloud session files it by procedures/report-bug.txt ( /report-bug ), the yard's “run tests” routine files what it finds, and /fix-bug fixes one issue per session. Something not built yet is a feature : it is scoped into an implementation treatment in intake/ by procedures/write-intake-document.txt , and /process-intake builds one piece of it per session. intake/ holds features only, never bugs. A question whose answer changes the design belongs in Design decisions . Something built but unseen belongs on the owning page’s Verification tab. A plan with an agreed shape that nobody is building yet belongs on that page’s Roadmap tab. Request shape Owner Next action Built and wrong A GitHub issue ( bug ; needs-owner if it waits on the owner) Record the observed failure, the version and the cheapest discriminating check. /fix-bug takes one per session. Built, not seen The feature’s Verification tab Write a pass condition and where to look in-game. Design is unresolved Design decisions Answer the gate before writing implementation code. Wanted, not yet scoped A treatment in intake/ Scope it with the owner by procedures/write-intake-document.txt : pieces, decisions, release. Shape is agreed, work is absent The treatment, or the feature’s Roadmap tab Define prerequisites, a first vertical slice and its acceptance test. /process-intake builds one piece per session. Implementation handoff packet A new implementation session should not rediscover the repository. First run node wiki/tools/check-roadmap-execution.mjs , then read this page, the owning page named below, and only the listed anchors. Form one local hypothesis, run the listed focused check if it already exists, then edit the smallest owning slice. If the check cannot run because the behaviour is NeoForge-only, write the runtime reproduction before searching further. Token-saving session contract Do not reread every roadmap page, search every occurrence of a concept, or design the whole subsystem before the first focused check. Do not change production code merely to make a test seam convenient. If a required test cannot be written without a NeoForge harness, leave the production path untouched, record the exact runtime reproduction on the owning Verification tab, and continue with the next independently testable slice. routing audit Known gaps is no longer a backlog. Every record on it has moved to the page it belongs to, and the page is kept only so old #gap-N links still resolve. There is nothing left to route from it. Open work now lives in three places: bugs in GitHub issues, unseen behaviour on each page’s Verification tab (collected on Open checks ), and plans in intake/ treatments and on Roadmap tabs (collected on the roadmap ). check-roadmap-execution.mjs still fails if a record on Known gaps is marked Open and is not linked from this section. That is the guard against the page quietly becoming a backlog again. If it fires, move the record to its page, or file it as an issue if it is a bug. Do not list it here. Session start and closeout packet Copy this small packet into the session notes before implementation. It is deliberately shorter than a design document: its job is to preserve routing and evidence between sessions. Slice: Owner page: Production anchors: Hypothesis: Disconfirming check: First edit: Focused result: Tests added or run: Generated artefacts updated: Runtime checks still needed: Next blocked gate: Closeout is complete when the focused result is recorded, the owning page says what is now true, generated artefacts are current, and the next session can begin from the named blocked gate without rereading the whole project. A session that found only that the report was stale should record that result and stop; it should not invent a replacement feature. What is left of the fix pass This section was the order for clearing the defects reported up to 2026-09-24. Most of it has shipped since, and is unplayed rather than unbuilt. New defects no longer join this list: they are GitHub issues, ranked and taken one at a time by /fix-bug . What is written here is what remains of the original six stages. Each one is still worth doing before new content on the same code, because a defect hidden inside a new system is harder to find. 1. There is still no server request for a record by UUID : HorseRecordSyncPayload is keyed by entity id. HorseQuery has no sold, dead or owner predicates. Unit tests still owed: record lookup by UUID, cache hit and miss, stale entity-id rejection, transfer ownership, sold/dead historical rows, and filters over a horse beyond the roster cap. 2. The required hardening matrix Whatever stage or issue is being worked, it is incomplete until its tests pass across these states: loaded and unloaded; tracked and untracked; alive, dead and sold; owned, transferred and unowned; owner online and offline; one horse and many horses; success and refusal; menu open and menu closed; save and reload between actions; singleplayer and dedicated server. Use the same matrix for the H menu, the info screen, breeding, notifications and equipment, rather than inventing a partial checklist for each. New-content vertical slices in dependency order These are the recommended clusters. Each slice should cross the relevant common model, server behaviour, client surface and tests when those layers apply. Do not build a large foundation without one player-visible proof using it. New features arrive as intake/ treatments and are built by /process-intake . The clusters below are where those pieces land. Breeding and horse behaviour Owner: Fertility & gestation and Horse care . Shipped 2026-09-24: bond reach, ground food, pasture edge, mouth reach, the stallion's day, the crowding cap, the cover notice and no kin gate. Both of the old gate questions are settled. “No incest prevention” means no restriction at all ( no kin gate ), and a full pen is a refusal the owner is told about. What remains is playing an owned pen and a wild band against the same rules. Owned horses and records Owner: The horse browser , with Villagers & transfer papers for selling and naming. Several things shipped without a registry: sold-horse greying (in the family tree only), owner damage and death notices, barn naming, and the H-menu Log tab . The server-side owned-horse registry is still owed , for three things: live roster refresh on birth, death, taming and transfer; rows beyond the roster cap; and sold and dead rows kept in My horses (see the exits treatment in intake/ ). First proof: register one horse, sell it, damage it, kill it, and breed a new one while its chunk is unloaded. The browser must keep the historical row, show the correct owner-facing notifications, and refresh from server state rather than from a client guess. The decisions page , the undead page and the philosophy page still call it open. Moving the answer onto those pages is the treatment's first step. A gate is finished only when its answer is written on the decision page or the owning page, and the losing alternatives are removed from the implementation plan. Otherwise the next session will spend its first hour reopening the same question. The execution loop Choose one slice. Name the player-visible outcome and its owning page. Read the gate. Check decisions, the open GitHub issues on the same code, and nearby Verification items before touching code. Find the narrowest owner. Put rules in common/ when they are game-free; keep NeoForge as translation and orchestration. Make the smallest end-to-end edit. Prefer one real item, one query, one notification or one behaviour over an empty framework. Run the cheapest falsifying check immediately. Use a focused test, fixture, parity check or narrow build before expanding the slice. Regenerate every derived artefact. Follow the build table , especially golden coats, WASM, generated wiki pages and search indexes. Update the owning page. Move shipped work off Roadmap, record what was seen on Coding, and leave only genuinely unbuilt work behind. Stop at a clean boundary. Record the next blocked gate and the one best next check in the session log. The slice brief Before implementation, write this compact brief on the owning page or in the session notes: Outcome: one sentence a player can observe. Owner: one wiki page and one primary code owner. Decision gate: the answer that must already be settled. Prerequisites: existing data, attachment, payload or UI contract. First proof: the smallest complete path from input to visible result. Acceptance: observable pass conditions, including refusal and failure cases. Checks: the cheapest focused test, then required regeneration commands. Out of scope: adjacent ideas deliberately left for a later slice.
