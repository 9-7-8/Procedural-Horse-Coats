Config

What a server owner or a single player may turn down, turn off or retune without touching the code. Every key the mod reads is listed on the Gameplay tab, baked from the config classes themselves, with its default, what it accepts, the comment the file carries, and the page of the feature it governs. The surface grew an option at a time wherever one was needed; the Roadmap tab is the sweep that would give it a shape, and the place the refusals live — there are things that look like config and cannot be, and the genetics are the sharpest of them.

Every key

Five files. The two in .minecraft/phc/ beside the genes/ and breeds/ drop-in folders are this mod’s own; the carts keep the two they came with, in config/. Each file is written out with its defaults the first time it is loaded — the server ones when a world is first opened — and each key in it carries the comment quoted in the last column here, so the file and this table say the same thing.

  • Server keys are gameplay: one answer for everybody on a server. A single-player world is a server too. <world>/phc/server.toml overrides the shared one for that world alone, and a client on a server reads the server’s values, never its own.
  • Client keys are what this machine draws, and a few remembered preferences. Two players on one server may set them differently and neither is looking at a different world.
  • Common keys are read at startup, before any world exists, and each machine reads its own copy; only the side that spawns horses acts on them. Which biomes get wild herds at all is decided when a world starts, so a change to a breed’s biomes needs a restart.

Edits to a file while the game runs are picked up without a restart, except where a key’s own comment says otherwise. A key whose feature page does not name it yet is marked so; this table is then the only place it is written down outside the file.

Every horse search box in the mod reads this one list - My horses, Horse realm, the breeding pickers and the stasis bank - so a search saved in any of them is offered in all of them. A query is a SQL WHERE clause: AND OR NOT ( ) IN LIKE, columns for the table's own fields, and a gene name as a column whose value is hom / het / none / any. For example:
  keepers=mare AND generation > 2 AND NOT lethal
  breed on=sabino = hom AND (flaxen = het OR flaxen = hom)
The name is whatever you typed when you saved it, or the query itself if you did not type one. An '=' in a name is not allowed, since it is what separates the two halves. Yours alone, and on this machine: it is a client preference, not something the world or the server knows about. Feature page

How the table is made

wiki/tools/bake-config-keys.mjs reads the four classes — ServerConfig, ClientConfig, BreedSpawningConfig and carts/CartsConfig — and rewrites the span between the BEGIN/END generated config keys comments on this page. --check exits 1 instead when the span is stale. It is row y of procedures/rebake.txt, and step 9 of add-a-config-option runs it.

  • It reads the Java source, the way the builder does. A comment() waits for the next define* call, or for a push(), which takes it as the section’s comment; push and pop build the dotted key. A key with no comment of its own — the four per-breed keys — takes its line from the enclosing section’s comment, where BreedSpawningConfig describes each one.
  • A default that names a constant is read from the constant, in the same file or in common/ (ReproRules.DEFAULT_NATURAL_CAP), so the table cannot disagree with the game about a number. An enum key’s allowed values are the enum’s constants. The few defaults that are not constants — !production(), a breed’s own weight — are words in the script’s PLACEHOLDERS.
  • Loops are written once, as a template. One section per shipped breed and one per CartKind are listed as breeds.<breed id>.* and carts.<cart id>.*, not once per breed: the breed’s own file is what fills them in.
  • It fails rather than write a short table. Every .define*( in each builder must become a row; every key needs an entry in the script’s HOME map (its feature page, the one hand-written thing in it), every HOME entry must name a live key and an anchor that exists; a default it cannot evaluate is an error, not a blank cell.

Reading source rather than booting a game and walking the built ModConfigSpec was a choice of cost: the NeoForge module’s test classpath carries no Minecraft on purpose, and a bake that needs a server boot would be run less often than one that takes a second. The price is that a builder written in a shape the script has never seen fails it, which is the safe direction.

Config: tune or disable basically everything

Asked for as a sweep. What exists is the key table: hand-written options in ServerConfig and ClientConfig, each added beside the feature that needed it, plus two generated blocks that are genuinely thorough — BreedSpawningConfig writes four options per shipped breed, and CartsConfig a block per CartKind. Two of the client keys, search.saved and genes.filter, are remembered UI state rather than settings anybody goes looking for, and tutorial.seen is the same.

What is not configurable, and each of these is a deliberate gap to reopen rather than an oversight: the genetics themselves — every gene is always registered, always occupies its genotype slot and is always inherited, whatever health.mode says — coat generation, every bond and care number except the two the daily bond decay reads (behaviour.bond_decay_per_day and behaviour.bond_floor), hunger rates, cowboy and stable and barn spawn rates, herd sizes, whistle radii, ticket behaviour, prices, jump sizes and styles, the armour protection ladder, and everything about the horse menu.

  • The genetics are the interesting refusal. A per-gene disable switch is the most-requested shape of this ask and the most dangerous one here, because a genotype code is positional — a gene that stops occupying its slot is a save format change and every existing horse reads wrong. If per-gene config is wanted it has to mean expression or founder frequency, never registration. The author-time version of this problem is already settled — an absence from genes/index.json is a killswitch, which is why that file is never regenerated from the folder (gap 162) — and that is the precedent to read before designing a runtime one.
  • Do it as one pass with a convention, not option by option. A drawerful of scattered scalars is what a config grows into when each is added where it was needed; a sweep is the chance to fix the shape — one file per concern, generated blocks where the roster is data, and a rule about what may be a server option versus a client one.
  • Every new system on this page should ship its own switch. Cheapest when written with the feature and near-impossible to retrofit consistently — the tack bench is the model, where one switch disabling the bench disables all horse-armour crafting with no per-recipe gating anywhere. The returned lead (2026-09-24) is the first thing to ship under this rule rather than be retrofitted to it: behaviour.leads_return was written in the same change as the behaviour, and off it restores vanilla exactly rather than half-disabling anything. ops.resurrect_grace_minutes (2026-09-26) is the second, and it is the case where the switch is not a preference at all — what it bounds is how many whole dead horses the world save is carrying, so an operator who never touches it is still being charged for it. A setting whose off position costs disk is one that has to ship with the feature. behaviour.mounted_mining_penalty_removed (2026-09-29) is the third, and it is the one that answers a piece of the server-versus-client question above rather than just obeying the rule: it is the first option in the mod read by client-side code. It can be, and stays a server option, because FML’s javadoc on ModConfig.Type says a SERVER config is “synced to clients during connection” — so a rule that both sides must compute identically does not need a client option, it needs a server one that the client is allowed to read. The convention that falls out: a client option is for what only the client can see; anything both sides compute is a server option, read on both.
