Config

What a server owner or a single player may turn down, turn off or retune without touching the code. Some of it exists already — a handful of hand-written options and two generated blocks — but it grew an option at a time wherever one was needed, and the ask is a single sweep that gives the whole thing a shape. This page is that plan, and the place the refusals live: there are things that look like config and cannot be, and the genetics are the sharpest of them.

Some config already exists — this page is its plan, not its reference

A config surface is in the game today: a small, scattered set of hand-written options across ServerConfig and ClientConfig, plus two genuinely thorough generated blocks in BreedSpawningConfig and CartsConfig. What follows describes that surface and says what should become of it; it is not a list of the options themselves, and the option list is not documented anywhere in the wiki yet. Config: tune or disable basically everything

Asked for as a sweep, and the current surface is smaller than it looks. Roughly fifteen hand-written options across ServerConfig (health mode, body size, three riding numbers, gestation days, two debug switches) and ClientConfig (scroll bar, sex symbol, tutorial, right-click to open, two coat-rendering numbers), plus two generated blocks that are genuinely thorough — BreedSpawningConfig writes four options per shipped breed, and CartsConfig a block per CartKind.

What is not configurable, and each of these is a deliberate gap to reopen rather than an oversight: the genetics themselves — every gene is always registered, always occupies its genotype slot and is always inherited, whatever health.mode says — coat generation, every bond and care number, hunger rates, cowboy and stable and barn spawn rates, herd sizes, whistle radii, ticket behaviour, prices, jump sizes and styles, the armour protection ladder, and everything about the horse menu.

  • The genetics are the interesting refusal. A per-gene disable switch is the most-requested shape of this ask and the most dangerous one here, because a genotype code is positional — a gene that stops occupying its slot is a save format change and every existing horse reads wrong. If per-gene config is wanted it has to mean expression or founder frequency, never registration. The author-time version of this problem is already settled — an absence from genes/index.json is a killswitch, which is why that file is never regenerated from the folder (gap 162) — and that is the precedent to read before designing a runtime one.
  • Do it as one pass with a convention, not option by option. Fifteen scattered scalars is what a config grows into when each is added where it was needed; a sweep is the chance to fix the shape — one file per concern, generated blocks where the roster is data, and a rule about what may be a server option versus a client one.
  • Every new system on this page should ship its own switch. Cheapest when written with the feature and near-impossible to retrofit consistently — the tack bench is the model, where one switch disabling the bench disables all horse-armour crafting with no per-recipe gating anywhere.
